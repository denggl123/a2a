## 已完成

| 部分 | 交付内容 |
|---|---|
| 业务与结算边界 | `TradeService` 独立负责询价、免费资格、接单、实际调用和原交付恢复。前十次技术成功样品强制公开脱敏投影，完全跳过支付协调及所有支付方法，不建零金额订单 |
| 独立积分方法 | SDK `PointsBook`、Node `PointsNode`；每个供应方仅维护自己发行的积分，分别记录发行方和持有方，不合成全网余额 |
| 服务发行 | EARN：真实服务后增加供应方持有的自家积分；DEBT：同时记录使用方欠账；技术失败不发行，质量评价另行记录 |
| 主动加分 | 供应方可明确新发行到使用方，也可转移自己的存量；命令重复返回原分录 |
| 已有积分支付 | PAY 只转移已有积分，不重复发行；按使用方指定的发行币种和最大总成本选自愿接受路径 |
| 接受与兑换 | 各方自己的比例、单笔/每日/持有上限；最多三跳服务兑换、两方或三方循环交换；整数倒算与向上取整 |
| 欠账与还账 | 供应方设定欠账额度；预留阻止并发超额；用原供应方积分偿还原欠账 |
| 整体提交 | 全体签名确认、持久预留、唯一提交/中止决定、幂等分录和收据；断线后的原决定补送与参与方主动核对 |
| 交付恢复 | 读取原供应方签名交付、核验结果和合同；不会重跑 Agent。确实未接单的请求先封闭迟到执行，再整体中止 |
| 原积分退款 | 双方接受原退款方案；按供应方实际收到的发行方积分退款，含第三方发行积分；累计金额和重复执行受到约束 |
| 控制台 | 账户、发行与服务政策、接受表、主动加分、还账、循环兑换、原订单核对；业务条件页选择 EARN / DEBT / PAY 与付款成本上限 |
| 完整产品 | Windows 单文件程序和 Linux 镜像包含全部模块；SDK 继续零第三方依赖；旧业务入口委托同一业务服务 |

PAY 不额外发行、主动加分区分 ISSUE 与 TRANSFER，是这次采用的明确分录规则。供应方自行定价；是否接受以及兑换比例继续由其他使用者决定。平台不抽佣、不保管钱包、不提供全局汇率。

### 实际断线恢复

1. Windows 使用者向 Docker A 请求服务，选择 A 发行积分作为付款单位。
2. A、B、C 的接受条件形成三跳：使用者给 B 1 份 A 积分；B 给 C 5 份 B 积分；C 给 A 5 份 C 积分。与同币种直接成本 5 相比，使用者本次总成本为 1。
3. 全体完成准备后，实际停止 C 容器，再执行 A 的真实 Agent。业务显示付款待确认，原积分订单保留 COMMITTING。
4. 重启 C 后核对同一交易，取得四方收据。各发行账本的最终余额严格符合原三跳分录。
5. 再次执行原计划，Agent 调用次数和各发行账本余额均不增加或重复扣减。
6. 随后实际完成 A/B/C 三方循环交换；重复请求返回原计划及原收据。
7. 双方协商退回 2 份原交易实际收到的 C 积分；C 的发行账本记录 A 向 Windows 转回，原服务不重新执行。

本轮保留 A/B/C 各供给的首十个公开样品。A 共完成 14 次、B 和 C 各完成 11 次；后续积分服务不替换原样品。
