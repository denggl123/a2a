## 发现的问题

### 1. [P1] 运行实例没有统一升级和配置，当前四节点发现环断开

Docker C 仍指向未监听的 18885；Windows 仍认识三个未监听的 879x 旧入口。当前 CLI 默认管理端口 8771，读取本机节点时报“指定节点尚未就绪，或端口与节点目录不匹配”。因此目前有四个节点实例，但未形成启动脚本约定的 `A → B → C → Windows → A` 发现环。

`network-local.json` 中的 45 项成功记录时间是 `2026-10-05T00:57:23.212021+00:00`，对应另一 Windows DID `did:a2n:ag_db841d51e2ac849aaa25dec9`，不能用作当前运行状态的证明。三个 Docker 镜像也尚未载入 `f3a6243` 的修复。

建议统一 Windows 的节点目录、身份和端口，保留数据；重建当前源码的 Docker 镜像并沿用三个数据卷；更新各节点发现地址，再执行四节点 12 个交易方向的 45 项验收。应先处理现有 Windows 实例，避免启动入口另外创建一个本机节点，导致实例数量和身份继续混淆。

相关入口：`scripts/start_network.ps1:44`、`:66`，`scripts/network_acceptance.py:27`。

### 2. [P1] 新签名错误没有接入邮箱工作线程，正常协议错误被变成断线和超时

位置：`packages/a2n-node/src/a2n_node/coord_mailbox.py:48`。

`PublicCoordination.handle()` 现在会为认证后的错误抛出 `CoordFailure`。邮箱工作线程仍直接调用它，把所有异常视为邮箱连接失败，清除 `registered`、`mailbox_route` 和会话，也没有向原请求者发送异常中已有的签名 ERROR 封套。

隔离双节点真实 HTTP 复现结果：

- 通过邮箱发送 PROBE 成功，证明正常连接有效。
- 请求不存在的商品卡，目标节点实际得到 `NOT_FOUND`。
- 调用方得到 `DEADLINE_EXCEEDED`，而非目标签名的 `NOT_FOUND`。
- 目标节点的邮箱注册状态变为 `false`。

正常的卡片失效、限流或无效查询都可能触发此路径。应在单个请求处理处捕获 `CoordFailure`，把 `exc.envelope` 作为邮箱应答；只有真正的邮箱传输或认证失败才重建会话。补上邮箱转送错误路径回归，当前新增测试只覆盖直接 HTTP 错误。

复现入口：`.tmp/review_mailbox.py`，使用临时加密数据目录，不接触现有节点数据。

### 3. [P1] 公共代理在网关保护之前无上限读取请求体

位置：`packages/a2n-node/src/a2n_node/public_entry.py:71`。

公开代理先将外部 `Content-Length` 转为整数并执行 `rfile.read(length)`，之后才转发至有 262144 字节协调请求上限的内部网关。代理层没有请求体大小检查、连接读取超时或连接并发上限。

隔离复现：向临时公共代理发送协调请求，声明 262145 字节而仅发送一个字节，代理继续等待请求体，没有提前拒绝已经明确超限的请求。内部网关的限制此时尚未生效。未认证客户端可用慢速或超大请求占用线程和内存，这会影响节点必须提供的公共发现服务。

应在公共代理读取正文前验证长度并按公开协议路径限制大小，设置有界读超时和连接并发限制。大任务中继和普通协调请求可以采用各自上限，不应统一放开。

复现入口：`.tmp/review_public_entry.py`，临时端口、单连接、小数据量验证。

### 4. [P2] 部分搜索成功时，界面却提示没有取得商品

位置：`packages/a2n-sdk/src/a2n_sdk/web/coordination.js:49`。

新分支只检查 `searchErrors` 是否非空，未检查已经取得的候选数量。一个来源成功、另一个超时时，候选列表保留有效商品，但提示“没能取回可核验的商品”。

复用现有控制台隔离 VM 实测：`candidateCount=1`，提示仍是“「add」已向外发出查询，但没能取回可核验的商品：one source timed out”。应区分无结果、部分成功和全部成功，部分成功显示已取得数量及失败来源。

复现入口：`.tmp/review_ui.cjs`；现有 131 项逻辑检查没有覆盖 `searchCoordination()` 的此种提示组合。

## 对业务愿景的判断

源码保持 `Daemon → NodeRuntime → LocalStore` 的单一装配和五个包，强制公共发现、可选样品/见证/中继开关方向一致。免费调用、真实样品、双方签名反馈及收据等基础能力已经具备，最新提交没有引入第二套业务体系。

最终信誉排序、防刷、机会分配和自动淘汰仍未实现；当前反馈事实及平均值不能视为信誉机制已经完成。真实支付、公网接入和独立离线安装包也仍是文档明确列出的未完成事项。四个本机实例的测试不能证明四个独立使用者或公网站点之间的效果。
