# 本机与 Docker 业务修复交付

日期：2026-10-08。环境：一个 Windows 完整 SDK、三个 Docker 节点。全部节点保留原身份和加密业务库。

## 1. 修复结果

### 信誉限制不再因来源缺失而失效

- 建立 LIMITED / MANUAL_ONLY 时保存充分支持的决策、事实摘要、算法与策略版本、决策时间和 30 天有效期。
- 来源离线、缺页或查询额度不足时保留原限制；不把缺失意见解释为表现改善，也不凭不完整查询加重限制。
- 重复复算同一批交易不升级或续期。新合格低质量交易才可以推进限制。
- 作者有效修订、撤回及完整查询支持的变化允许恢复；期限届满回到 OBSERVE 并提示复核。主人屏蔽由主人解除。
- 模式变更立即应用于既有记录：切回 SHADOW / SUGGEST 停止自动限制；DISABLED 清除算法限制，主人屏蔽仍保留。

实现：`a2n_sdk/policies.py`，控制台显示保留原因、有效期和复核状态。

### 待付款订单不再无限锁住设置

- 设置变更产生一个加密保存的通道版本；新报价用新设置，旧订单固定原钱包、原链、原资产、原 RPC 和原驱动。
- 卖方接受凭证单列 OPEN / EXPIRED / EXPOSED / REVOKED / FULFILLED 等授权状态。未付款过期可以改设置，资金事实不会被改成“付款失败”。
- 未知付款保持原订单，只核对原通道。钱包轮换、关闭当前通道和重启后仍能查询原付款；退款也使用原单对应的钱包与通道。
- 相同钱包的原生币交易序号在同一个账本事务中预留，旧版本和新版本不会分别分配相同序号。
- 有效及暴露中的接受凭证受全节点 512、单买方 16 的上限约束。
- 控制台不再为已经过期的 READY 计划提供新付款按钮，保留取消和原事实核对入口。

实现：新增 `a2n_node/payment_channels.py`，调整 `payment_service.py`、`evm_payment.py` 和支付控制台。

升级前已被其他程序覆盖且未保存的旧配置无法凭空恢复；本次迁移绑定升级时仍可取得的配置。升级之后的通道版本会保留。

### 补齐命令行管理入口

统一 CLI 支持 PUT，可通过修订头修改业务策略。检查同时验证了成功更新和过期修订冲突拒绝。

## 2. 实际代码 Agent

源码：[文本结构分析 Agent](../examples/text_inspector/agent.py)，使用说明：[README](../examples/text_inspector/README.md)。

这个服务实际处理文本，返回字数、行数、段落、词频、短摘要及输入 SHA-256。中文按单字、英文按单词统计；不使用外部模型。它在独立 Docker 服务中运行，通过 SDK 的受保护接口显式上架，普通产品启动不会自动发布它。

保留的商品：`text-inspector-cf74dc27ae`，提供方：`node-a`。Windows、node-b、node-c 工作台均已导入 `text-use-cf74dc27ae`。技能是 `inspect`，输入形如 `{"text":"需要分析的文本"}`，当前明确声明免费。

本轮成功验收进行了 12 次正常交付和 1 次双方同意的补做，Agent 实际执行增量恰好为 13。前十次为 FREE_INITIAL，后两次为 FREE_VOLUNTARY。重复执行请求及重复补做请求读取原结果，没有新增上游执行。

前十个槽位全部公开；公开投影中不含测试邮箱或原任务号。质量意见的修改和关闭异议没有改写这十个槽位。

受控流程还验证了：

1. 三个买方身份签名发布意见，卖方也能对真实买方写签名反馈。
2. 多来源查询取得三个有贡献对手组；观察之后，新增交易意见推进 LIMITED、MANUAL_ONLY。
3. 本机策略实际拒绝新调用，上游执行计数不变。
4. 查询额度不足导致来源不完整，已有充分支持的限制仍有效。
5. 作者修订为正向意见后重新查询，恢复为 NORMAL；旧版本不重复计权。
6. 双方签名同意补做；异步交换在双方落库后显式开始一次新关联任务；重复启动不多执行。
7. 双方签名关闭异议，原交付和样品保持可读。

最终恢复原 SHADOW 策略。四个调试过程中创建的商品已下架，原样品和历史留存；成功商品仍可调用。调试流程留下的一项异议也已由双方签名关闭。

复现脚本：[local_business_acceptance.py](../scripts/local_business_acceptance.py)。脚本会创建新的验收商品，并短暂启用受控阈值，在结束时恢复原策略。意见明确标为受控验收，不代表独立真实用户反馈。
