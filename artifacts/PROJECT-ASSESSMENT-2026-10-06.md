# A2N 项目完成度与非营利价值评估

日期：2026-10-06。依据：发起人的愿景、当前工作区源码、既往实测记录、本轮四个本地节点管理查询、第五节点公共查询，以及隔离环境的机会策略回放。

## 1. 总体判断

**A2N 已具备开展小规模免费业务试点的工程基础。核心价值主张清楚，真实供需生态和长期信誉治理效果仍需证明。**

阶段估计：

| 评估口径 | 当前判断 | 解释 |
|---|---|---|
| 首版功能工程 | 约 80% | 单一节点体系、发现、免费交付、履历、双方反馈、安装与恢复已有实现和测试；收费、媒体及部分生命周期能力仍欠缺 |
| 普通用户独立使用的交付成熟度 | 约 50% | 新电脑、自动入网、跨公网、长期常驻、发行签名及用户操作成本仍需要实机试点 |
| 公平交易与信誉自净的真实效果 | 尚未验证 | 当前公开反馈投影、信誉视图及机会记录均为零，缺少独立买卖双方的持续业务数据 |

比例是按上述范围做的阶段估计，并非测试覆盖率或按代码行数计算；剩余任务的工作量不能按比例线性推算。

## 4. 架构质量

目前为五个代码包、六个逻辑层：基础、网络、协调、业务、接口、产品装配。六层与五包属于不同划分维度。

优势：

1. 单一身份及加密业务库，记录归属清楚，迁移和备份能够保持历史。
2. SDK 业务规则通过端口注入网络、身份、验收与资金实现；信誉计算本身不做网络 IO。
3. 公共发现义务与商品信誉分开，基础网络服务不因为业务差评而关闭。
4. 任务事实、意见、资金与协商分开，能够表达交付成功但质量拒绝、结果未知等实际情况。
5. 有实际依赖方向与无环检查，单一装配及体系退役有测试支持。

维护债务：

- 管理处理器约 973 行、本机 HTTP 处理器约 889 行、Daemon 约 730 行，新增功能仍容易集中到少数大文件。适合逐步分离命令与查询处理、生命周期协调和业务编排。
- 许可、贡献规范、安全报告渠道及仓库 CI 工作流目前未见根级正式交付文件。
- 文档中仍混有历史平台、旧开关和旧进度；接手维护时需要明确一份当前事实索引。
- 发行签名、版本兼容、升级异常终止恢复和新机试点尚未组成稳定发行流程。

当前 A2A 接口采用 `message/send`、`tasks/get` 和 `agent.json` 等形态，未见 A2A 1.0 的版本协商和 `supportedInterfaces` 实现或官方客户端互操作验收。官方 1.0 规范包含版本选择和标准 AgentCard 发现要求，外部生态兼容应单独补齐。[A2A 1.0 规范](https://a2a-protocol.org/v1.0.0/specification/)

## 5. 非营利价值

### 5.1 把调好的工作流变成可使用的成果

使用者得到一个有说明、案例和交付规则的能力，减少配置模型、依赖、机器和流程的重复劳动。下一阶段能否提供真正有用的 Agent，决定这一价值能否被普通人感知。

### 5.2 让供需双方保有自己的记录和选择权

本地账本、节点身份、双向反馈及本机策略，使参与者能够保存履历、核对事实、选择对手与承担明确范围内的损失。退出或迁移时保有身份和记录具有长期价值。

### 5.3 用免费真实交付帮助买卖双方认识彼此

首十次采样能够把用户测试转化为可见案例，也降低首次尝试的成本。样品需要让人理解需求、成果和质量情况；公开槽位本身不足以证明 Agent 好用。

### 5.4 形成分布式互助网络

节点通过引荐让各自认识的能力能够被更多人发现，不依赖一个必须完整收录所有 Agent 的目录。这个设计适合先从一个有共同任务的社区形成真实使用循环。

### 5.5 把诚信变成可解释的长期行为约束

双方意见、真实交付锚点、来源、版本与贡献上限，提供了比单次情绪评价更扎实的基础。公平效果仍取决于独立参与者、来源覆盖、参数校准及误伤恢复。

非营利定位可以与供给方收费并存。卖方持续承担机器、流量和工作流维护的安排，会影响网络能否长期提供有用成果；项目零抽成能够保持其公共服务定位。

## 6. 需要正视的设计边界

### 6.1 “不诚信必然淘汰”无法仅靠签名保证

一个人可以控制多个节点，自交易或用新身份重新入网。签名验证来源与完整性，不能证明多个评价者独立，也不能保证主观意见真实。多身份攻击是去中心化信誉的基础问题。[Douceur：The Sybil Attack](https://www.microsoft.com/en-us/research/publication/the-sybil-attack/)

合理目标是让已有不良履历逐步降低机会、使重新建立可靠履历需要真实交付，并保留新人进入与被误判者恢复的通道。不同节点看到的评价不完全相同，最终判断也可能不同。

### 6.2 来源缺失会让已有实际限制退回正常

本轮用仓库既有测试数据，在隔离的内存业务库中回放：

| 步骤 | 记录状态 | 实际生效状态 |
|---|---|---|
| 已有足够负面意见，启用 ENFORCE_LOCAL | LIMITED | LIMITED |
| 保留相同意见，仅改为已知来源查询不完整 | LIMITED | NORMAL |

代码将自动限制生效与 `known_sources_complete` 绑定。这个规则保护信息不充分的对象，但也会放松已存在的风险限制。启用自动限制前应区分：暂缓新增惩罚、已有风险的有效期、恢复需要哪些新事实。当前现网处于 SHADOW，本轮只进行了隔离回放。

### 6.3 公开规则依赖在线节点与可公开内容

合规程序强制首十次技术交付形成公开履历，现版本并非全网永久存档。节点停机、删除本地数据、重新生成身份或改用不合规实现，都会影响履历可获得性。

自动脱敏能处理已知格式，不能识别任意商业机密。强制公开应在调用前明确展示，并用于适合公开采样的任务。公开案例质量、隐私告知及必要的多来源保留需要真实使用验证。

### 6.4 一键安装后的入网和成熟工作流部署仍有成本

新电脑仍需认识至少一个可用入口；NAT、休眠、重连及出站邮箱的实际运维尚需联验。当前私有文件单件 16 MiB、总容量 128 MiB、音视频预览及流式交付缺失，对视频成果场景存在直接限制。

WASM 包的权限和资源限制已实现，GPU 工作流、模型下载、依赖管理和大文件成果交付尚未覆盖。

## 7. 建议的下一阶段顺序

### 第一阶段：使真实任务在不同电脑之间持续可用

- 完成五节点 20 个方向的真实结果、签名、恢复及文件读取验收，核对远端实际版本。
- 完成一台普通用户新电脑的安装、首次入网、重启、备份恢复和升级中断试验。
- 选择 2–3 个适合公开采样、具有明确成果的实际 Agent，覆盖真实任务及用户可读的案例。
- 为真实供给明确超时、并发、机器及第三方服务成本的限额。

### 第二阶段：兑现重信誉的使用闭环

- 把反馈、公开短评、体验查询、本机信誉计算和机会解释接入用户日常操作。
- 解决来源不全时已有限制失效的规则；明确重入网免费服务的强制或可选语义。
- 邀请 10–20 位独立参与者试用；这是建议的试点规模，不是现有用户数。
- 验证反复低质量交付、不诚信陈述、恶意差评、多身份互评，以及解释、误伤与恢复。
- 在可观察、可撤销的本机范围内逐步从观察转向建议和执行。

### 第三阶段：提升交付与互操作

- 改善首次发现、选 Agent、看案例、执行与查看结果的主流程。
- 依据真实任务增加工作流后端、合理的大文件传输和音视频案例预览。
- 完成官方 A2A 客户端及服务端的互操作验证，明确协议版本与兼容策略。
- 建立许可、贡献、安全报告、CI、发行签名及版本变更规则。

### 第四阶段：满足供给方的收费需求

- 完成一个明确模式的收费报价、接单授权和真实支付驱动。
- 联验到账、UNKNOWN 对账、退款；进一步验证创作者分成。
- 继续以平台零抽成为规则，按实际供给需求安排开发优先级。

## 8. 用什么衡量非营利项目的成功

1. 普通人独立完成安装、找到合适 Agent、取得成果的比例及耗时。
2. 非测试任务的完成率、实际满意度和主动重复使用。
3. 描述、公开样品是否与真实交付一致，是否帮助用户做出选择。
4. 双方反馈参与率、可验证公开意见覆盖和实际使用信誉信息的比例。
5. 不可靠对象在出现充分新事实后如何失去机会，以及误伤和恢复的比例。
6. 新供给是否能得到合理的首次尝试机会，用户数据和履历能否迁移。
7. 公共发现对参与者 CPU、流量及维护时间的负担。
8. 核心规则和代码是否能够由更多维护者接手。

## 9. 能发展成什么

- **近期：一个小社区内的成熟 Agent 互助市场。** 先证明具体任务能完成、案例能帮助选择、双方履历能改善后续合作。
- **中期：工作流成果与信誉履历的共享规范。** 不同社区和工具可接入共同规则，参与者保有自己的账本与本机选择权。
- **长期：跨组织、跨网络的 Agent 供需协作基础。** 实现这一阶段需要独立社区参与、稳定互操作和经过真实使用检验的治理规则。

**值得继续推进。下一阶段价值增长主要来自有用供给、独立用户、可靠交付和实际发挥作用的信誉规则。**
