# 自持模式（无服务器 · 无托管）：差多远，补齐了什么

> 目标原话：**没有托管商（积分不上线）时，它就是一个去中心化的网络（不需要服务器）；
> 任意大于两个人用，就能相互发现、相互调用。**

结论先说：**发现层本来就已经不在服务器上；断点在"调用"这一环。**
平台模式下，"我调你"这个动作由三样东西承担 —— 平台中继负责把请求送过去、
平台注册表负责给出对方的地址、平台门禁负责判断该不该放行。
这三样去掉之后，剩下的是一个**节点形态的装配体**：`packages/a2n-node`。
本次补齐的就是它，平台侧一行没改。

---

## 一、差距对照：逐项看"平台模式靠谁"→"没平台时缺什么"

| # | 能力 | 平台模式靠谁 | 拿掉平台后缺什么 | 现在怎么做的（落点） | 状态 |
|---|---|---|---|---|---|
| 1 | 身份 | 平台发 `uid`，`agents` 表登记 | 没人分配 id，也没人背书 | 身份 = 公钥指纹 `did:a2n:ag_<sha256(pub)[:24]>`；卡自带 `pub`+`sig`，验卡不需要任何机构（`card.build_card` / `card.verify_card`） | ✅ 补齐 |
| 2 | 发现 | 查平台注册表（`registry` 表） | 没有全局目录 | 邻居 gossip + 多跳按需查询；HELLO 验签并绑定 DID↔公钥，OFFER 沿实测反向路径返回，按技能携带 MTU 内“业务入口 + 卡哈希”，不广播完整目录 | ✅ 已有 + 加固 |
| 3 | 找地址 | 对外只发 `/v1/relay/{id}`，真实地址不给别人 | 没有中继可退，地址必须自己给 | 卡里自带 `url`（`card.card_endpoint`）；`verify_card(require_endpoint=True)` 明确拒绝"没有直连地址"的卡 —— 没有中继时，留空就是不可调，不该假装能调 | ✅ 补齐 |
| 4 | 调用 | `hub.forward` 平台代发 + `gate.resolve` 门禁 | 没有中间人，也没有中心门禁 | 每个节点自己开 HTTP 入口（`peer.serve`），请求直连对方 `/a2n/call`；请求**自带 DID 签名**（取代平台模式的明文 `X-Principal` 声明） | ✅ 补齐 |
| 5 | 供给方守门 | 平台门禁 + 上架校验 | 门禁没人做了 | 门禁下沉到节点：`SovereignNode._admit`。默认只对开放能力放行；受限能力只吃白名单 did。**先验身份，再谈业务** | ✅ 补齐 |
| 6 | 交付凭据 | 平台 notary 写 `receipts` 表（中心事实） | 没有中心公证人 | **双边互签**：供给方签交付收据、调用方签回执引用该收据的签名（单向依赖）。两方各持带对方签名的证据（`receipt.sign` / `receipt.ack`） | ✅ 补齐 |
| 7 | 本地留痕 | 平台的 `receipts` 表 | 自己的库谁建 | 节点自己 `init_db()`，用既有 `a2n-notary` 在**本机**刻章（`task.created` / `task.submitted` / `acceptance.passed` / `delivery.acknowledged`） | ✅ 补齐 |
| 8 | 记账/结算 | 积分 + 托管（总量 ≡ 托管） | 没有发行方 | 无托管 = 无积分增发；`settle_mode` 目前只有 `free` / `bilateral`，后者表达双方约定并留下互证，不是任意币种的自动清算 | ⚠️ 通用去中心化结算未做 |
| 9 | 防重放 | 平台会话与凭据 | 会话没了 | 请求带 `nonce` + 时间窗，接收侧 `ReplayGuard` 去重（`peer.ReplayGuard`） | ✅ 补齐 |
| 10 | 篡改/冒名检测 | 平台改写有审计 | 没有审计方 | 签名域 = 整张卡 / 整份 body：改一个字节就验不过；`did` 必须由自带公钥推出，冒充不了别人（`card` / `receipt` / `peer` 三层同一条纪律） | ✅ 补齐 |
| 11 | 撤回 / 争议 / 仲裁 / 售后 | 平台 `acceptance` + 仲裁工作台 | 没有第三方裁决 | **不在本次范围**（见第四节边界） | ⛔ 未覆盖 |
| 12 | 全局信誉 / 排行 | `a2n-reputation` + 行情板 | 没有汇聚点 | **不存在**：信任只能由节点本地声明（白名单），或由调用方自己积累的调用历史决定 | ⛔ 按设计不做 |

一句话概括第 8 行：**"不需要服务器"的根因不是"服务器被替换掉了"，而是"没有账本需要一致"。**
只要积分还在发行，就必然有一个"谁记着总量"的角色；把托管拿掉，这个角色自动消失。

## 二、三条不变式（无托管模式下不是"省掉了"，而是"本就不存在"）

1. **没有发行方** —— 没有托管就没有积分增发。节点不产生钱，只产生事实
   （谁调了谁、干了什么、结果是什么哈希）。
2. **没有中心账本** —— 事实由两方互签、各存一份。任一方单独改写历史，
   对方手里的副本就是反证。
3. **没有全局目录** —— 发现靠邻居。你能看到多大的网，取决于你连了多少人。
   这不是缺陷，是"没有人能替你决定该看见谁"。

## 三、怎么跑

```bash
# 一个节点（自己的钥匙、自己的库、自己的入口）
python scripts/sovereign_node.py --name alice --home data/sovereign/alice \
    --skill upper-case --http-port 9661 --p2p-port 9761 --bootstrap 127.0.0.1:9762

# 同机安全演示：A ── B ── C，三者入口都解析到同一实测来源，因此 A 可取卡并调用 C
python scripts/sovereign_demo.py
```

```python
from a2n_node.home import use_home        # ① 先定库（零依赖，必须在最前）
home = use_home("data/nodes/alice")
from a2n_node import SovereignNode        # ② 再 import（这时才碰 a2n-store）

node = SovereignNode(name="alice", skills=["ocr-pro"], home=home,
                     executor={"ocr-pro": lambda p: {"text": p["text"].upper()}})
node.start()
card, why = node.find("ocr-pro")          # 发现 → 取卡 → 验卡 → 核对哈希（四步都不能省）
out = node.call("ocr-pro", {"text": "hi"}, card=card)
```

> **顺序不是风格问题，是正确性问题**：`a2n-store` 在 import 时读 `A2N_DB` 并缓存连接，
> 库路径一旦 import 就定死。"悄悄写进别人的库"是最难查的一类事故 ——
> 数据看着都对，只是写错了文件。所以 `use_home` 零依赖、且必须在最前。

演示脚本的 8 步（`scripts/sovereign_demo.py`）：

1. 三个进程、三个库：没有第四个进程在中间；
2. A 靠邻居看到 C 的线索 —— 多跳发现，**全是自报，一个字都还没验**；
3. 从实测来源取卡并本地验签 —— 身份自洽 + 卡哈希与发现阶段播的一致；为防 SSRF，
   跨主机的非直邻目标目前不会仅凭多跳 OFFER 自动取卡；
4. 直连调用 —— 请求打到 C **自己**的入口上；
5. 双向互证 —— A 手里有 C 签的收据，C 那边记着 A 的回执；
6. 改一个字节就露馅 —— 篡改输出哈希 / 改 task_id / 冒充签名者 / 掉包回执，全部验不过；
7. 再放一个人进来 —— 新节点只拿一个种子地址就找到了网络里的另一个人；
8. 结构性证据 —— 进程里 `a2n_server / a2n_custodian / a2n_account / a2n_settlement` **均未导入**。

## 四、已知边界（诚实清单）

1. **跨公网仍需要一个"会合点"和真实可达的数据路径。** 同机/同局域网靠 beacon 即可；跨公网至少要有一方
   有可达地址，或一个只做会合的 rendezvous（它不参与任何业务，不记账、不见内容 ——
   这是"会合点"不是"服务器"）。NAT 双向不可达时，可以打洞或走**自愿中继**：
   常驻节点已实现**经活跃邻居协调的 UDP 打洞**（三方签名报文，锥形 NAT 通常可通，
   **对称型 NAT/CGNAT 打不通**，跨真实公网 NAT 尚未实测）；中继会看到元数据（谁在
   什么时候找了谁），但看不到内容，也改不动凭据。ICE/QUIC 完整路径协商仍未实现。**
2. **没有全局信誉。** 去中心之后，"这人可不可信"没有第三方能替你回答。
   现在的做法是节点本地白名单 + 调用方自己的历史。想引入跨节点信誉，
   需要见证人机制（`a2n-consensus` 已有雏形），而见证本身又需要激励 —— 那就要回到钱。
   **这是"无托管"模式下最贵的一块空白，建议先不假装它有。**
3. **双边互证只覆盖两方。** 双方各自的副本互为反证，这是两方情形下可达到的最强保证；
   三方以上（例如"我说我交付了，第三方说没收到"）需要见证人，`a2n-consensus`
   的 2/3 见证权重可以承接，但没有托管时"见证的锚"是什么，需要另行定义。
4. **通用去中心化结算、撤回 / 争议 / 仲裁 / 退款不在本模式内。** `bilateral` 只记录
   双方约定和互签事实，不负责跨币种原子交换，也不能自动执行退款。纯免费能力交换不需要
   这些；一旦涉及当前产品里的真实付费，就必须回到托管 + 仲裁链路。
5. **密钥即身份。** 私钥丢了就是换了一个人，没有"找回账号"——因为没有谁有权给你补发。
6. **发现可见度取决于连接度。** 只连一个人，就只能看见那个人的邻居；多跳 OFFER 只是
   候选线索。当前安全策略只从签名直邻的实测源地址取完整 Card，所以真正跨主机的多跳
   目标还需要直邻会合、受信代理或未来的端到端安全传输层，不能把“看见”写成“已可调用”。

## 五、与平台模式的关系：同一个人，不是两套身份

| | 平台模式 | 自持模式 |
|---|---|---|
| 身份 | `agents.agent_id` | `did:a2n:ag_<指纹>`（同一个键推导） |
| 卡哈希 | `a2n_registry.card_hash` | **同一个函数**（`card.card_hash` 直接复用） |
| 验签 | `a2n_p2p.envelope` | `verify_pub`（**同一个实现**） |
| 事件名 | `task.created` / `acceptance.passed` … | 同名 + `delivery.acknowledged` |
| 调用结论 | 平台路由的返回体 | `CallOutcome`，字段同形 |

所以这不是分叉出一个"另一套 A2N"，而是同一套身份与语汇在**没有中心**时的形态，
日后接回平台不需要重新认识任何一个人。**单一来源纪律**在这里是硬要求：
指纹、卡哈希、验签、签名域，一处都不能复制第二份 —— 复制出来的那一刻，
同一把钥匙就会算出两个身份，同一张卡就会有两个哈希。

## 六、验证

```bash
python -m pytest tests/test_sovereign.py -q      # 34 项（单元 + 真进程集成）
python scripts/sovereign_demo.py                 # 8 步演示，全绿退出码 0
```

- **单元**（不碰库、不出网）：卡自证（改字段/改 did/换签名/缺一块/无入口）、
  双边互签（改字段/冒名/第三方代签/回执引用唯一性）、请求签名（载荷篡改/自称身份/
  重放/时钟越窗/应答绑定）、`use_home` 的库归属纪律。
- **集成**（真进程、真端口、两个库）：两个节点互相发现 → 取卡验卡 → 直连调用 →
  收据在**另一个进程**里验得过 → 供给方那边记到回执；以及"节点在干活之前先挡掉该挡的"
  （401 身份 / 403 能力 / 403 准入）。
