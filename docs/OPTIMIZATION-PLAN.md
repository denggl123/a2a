# A2N 整体优化方案

针对六条诉求（网络层发现 / 服务层调用 / 自动结算 / 硬指标评估 / 试用与案例 / 评分归一化），
加上本轮新增的两条约束（**前 10 次不按人计**、**增加"与模板偏差"这个质量维度**），
以及控制台"模块清晰、简单明了"的改版要求。

每条都先给**判据**，再给**设计**，最后给**验收**。判据不过的设计一律不做。

---

## 0. 一页看完：归成四个工作面

| 工作面 | 包含 | 现状 | 优先级 |
|---|---|---|---|
| **W1 证据面**（质量事实） | 模板偏差（硬）+ 归一化评分（软）+ 案例公开 + 计量真签名 | 测量有了、**评估系统不存在** | **P0** |
| **W2 经济面** | 试用 → 毕业 → 收费、自动结算、定时对账、统计口径隔离 | 结算"顺手结"、无定时对账、无试用概念 | **P0**（试用）/**P1**（结算） |
| **W3 信任面** | 发现的卡片自证闸、relay 收口、`mock-signature` 换真签名 | 三条都没收口 | **P0**（真签名）/**P2**（其余） |
| **W4 呈现面** | 控制台模块化 + Agent 详情"四段证据" | 三入口已成型，缺新模块的落点 | **P0** |

**为什么这么排**：第 4/5/6 三条诉求全部指向同一件事——**"使用端能不能真实评估质量"**。
这件事不做完，"免费换案例""归一化评分"都无处呈现，所以 W1 + W4 必须同批做。
真签名（W3）是 W1 的证据基础，必须一起做；否则计量上报是"mock"，硬指标就只是一句自报。

## 1. 五条统一判据（任何设计先过这一关）

1. **每个对外数字必须标"谁测的"**：平台探测 / 服务端自报 / 使用端实测 / 对手方凭证。不标口径的数字不许上界面。
2. **硬指标直接对外、不做归一化；软评分归一化后对外；两者分开呈现，绝不合成一个总分。**
   合成总分 = 把"平台探测 200ms"和"某人心情好给的 90 分"搅在一起，数字不可解释，也就不可验证。
3. **可复算**：任何一个对外数字，第三方拿同样的素材必须能算出同一个结果。算不出来的数字不许对外。
4. **一个事实一个写入方**（沿用既有纪律）。
5. **新增任何阈值，先想同源自刷**：能不能自己开小号把它刷满？能刷的阈值等于没有阈值。

## 2. W1 证据面

### 2.1 模板偏差（硬指标 · 主要衡量质量）

**是什么**：每个能力在上架时声明一份**验收模板**（这份活儿交付成什么样算合格），
交付物与模板比对得出的偏差，就是它的质量分。

**模板包含四样**（上架时声明、公开可见）：
1. **必需结构**：字段/段落/文件清单，缺一个记一次
2. **必需内容项**：例如"必须含原文与译文""必须给出引用出处"
3. **可量化参考**（有则填，没有就标"无参考"）
4. **容差**：允许多大偏差

**偏差分三个可复算的分量**：

```
d_结构 = 缺失或多余的项数 ÷ 模板项数
d_完整 = 应有内容项里没覆盖的比例
d_内容 = 有参考时的一致性距离（无参考时为 0，并明确标注"无参考"）

总偏差 D = w1·d_结构 + w2·d_完整 + w3·d_内容     ← 权重随模板版本化并公开
质量分  = 100 × (1 − D)
```

**三条铁律**：
1. **模板和权重上架时声明、公开可见、改了必须升版本**；历史案例用**当时的模板版本**重算（与既有"分账规则版本化"同一条纪律，两年后要能重放）。
2. **偏差必须可复算**：任何人拿模板 + 交付物都能算出同一个数 —— 否则它不叫硬指标。
3. **模板是"要求"，不是"答案"**：它只衡量"有没有满足你声明的要求"，不衡量"结果好不好"。
   **所以它和主观评分不能互相替代，更不能合成一个总分。**

**无模板的能力**：不产生偏差指标，界面显示"未声明验收模板"。**绝不允许伪造一个 0 偏差。**

**与现有实现的关系**：现有验收策略（`a2n_acceptance/service.py:16` 的 `BaselineSamplePolicy`）
已经返回 `score`，但只有两档（1.0 / 0.4）。模板偏差天然就是**同一个位置上的第二个策略**
（一个可替换的"判定规则"），把 `score` 升级为连续值即可，不改调用方。

### 2.2 归一化评分（软指标）

**公式**（用你给的三个数字反推出来的两段折线，μ=80 时 40→25 / 80→50 / 90→75 全对）：

```
μ_用 = 收缩后的评分者均值
f(x) = x · 50/μ_用                          (x ≤ μ_用)
f(x) = 50 + (x − μ_用) · 50/(100 − μ_用)     (x > μ_用)
```

**必须定死的六件事**：

| # | 规则 | 为什么 |
|---|---|---|
| 1 | 锚点 μ 是**这个评分者给所有供应商的平均**，不是"给这一家的平均" | 若是后者，这家永远被拉回 50，做多好都涨不上去 = 判无期徒刑 |
| 2 | 收缩：`μ_用 = (n·μ_原始 + k·50)/(n + k)`，建议 k=10 | 第一次评分时 μ 就等于那一次的分（输出恒为 50，零信息）；只评过一家时 μ 就是那一家的分。样本少时必须往 50 拉 |
| 3 | **两端斜率设上限**（建议夹在 [0.5, 3.0] 内） | 现在 μ=80 时上斜率 2.5 / 下斜率 0.625，**手松的人更能把人推高**（同样"超预期 10 分"：手松给 75、手紧只给 58），与直觉相反；μ=90 时上斜率是 5，几乎成了加分武器 |
| 4 | 边界保护：μ=0 会爆炸、μ=100 会除零 | 必须有截断 |
| 5 | 评分**必须绑定一次具体交付**（哪一单），不能凭空打分 | 这样每个评分都能点开看那次交付，也天然防刷 |
| 6 | **归一化分本身必须可复算**：随评分一起公布 `μ_用` 与样本数 n | 否则归一化就是平台说了算的黑盒 —— 直接违反最核心的承诺 |

**最小样本门（对应"前 20 次"）**，建议两个门都要，分工明确：

- **评分者的门**：他自己满 **20** 次评分之前，他的评分只进**本地校准池**，不对外发布；
- **供应商的门**：它满 **20 个去重评分者**之前，详情页**只给案例、不给分数**。

这两个门正好和第 5 条接上：**案例先行，分数后到。**
（还有一条必须做：对外分数要**同时给出"样本数"和"去重后的评分者数"** ——
"3 个人评的 88 分"和"300 个人评的 88 分"可信度完全不同，长得一样就是骗人。）

### 2.3 案例：试用期的"简历"

新 agent 没有历史，所以**用案例代替分数**。前 10 次免费期产生的原始材料公开挂在详情页：
谁调的、输入输出摘要、耗时、对方签收没有、模板偏差、以及打分（有的话）。

**三条规则**：
1. **脱敏与知情**：必须在调用**之前**明确告诉使用者——"这次免费，代价是这次交互会作为公开案例展示
   （内容可脱敏，你可以选择不上传）"。**不能一边发补贴一边悄悄披露用户数据。**
2. **同源不公开**：自己调自己的那些次，**照常计入 10 次免费额度**（尊重提供者，见 §3.1），
   **但不进公开案例、不进评分统计**。这两件事必须拆开——否则"10 次免费"要么被白嫖感知毁掉，
   要么被自开小号刷掉。
3. **案例是既有事实的投影，不是第二份真相**：材料来自已有的任务、计量、凭证链与流程时间线
   （已有只读端点 `GET /v1/console/calls/{id}` 就返回时间线），**不新增一份"案例表"**。

### 2.4 展示纪律：三段式，不给总分

Agent 详情页固定三段，**各自标口径与样本数，互不相加**：

```
① 客观表现   平台探测 rtt · 使用端实测耗时 · 完成/退回次数 · 计量对账差异
② 质量偏差   模板偏差率（结构 / 完整度 / 内容 分项）+ 模板版本 + 无参考标注
③ 使用评价   归一化评分 + 去重评分者数 + 当时的 μ（可复算）
④ 案例       试用期 10 条（打"试用"标）+ 最近 N 条，每条可点开
```

排序/筛选**可以用其中任一维度**，但不提供"综合分"。这一条看着反直觉，但它正是产品
区别于"评分网站"的地方：**我们不给结论，我们给证据。**

## 3. W2 经济面

### 3.1 试用与毕业：前 10 次免费 → 毕业 → 收费

**你的约束我接受**：额度**不按人计**，按次数计。
理由你也说清了——**提供者做满 10 次活儿却一分钱没有，还要被要求"来自不同人"，体感就是被白嫖**。
所以：**任何完成的调用都计数**，谁调的都算。

代价是"自己调自己"也能凑满 10 次。这个代价**不通过加限制来消除，而是通过把它移出公开证据来消除**（§2.3 第 2 条）。
这样提供者不觉得被白嫖，使用端也不会被自刷的案例骗到 —— **两边都不吃亏，靠的是"计数"和"证据"分开算，而不是靠为难某一方。**

**计数规则**：
- 只计**完成的调用**（失败、超时、被退回都不计）—— 不能让失败吃掉额度。
- 首装给 **10** 次；节点断线重连后**补 5** 次。
- **重连补额必须有界**（否则"重启即免费"就是无限免费）：
  同一 agent 身份**每自然日最多补 1 次**；**生命周期累计免费次数设上限**（建议 30，待定）。
  "补 5 次"的含义是**重连后额度重置为 5**，不是又给 10。

**毕业判据（四条全满足，"参数齐全、样本合理"就落在这四条上）**：

1. 免费额度用尽（累计完成 ≥ 10 次）
2. **上架参数齐全**：计价维度、单位价、SLA、验收策略/模板、结算方式 —— 缺一项不许毕业
3. **公开证据足够**：≥ 3 条**非自源**案例（带模板偏差或评分）—— 样本"合理"指的就是这个
4. 没有未了结的争议、没有未签收的交付

**毕业之后才允许收费。** 这条是铁律，它同时解决了另一个隐患：
**参数不全就不可能出现"标了价却算不出钱"的单**。

**状态**：`试用中（3/10 · 免费）` → `毕业（可收费）`。未毕业的 agent，界面上**不显示价格**，
只显示"试用中 · 免费"。毕业后价格才出现。

**摊主可选促销**（毕业后）："每位新使用者首单免费"——由摊主自愿开启、自己出钱，
**不是平台强制**（因为强制就等于把"被白嫖"又推回给摊主）。

**统计口径隔离（这条不做，数据立刻变假）**：免费单天然落在"非积分完成"状态，
会把行情页的成功率**抬高**（而 GMV 只计积分，不受影响），结果是
**"成功率虚高、GMV 不动"**。所以试用单必须打 `trial` 标，
从"付费成功率"与 GMV 口径里剔除，或者**分开两个数并列显示**。

### 3.2 自动结算

**现状（核实过）**：结算是在"提交那一次调用"里同步做的，且只在积分模式下；
系统**没有订阅"验收通过"事件**、**没有定时对账、没有任何后台任务**。
准确说法是"验收通过 → 同一事务里就结了"，**不是"自动结算"**。

**目标**：
1. **事件驱动**：验收通过即自动结算，不再依赖"有人发起那次调用"。
2. **两条记账路统一触发点**：积分与直付/对等账户各有各的路径，必须由**同一个触发点**收口。
3. **幂等**：以任务号作幂等键 —— 重复事件不许二次结算（这是最容易出的事故）。
4. **定时对账**：每日日切对一次账（积分总量 vs 托管余额），差异写进运维页并报警。
5. **失败可见**：结算失败必须进"待处理"队列并显式呈现，**绝不静默**。

**保留既有优点**：钱、记账、终态必须在同一个事务里（现在就是这么做的，别改坏）。

**定稿（已实现，代码为准）**：五条各落到一个具体位置，改其中任何一条都要同时改文档、改代码、改测试。

| # | 落实在哪 | 关键取舍 |
|---|---|---|
| 1–2 | `a2n-gateway.call.invoke` 与 `a2n-task.service.submit` 都调 `a2n_settlement.closing.record` | **同一个触发点**：两条记账路不再各写各的账；谁结的、为什么没结，只有一处事实可查 |
| 3 | `closing.record`（`task_id` 是 `settlements` 的主键） | 重复事件 `already=True` 原样返回 —— **不二次计数、不许事后改金额** |
| 4 | `closing.daily_cut` + `app._start_closing_loop`（`A2N_CLOSING_INTERVAL_SEC`，**默认 0 = 关**） | 日切默认**不自动开**：没配就别偷偷跑；`reconciliations` 按天 `UNIQUE`，同日重跑是**覆盖**不是追加 |
| 5 | `closing.mark_pending` + `GET /v1/ops/settlement/pending` | 失败落一条 PENDING 事实（**绝不静默**）；已结的单**不许被降级**成待处理（那会凭空多出一笔差额） |

一个**例外**要写明白：裸中继（relay）的成交**不进**这张表 —— 它没有 `task_id`，也就没有幂等键，
强编一个键只会造出无法追溯的账。relay 的账仍走 deals 自己那条线。

金额口径：`amount_minor` 用整数最小单位、币种跟着钱走；汇总**绝不跨币种相加**，
所以头条三个数字是**笔数**（无币种），金额按币种分行（`closing.by_currency`）。

### 3.3 需要新增的事实（概念级，不含实现）

验收模板与版本 · 模板偏差记录 · 评分记录（绑定任务号）· 评分者的校准统计（均值与样本数）·
试用额度与毕业状态 · 计量上报的签名。

## 4. W3 信任面

### 4.1 发现的"卡片自证闸"（P2）

**现状**：有两条互不同源的路 —— 对等发现（按能力多跳查询）和平台目录查询。
**平台那条路发现完直接派单，没有"取对方的卡 → 验卡 → 核对哈希"这一步**；
自持模式里有这道闸。等于平台路是"按自报信任"。

**改法**：把自持模式那四步搬进平台路，**验不过的卡不许出现在"可直接调用"里**。
发现和可用必须是同一件事——"在你列表里"就等于"验过了"。

**定稿（已实现，代码为准）**：闸门收在**服务端**，结论只由服务端给出（前端不自己猜）：
`a2n_p2p.attest.verify_selfproof`（签名域 = 整张卡去掉 `sig`）+ `a2n_registry.service.card_verdict`，
三态必须诚实：`signed`（验过）/ `unattested`（没自证 —— 不隐藏，但也**不冒充验过**）/ `invalid`+`tampered`（拒收）。
`register/update_card` 由 `_guard_selfproof` 拦"自称有身份却验不过"的卡，且**自签卡必须自带 uid**
（平台不补 uid —— 补了就等于替节点改了签名域，签名当场失效）。
发现路 `a2n_dispatch.query` 与 `assignable` 一律跳过被拒收的卡；"可直接调用"必须**同时**满足"能付费"与"已自证"。

### 4.2 relay 收口（P2）

**现状**：另有一条中继入口绕开治理链（不过门禁、只对等账户记账）。
**改法二选一**：① 收进治理链；② 明确为"只给对等账户用的底层原语"，**对使用端不可见**。
建议 ②，并在界面上彻底消失。

**定稿（已实现，代码为准）**：取 ②。`/v1/relay` 不在使用端界面上出现 —— 控制台只调 `POST /v1/invoke`
（`tests/test_relay_closure.py` 扫文档断言，防止"悄悄长出第二个调用入口"）；403 的文案直接把人指回 `/v1/invoke`。
SDK 侧 `call_agent` 走治理链，`relay()` 仍是裸中继原语。

### 4.3 计量真签名（P0）

**现状是硬伤**：计量上报的签名字段是写死的假值（`mock-signature`）。
所以现在"可验证"的真实含义只是**平台自观测 vs 节点自报的比对**，不是可复算的证据。

**改法**：节点用自己的钥匙签"计量内容 + 任务号"，验签不通过的计量进"争议"而不是"已对账"。
**并且验签结果要和明细一起展示** —— 只给结论不给过程的"可信"是假的。

**定稿（已实现，代码为准）**：唯一口径源是 `a2n_p2p.attest.sign_metering`（签 `task_id + node_id + dims`）。
**算法写完不等于有人在链路上签** —— 节点唯一的机会在**转发边界**：`hub.forward` 把 `task_id` 与
**入账那份同一个** `dims` 一起下发，`TunnelClient._handle_forward` 本机执行完**就地连署**随回包上行；
推送交付则由 `Node._handle` 签它即将上报的那份 usage。
归属靠卡上公钥：**卡没声明 `x-a2n.sovereign.pub` 一律拒收**（否则任何一把钥匙都能替该节点背书）。
SDK 保持零依赖：签名格式不进 SDK，调用方注入 `attest_fn(task_id, node_id, dims)`。
控制台徽标读 `objective.metering_attested`，显为 `已签 N/M` / `未签名`。

## 5. W4 控制台改版：模块清晰、简单明了

### 5.1 六条原则

1. **主入口保持 3 个不变**（上手难度取决于入口个数，不取决于功能多少）。所有新能力加进**已有入口内的小页**，不新增主入口。
2. **运维类全部收进一个默认折叠的"运维"区**：全网总览、调用测试、账本与凭证、争议仲裁、批次共识、AP2 凭证、**结算与对账（新增）**。
3. **每个小页只回答一个问题**，页面标题就是那个问题。
4. **复杂度下沉**：列表给结论，明细进抽屉/详情页。列表行永远不长。
5. **每个数字必须带口径与样本数**（"使用端实测 · 12 次 · 中位 820ms"）。
6. **取数失败不许翻成空态**：加载失败就说"加载失败，点刷新重试"，**绝不能说成"你还没有…"**。

### 5.2 页面地图

| 主入口 | 小页 | 这一页只回答一个问题 | 本次改动 |
|---|---|---|---|
| **找 Agent** | 发现 Agent | 有什么能用、能不能直接调 | + 试用徽标、+ 证据入口（点进详情） |
| | 待使用 | 我收藏/自建的候选 | 不变 |
| | 调用记录 | 我调过什么、结没结 | + 结算状态列（已结/待结/失败） |
| **卖 Agent** | 自售列表 | 我卖得怎么样 | **+ 试用进度（3/10）、+ 毕业阻塞原因** |
| | 他人调用记录 | 谁调了我的、签收了没 | + 签收状态、+ 明细里的模板偏差 |
| | 行情信息 | 我该定什么价 | + 口径标签、+ 试用单与付费单分开 |
| **我的账户** | 账户信息 | 我的钱和支付方式 | 不变 |
| | 流水列表 | 每一笔哪来的 | + 试用/付费标记 |
| **运维**（默认收起） | 全网总览 / 调用测试 / 账本与凭证 / 争议仲裁 / 批次共识 / AP2 凭证 / **结算与对账** | 各自一件事 | **+ 结算与对账** |

### 5.3 本次改版的核心：Agent 详情页 = 四段证据

**这是整套改版的落点。** 详情页自上而下四段，顺序固定，来源分开：

```
┌ 头部：名字 · 能力 · 状态徽标（试用中 3/10 · 免费  或  毕业 · ￥0.05/次）
├ ① 客观表现   rtt（平台探测 11 次）· 实测耗时（使用端 7 次）· 完成/退回 · 对账差异
├ ② 质量偏差   模板 12% · 结构 0 / 完整 8% / 内容 4% · 模板 v2 · 参考：无
├ ③ 使用评价   72 分 · 来自 9 位使用者 · μ=66（点击可复算）
└ ④ 案例       试用期 10 条（标注"试用"）· 最近 10 条 —— 每条可点开看交付与签收
```

**样本不足时给原因，不给空白**：例如"还差 11 位使用者的评价才能对外显示分数"。
空白会被读成"这家很差"，必须写清是"还不够"，不是"不好"。

**三段之间用一条竖线或分组框隔开，不做加总。** 界面本身就在说"这三件事不是一回事"。

### 5.4 三个新增界面元素（都很小，但缺了整套逻辑就看不见）

1. **试用进度**：`试用中 3/10 · 免费` 的徽标 + 一行进度条（自售列表行内可见）。
2. **毕业阻塞原因**：毕业按钮点不动时，必须写清"还差什么"（缺计价维度？缺 2 条非自源案例？有未签收？）。
   这一条直接把 §3.1 的四条判据变成可操作的清单。
3. **结算与对账页**：三个数（今日应结 / 已结 / 待处理）+ 一份差异明细。差异必须能点开看是哪一单。

## 6. 分期与验收

| 期 | 内容 | 什么算做完 |
|---|---|---|
| **P0** | 计量真签名；模板偏差；归一化评分 + 最小样本门；试用与毕业 + `trial` 口径隔离；控制台详情页四段证据 + 试用徽标 | 一个新 agent 经历"10 次试用 → 毕业 → 收费"全程，详情页能看出这 10 次的模板偏差与（样本够时的）归一化评分；免费单不污染付费成功率 |
| **P1** | 结算事件驱动 + 幂等 + 待处理可见；定时对账 + 差异报警；控制台"结算与对账"页 | 验收通过后不需要任何人再操作就结完；人为制造一次结算失败，能在页面上看见并追溯 |
| **P2** | 发现的卡片自证闸；relay 收口；运维区重组 | 平台路发现到的每一张卡都验过签；使用端界面上再也没有第二条调用入口 |

**P0 的验收必须带一个反例**：自己调自己 10 次 → 能毕业（因为不按人计），
**但这 10 条不进公开案例、不进评分统计**。这个反例过了，§2.3 和 §3.1 的取舍才算立住。

**进度：P0 / P1 / P2 三期均已落地。** 对应关系 —— P0 见 §2 与 §4.3；P1 见 §3.2 与 §5.4.3；P2 见 §4.1/§4.2。
每期都另有**护栏测试**（`tests/test_settlement_closing.py`、`test_card_gate.py`、`test_relay_closure.py`、
`test_quality.py`、`test_metering_wiring.py`）与**活库核验**（`scripts/check_evidence_live.py`）盯着 ——
"看起来做了"不算数，要能在清库冷启后的活库上一步一步验出来。

## 7. 风险与不做的事

- **不做综合总分**。哪怕它看起来更好卖，它会把可验证变成不可验证。
- **不做"平台认证 / 优选 / 金牌"**。一旦有认证徽标，就有一个可以卖的位子。
- **不做"为了凑样本而放水"**：样本不够就显示"还不够"，不许用自源数据凑。
- **不做"免费期偷偷降质"**：试用期与付费期的验收标准必须完全一样，否则毕业后的评分会断崖。
- **最大的风险是"评分被工具化"**：供应商之间互刷、或联合刷分母。
  防线只有三条：**绑定具体交付**、**去重且公开样本数**、**同源不计入**。
  三条之外再加权重调整都是徒劳——这三条不做，后面都是假的。

## 8. 已拍板的 5 条（定稿，代码为准）

原先列在"待你拍板"，现全部按建议值定稿。**数值的权威位置是代码常量**，这里只记结论与理由。

| # | 结论 | 为什么是这个值 | 代码 |
|---|---|---|---|
| 1 | 首装 10 次；重连把额度**重置为** 5（不是又给 10）；每自然日最多补 1 次；**生命周期累计授予上限 30** | 不给上限 = "重启即免费"，等于无限免费；给上限又不按人计，提供者的体感才不被白嫖 | `a2n_registry.trial`：`INITIAL_CAP=10 / RECONNECT_CAP=5 / TOTAL_GRANT_CAP=30 / REGRANT_MIN_HOURS=24` |
| 2 | 毕业需**非自源案例 ≥ 3 条** | 0 条 = 只有自说自话；1~2 条 = 一条差评就能定性。3 条是"看得出稳定性"的最小值，且刻意保持低门槛（新节点不该被证据门槛卡死） | `a2n_reputation.ratings.MIN_NON_SELF_CASES = 3` |
| 3 | 归一化两端斜率**夹在 [0.5, 3]**；收缩系数 **k=10**；锚点 μ→50 不动 | 不做 z-score：z-score 会丢掉 0→0 / 100→100 两个不动点，也不再有"50 = 他眼里的中性"这个可解释锚。夹取只压 μ 极端时的放大（μ=5 时 50/μ=10，一次低分就能把一家打到地板） | `a2n_reputation.ratings.normalize_score` + `SLOPE_MIN/SLOPE_MAX`、`K_SHRINK=10` |
| 4 | **两个门都要**：评分者自己满 20 次评分才发布他的评分；供应商满 20 位**去重**评分者才对外给分 | 合成一个门就丢了一半语义：前者治"一个人刚来就打的分不可信"，后者治"3 个人刷 100 条不可信"。两个门治的是两种不同的病 | `a2n_reputation.ratings.PUBLISH_MIN_RATER / PUBLISH_MIN_RATERS = 20` |
| 5 | 模板权重默认 **结构:完整度:内容 = 3:4:3**；**无参考时内容权重归零、另两段重归一化** | 完整度最高（4）："该给的没给"是质量事故；结构次之（3）：形状错但内容在仍可用；内容需要参考物才测得了，没参考就**不测**（不是记 0 偏差）；权重随模板版本存档，历史案例可重放 | `a2n_acceptance.template.DEFAULT_WEIGHTS`、`deviation()` 的 `no_reference` 分支 |

**定稿的纪律**：这五个数都写进了代码常量并各有一条护栏测试（边界值 + 反向）。
改其中任何一个，都必须同时改这里、改代码、改测试 —— 口径三处不一致就等于没定。
