# 对等账户自动匹配与结算

## 1. 参与者与配置

没有中心平台代收账户，平台手续费为零。供应方声明可接受的结算方式；使用方在自己的节点配置方式、优先顺序和额度。共同的方式才可能成为本次交易条件。供应方积分账户是节点 DID；链上账户由双方自己的钱包与通道配置确定。

控制台「我的账户 → 结算方式与顺序」可以添加、移除、上下移动方式。积分、x402、直接转账通过同一个支付协调入口进入各自子模块。创建新的结算规则不会迁移或重定价既有交易。

配置项：

| 项 | 含义 |
|---|---|
| `provider_methods` | 供应方支持列表；Agent 自身积分模式、实际钱包和通道仍须可用 |
| `buyer_preferences` | 使用方付款规则，数组从前到后优先 |
| `automatic` | 是否授权自动执行已取得报价的调用；默认关闭 |
| `expected_revision` | 更新需匹配当前版本，避免覆盖同时发生的配置 |

`null` 沿用现有通道并保留逐笔选择；`[]` 明确不支持任何收费方式。免费服务和前十次样品仍可执行。自动结算必须提供非空、明确有金额上限的使用方规则，积分还需明确 EARN、DEBT 或 PAY。

## 2. 匹配规则

1. 业务层先固定本次请求及是否免费。前十次免费技术交付一定形成脱敏公开样品；此阶段不创建支付计划、积分发行或积分债务。
2. 供应方基于服务定价、支持列表及实际通道给出签名报价。使用方能力与供应方能力取交集。
3. 按使用方规则的顺序遍历报价。`method` 必填；已填写的 `network / asset / currency / flow / mode` 必须精确匹配。未填写的字段允许匹配该方式实际可用的值。不把不同链、代币或币种视为相同，也不自动兑换法币或链上资产。
4. 检查本规则单笔金额上限。超出则检查后续规则；满足的第一个选项成为推荐。查询匹配本身不付款、不执行 Agent。
5. 自动调用保存首次选定的选项、命令标识与合同；接受原报价后，执行对应子模块。链上风控另行检查单笔、每日、累计未定及同一对方的额度。积分子模块检查余额、债务许可、兑换关系、路径及各方预留。

规则金额是最小单位的非负整数，以十进制字符串提交，避免浏览器整数精度丢失。`max_amount_minor` 限制报价金额；原生转账 `fee_cap_minor` 另限网络费，风控总支出包含这项费用。积分 PAY 可固定 `funding_issuer` 和 `max_cost`；未设置 max_cost 时按本次报价数额作为消耗上限，跨发行人兑换不会无限支出。

示例：先接受供应方增加自己积分的 EARN 服务，再尝试指定网络的 USDC：

```json
{
  "expected_revision": 0,
  "provider_methods": [{"method":"a2n-points/1","mode":"EARN"}],
  "buyer_preferences": [
    {"method":"a2n-points/1","mode":"EARN","max_amount_minor":"100"},
    {"method":"x402/2","network":"eip155:8453","currency":"USDC","max_amount_minor":"1000000"}
  ],
  "automatic": true
}
```

## 3. 自动验收和付款时序

必须区分三种验收：发布自动验收验证项目版本和产品；任务声明模板检测约定结构或规则；质量评审检测实际任务的质量。这三者不能互相替代。未声明模板的调用只说明收到交付，`quality_measured=false`，不宣称质量合格。

| 方式 | 当前时序 |
|---|---|
| 样品及其他免费条件 | 执行、技术交付、适用的验收、记录体验；结算跳过 |
| 原生转账 | 原报价接受 → 付款确认 → Agent 调用与验收 |
| x402 exact | 接受合同 → 固定授权 → 执行与交付事实 → 对应授权结算/核对 |
| 积分 | 接受合同与各方预留 → 执行 → 供应方签名交付 → 决定与各方应用 → 恢复一致 |

现有自动结算依据约定的技术交付及付款协议；人工评价或语义质量未通过不会自动撤销已发生的付款。质量争议独立记录，退款仍需双方接受方案。积分 EARN/DEBT 是供应方按真实服务增加自己的积分；PAY 使用持有积分兑换；三方兑换由可恢复协议推进一致，网络中断不代表同时物理提交。

## 4. 中断、失败与授权变更

- 相同 `command_id + offer_id` 返回或恢复同一计划；改变参数复用命令会被拒绝。
- 已选计划准备失败保留原命令。未知付款、授权、交付或积分提交只核对原计划，不能切换到下一种方式制造第二笔支付或再次执行 Agent。
- 没有共同方式、额度不足、钱包缺失或积分路径不可用，会明确停止。不会在已选计划失败后悄悄尝试另一种方式；所有后续变更需明确处理原单。
- 关闭自动结算或收紧使用方支持和额度，阻止尚未开始的自动付款/积分调用。已经产生外部影响的原单仍可恢复；冻结的账户和通道用于原单核对。
- `NodeClient.call/call_agent` 默认读取本机授权；开启自动结算后，已导入的签名节点 Agent 自动报价、固定选择并执行。默认关闭时沿用原来的逐笔方式。本机挂载、未签名外部 Agent 与带既有支付计划的原单继续经过唯一调用链。
- 使用稳定的 `task_id`。SDK 重试先读持久化调用记录，复用原报价与原计划；修改输入复用同一任务标识会被拒绝。收到 UNKNOWN 后可用 `get_task` 查原单，不必再次发起购买。
- 后台每轮只恢复一个已授权的未完成订单，记录退避时间与诊断；节点重启后继续恢复。没有报价的历史免费记录不能被猜测执行。后台不发现或购买新 Agent。

## 5. 边界与接口

SDK `SettlementPolicy` 只维护本机规则及纯匹配；`PaymentCoordinator` 维护双签合同及统一订单；Node `AutomaticTrade` 编排已授权的一次调用；原生币、x402、积分模块负责自己的账户、协议和结算。发现和评分不执行付款。

本机接口（受现有管理授权保护）：

- `GET /v1/payment-coordination`：规则、订单、已配置的通道状态。
- `POST /v1/payment-coordination/policy`：完整规则更新。
- `POST /v1/trades/quote`：取得一次固定输入的报价。
- `POST /v1/trades/match {offer_id}`：纯匹配与排除原因。
- `POST /v1/trades/auto-execute {offer_id, command_id}`：固定选择、执行或恢复。
- `POST /v1/trades/call {scope, request, automatic}`：SDK 的普通调用入口，返回规范 CallOutcome；automatic 可省略，或明确关闭本次自动报价。既有自动单仍按原单恢复。
- `GET /v1/trades/call?scope=...&task_id=...`：查询原自动调用；不存在时返回 null，SDK 再查询原 A2A 任务。
- `GET /v1/trades/automatic`：最近一百个任务的状态、原计划标识、退避与诊断，不返回调用输入或钱包凭据。
- `GET /v1/trades/automatic?command_id=...`：读取该原单的状态与已记录交付；控制台通过只读轮询展示后台恢复，不重新执行。

单一现有接口仍支持逐笔确认。多钱包并行选路、所有支付协议互通、托管裁决，以及主网资金安全审计不属于本次已验证范围。
