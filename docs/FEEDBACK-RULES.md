# A2N 双方反馈规则（R2）

版本：v0.1 · 2026-09-30 建立。性质：供开发与验收使用的规则设计稿，**尚不代表实现完成**。对应 [DEVELOPMENT-ROADMAP.md](DEVELOPMENT-ROADMAP.md) 的 R2 批次；接口契约见 [FEEDBACK-API.md](FEEDBACK-API.md)（消息版本名 **a2n-feedback/1**）。业务底座遵循 [VISION.md](VISION.md)：公益、零交易抽成、重信誉轻证据、前 10 次免费调用默认形成样品。

## 1. 目标与边界

R2 的目标：**一笔真实任务之后，买卖双方都能留下与其角色和任务状态对应的、签名的、不可伪造的反馈。**

R2 明确不做的事（防止把 R2 做成 R3）：

| 不做 | 归属 |
|---|---|
| 算信誉分、混成人格总分 | R3 |
| 用反馈改变排序、调用量、接单机会 | R3 |
| 自动惩罚（低分→限流/封禁） | R3，且"单个差评不直接形成全网封禁" |
| 跨节点按需拉取反馈摘要、全网同步 | R3 |
| 付款行为维度 | R4 启用付费后加入 |
| 裁定争议、自动退款 | 本机「这单我不认」（`a2n_sdk/disputes.py`）是另一条线，两表不共用 |

## 2. 身份口径（已拍板，2026-09-30）

**买方与卖方都用节点身份：一个 did = 一个节点。** 反馈作者就是本机节点的 `did:a2n:ag_*`，用现有 ed25519 身份（`a2n_p2p.identity.Identity`）签名，公钥指纹即 did。**不引入账户层身份，不引入多身份 / principal header** —— 与"跨节点发现是 SDK 层职责，与用户身份无关"的既有口径一致。

由这个口径推出两条必须如实呈现的边界：

- 不同 DID 只代表不同身份标识，**不证明背后是独立个人**；界面展示交易对手数量时必须带这个口径说明（与路线图 R2 节一致）。
- 一台电脑一个身份：同一个人换一台节点就是另一个 did。R2 照实记录 did 并签名；防串谋属于 R3 的影响限制，不是 R2 的身份验证问题。

## 3. 双向反馈与状态对应

一次真实任务（`task_id` 贯穿 tasks/a2a_tasks/deals/pay_charges 四表）可以产生两份各自独立的反馈：

| 方向 | 首版维度 | 状态对应硬闸 |
|---|---|---|
| 买方 → 供给方 | 交付质量 `quality`、按时 `punctual`、沟通 `communication` | **`quality` 只允许对已交付（`COMPLETED`/`ACCEPTED`/`SETTLED`）的任务打分**；失败/取消单只能评可达性与体验 |
| 供给方 → 买方 | 需求按约 `on_spec`、沟通配合 `cooperative` | 全部实际任务状态都可留；正常取消、缺少评价不算不诚信 |

规则：

1. **每方向只有一份当前有效反馈**。同任务同方向同作者重复 `open` 必须拒绝（走"修改"），修改保留版本不抹旧版 —— 不靠反复提交放大影响。
2. **分数**：每维 1–5 整数；`note` 可选一句原因，走与样品相同的脱敏（邮箱/手机号/密钥/私钥）。维度可留空，留空不算差评也不算好评。
3. **没有调用关系不能凭空评价**：只能对本节点真实存在、且与该 `task_id` 关联的任务开评 —— 与 disputes 同一纪律（只能对真有的那一笔开单）。
4. **失败单照实**：网络失败如实记录为失败，"网络失败被误当作品质量差"是 R3 验收反例；R2 的硬闸先保证 `quality` 根本打不出去。
5. **低分与合理拒收不自动成为恶意行为**：R2 没有任何信誉扣减逻辑；反馈与争议、与结算互不影响账本数字。

## 4. 防报复性差评与未评价口径

- 默认形态：**双方提交后公开**；评价期延迟公开（到期再公开）作为可配置项，评价期长度在小规模试点中定稿，v0.1 建议值 7 天，**不是承诺值**。
- 不评价保持「未评价」：不算好评，也不阻塞调用、试用完成或结账。反馈永远不是交易的前置条件。
- 对外文案不许承诺"永久"：反馈条目只说"留存、可修改留版本"，不说"永久公开"。

## 5. 签名与采信

- 反馈对象由作者节点身份自动签名（`proof = {pub, sig}`，ed25519，无填充 URL-safe Base64，与协调层同口径）；**对方不能伪造或改写评价** —— 收到的一份必须验签后才算"有来源"。
- 验签失败的反馈**原样留痕但不采信**，界面如实标「验签未过」，不静默丢弃也不混入有效统计。
- 自源反馈（`author_did == provider_did` 的买方评价，或作者评自己节点）照实存并标 `self_source`，R3 不计独立信誉 —— R2 先把标记打上。
- 未认证第三方调用（拿不出节点签名的反馈）只能展示为「未认证体验记录」，不进有来源统计（R3 消费时的口径，R2 先把来源字段存对）。

## 6. 存储与本地权威

- 落 `a2n_sdk` 的本地反馈服务（`FeedbackBook`），跑在节点 `LocalStore` 上，与 `TrialBook`/`DisputeBook` 同层：**本节点自己写的反馈是本地权威**；收到的对方反馈是「原样留存的签名对象」，不合并、不代签。
- 版本链：`revision` 递增 + `prev_hash` 链接，修改可追溯；删不掉（履历不是宣传稿）。
- 计数与版本必须走 `store.tx()` 原子写（R0 补强教训：并发完成不能丢更新）。
- 任务关联字段：`task_id`、`provider_did`、`service_id`、任务状态快照、来源（`self`/`counterparty`/`third_party_unverified`）。

## 7. 控制台落点

- 调用记录行加「写反馈 / 改反馈」；未评价的如实显示「未评价」。
- 反馈列表面板：作者、方向、维度分、原因、版本号、验签状态、来源标记；交易对手数带第 2 节口径说明。
- 前端取数失败不翻空态；没有反馈就给诚实空态，不装作有评价。

## 9. 验收规则（R2 全量，逐条可测）

1. 同一任务双方各留一份有效反馈，互不覆盖。
2. 重复提交幂等：同 `Idempotency-Key` 重放返回原结果；同方向二次 `open` 被拒并指明走"修改"。
3. 修改保留版本：`revision` 链完整，旧版可查不可改。
4. 未交付不能评成品质量：服务端 400，文案说明原因。
5. 低分、合理拒收、正常取消：不触发任何自动惩罚，也不影响结算。
6. 无调用关系不能评：任务不存在或不属于本节点 → 拒绝。
7. 伪造反馈验签不过：留痕但不采信，不进有效统计。
8. 未评价不阻塞：调用、试用完成、结账全程可走通。
9. 反馈不影响账本：四表数字与无反馈时完全一致。
10. 措辞纪律：界面不出现"永久"，不出现"赚"，未评价明确显示"未评价"。
