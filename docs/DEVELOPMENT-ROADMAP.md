**要交付的产品体验**

卖方挂上自己的 Agent，写清能做什么、需要什么输入、会交付什么。最初 10 次免费服务自动积累真实样品，买方看描述和样品后尝试使用，双方反馈逐步影响后续选择和接单。好服务和诚信用户能持续获得交易机会；偶发不满意和有限坏账有可承受的处理方式。

A2N 的交易抽成为零，公共设施不出售排名和曝光。轻证据体现为自动保留必要调用事实、少打扰用户；不等于放任重复扣款、伪造成功、篡改历史或泄露用户输入。允许单笔吃亏是双方承担有限交易风险，不能成为实现错误的理由。

本轮交付对象是 `a2n-node.Daemon` 驱动的产品节点。旧 `a2n-server` 中已有的模块作为复用参考，其测试通过不能直接代表产品节点已经具备这些能力。

**开发顺序与完成标准**

| 批次 | 对用户交付什么 | 依赖 | 通过标准 |
|---|---|---|---|
| R0 调用与生命周期 | 能找到当前供给，点开后真正拿到结果 | 当前代码 | 五个正常容器案例均交付成功；故意失败案例返回真实原因；重复重启不增卡、不换商品身份 |
| R1 描述与前 10 次样品 | 能看描述、看交付样品、免费试用，进度真实 | R0 | 全新 Agent 从 0/10 到 10/10；样品自动出现且可看；重启与重试不重复计数；差样品不被好样品替换 |
| R2 双方反馈 | 买方评实际服务，卖方评合作体验；双方可解释和更正 | R1 | 同一任务双方各一份有效反馈；重复提交幂等；未交付不能评成品质量；低分与合理拒收不自动成为恶意行为 |
| R3 信誉影响交易 | 买方更容易选到适合的服务，卖方可控制接单风险 | R2 有真实数据 | 算分可解释；自调和重复互刷影响受限；新人有机会；持续差表现降低后续选择概率 |
| R4 小额付费 | 试用后可按明示价格交易，双方知道是否已付款 | R1、R2；可与 R3 并行 | 一种币种、一条实际渠道完成付费；重试不重扣、失败不假收款；A2N 份额为零 |
| R5 独立用户试用 | 实际买卖双方持续使用，参数由真实表现修正 | R0–R4 | 多个独立节点与真实工作流连续运行；比较选择、复用、反馈覆盖和误伤情况 |

第一个可交付版本止于 R2：调用、描述、前 10 次样品、双方反馈组成可试用的免费市场。第二个版本接入 R3/R4，观察信誉是否改善交易选择。每批完成后以实际行为验收，再继续下一批。

**R0：先修当前阻断，不扩大功能面**

1. 给供给挂载传入真实协议类型。greenlight 使用普通 JSON 适配器；标准 A2A 上游继续使用 A2A 适配器。验证 skill、payload、错误、长任务和结果在边界上被正确翻译。
2. 商品标识独立于上游地址与临时端口。演示供给按节点身份与逻辑商品标识稳定保存；卡片修改保留版本。更换地址更新挂载，不重置试用、样品和信誉。
3. 对当前演示卷中的重复旧供给设计一次性迁移：先备份、识别同一商品的新旧挂载、停止旧卡发布，保留已有调用记录及来源。仅处理能确认归属的演示条目，不按同名删除用户供给。
4. 已导入旧卡的买方能刷新地址或得到明确的已更新提示。不能只修卖方目录，留下买方收藏永久失败。
5. 将宿主机与容器调用、两台不同网络电脑调用分别验收。跨网络先使用实际可达的 HTTP(S) 路径或现有自愿中继；原生 P2P 穿透效果单独记录。

验收应运行真实的“目录发现 → 本机导入 → 调用 → 查看结果”链路。五个正常案例各调用一次，失效案例验证失败，再至少三次重启核对身份、卡数和调用。主机与容器成功不能被写成公网双机通过；离线后恢复不得自动重放已经发出的任务。

主要落点：`docker/node_entry.py`、`a2n_node/supply.py`、`a2n_sdk/runtime.py`、`a2n_sdk/upstream.py`、`a2n_sdk/management.py`。补协议组合和带持久化的重启回归，不能只测试 greenlight handler 能返回字典。

**R1：把前 10 次服务变成 Agent 的真实履历**

商品详情首先展示：能做什么、输入示例、交付示例、前 10 次样品、试用进度与价格；随后再展示反馈与信誉。签名、凭据、网络诊断放在需要查看时展开的位置。

首期样品至少包含需求摘要、实际交付内容或预览、调用时间、Agent 版本、耗时及是否免费。文字、结构化结果优先支持；文件提供安全的预览和下载，后续扩展图片、音视频。大文件按需加载并限制公开存储占用。

样品从真实调用结果生成，不以买家先评分、卖家手工上传或申请审核为前置。卖方补充的宣传示例与免费试用样品有明确标识。初始样品固定关联具体调用和版本，卖方不能用删除后补一个好样品的办法筛掉不理想交付。修改 Agent 后展示版本差异，不把旧样品冒充新版本表现。

首次免费调用前明确告知其交付默认形成公开样品；这条规则是试用模式的固定说明，不能在用户调用后才出现。公开预览使用允许公开的内容投影，移除密钥、身份信息和业务隐私。不能安全公开的内容保留样品位置并显示隐藏原因，不能以隐私处理为由让卖方挑好评。历史未告知的私有调用不直接改成公开样品；不要求用户每笔上传证明或填写复杂授权单。

试用计数与展示遵循：

- 首次仍是前 10 次完成调用免费，不改成自愿促销，也不改成每个买家 10 次。
- 技术失败、没有交付的超时和取消不占完成名额，但保留在失败统计中。
- 交付已完成但买家觉得不好，应保留样品和反馈；不能仅因低分而删除这次完成并要求卖方继续无限免费。如何对应当前 `ACCEPTED/REJECTED` 状态，实施时需明确区分技术交付与主观评价。
- 同一任务重试、轮询和重复完成回调只计一次。并发占用试用名额时，在接单时固定本次是否免费；不能结果回来后才把它变成收费单。
- 按“多一次影响不大”的原则，建议允许试用结束时已接下的少量并发免费单继续免费，由卖方的并发上限限制额外消耗；首批样品固定前 10 次完成，额外完成另列。首期无需为严格卡死第 10 个名额引入复杂预约和回收机制，也不能无限接免费单。
- 试用计数和样品身份重启后连续，更换端口、修改描述不重新开始。
- 重连免费采样沿用现有 5 次、补额频率与累计授予上限，和初始样品分开，不悄悄重置成新 Agent。
- 第 10 次后显示真实试用结束状态；若卖方选择继续免费就明示，若付费通道尚未具备就显示未启用付费，不能自动扣钱或永久冒称仍在首轮试用。

自源调用依现有规则计入完成次数，不计独立信誉。旧文档不公开自源案例；是否在新样品页保留一个标有“卖方自测”的展示位置，属于待定的展示细则，不能直接把自源称为独立买家样品。样品不足时说明原因，不编造 10 个独立评价者。

主要落点：产品节点本地存储与调用完成路径、供给投影和管理接口、`web/runtime.html`。已有 `calls` 保存私有原始输入输出，样品保存公开选择、预览和版本引用，避免复制一套不再跟随原始交付的“成功记录”。

**R2：先有可信的双方反馈，再有复杂分数**

> 可执行规则与接口契约：[FEEDBACK-RULES.md](FEEDBACK-RULES.md) v0.1 + [FEEDBACK-API.md](FEEDBACK-API.md)（a2n-feedback/1），2026-09-30 建立，**设计稿未实现**。身份口径已拍板：买卖双方都用节点 did，一个 did = 一个节点。

| 方向 | 优先询问 | 避免的误判 |
|---|---|---|
| 买方 → Agent | 结果是否符合描述、是否有用、交付是否及时；可选一句原因 | 技术成功不自动生成好评；没有结果不能评价内容质量 |
| 卖方 → 买方 | 需求是否按约、沟通配合、是否重复恶意消耗；付费启用后再加入付款行为 | 给低分、提出合理异议、正常取消或缺少评价不等于不诚信 |

一次交易每个方向只有一份当前有效反馈，修改保留版本，不靠反复提交放大影响。完成、失败、取消等实际任务都可留下与其状态对应的反馈：失败单可评价可达性或服务体验，无法评价未产生的成品质量。没有任何调用关系的人不能凭空评价。

双方反馈默认独立填写。建议采用双方提交后公开，或到约定评价期结束再公开，减轻报复性差评；评价期长度在小规模试用中定稿。不评价保持“未评价”，不当作好评，也不阻塞调用、试用完成或结账。

首版先记录少量维度、原因、时间、任务关联和来源。收到、按约认可、付款状态仍分别保存，但正常使用不要求买卖双方逐步手工签署复杂材料。反馈使用节点已有身份自动签名，让对方不能伪造或改写评价；争议和回复进入后续信誉参考，不直接宣布谁恶意。

双方身份可认证的节点调用进入有来源的信誉统计；普通第三方调用若缺少已认证买方身份，只能展示为未认证体验记录。不同 DID 仅代表不同身份标识，不证明背后是独立个人；界面的交易对手数量必须说明这个口径。

主要落点：`a2n_sdk` 中的本地反馈服务和存储、`a2n_node` 中的身份签名与交换、产品控制台。旧 `ratings.rate` 的任务关联、身份检查、去重思路可复用；其只允许买评卖和只允许成功单评价的规则不直接照搬。

**R3：用信誉改变后续机会，并给新人留入口**

Agent 的交付质量按稳定商品身份和版本积累；卖方的履约行为按节点身份积累；买方的合作行为按买方身份积累。一个卖方的多个 Agent 不应自动共享完全相同的质量分，也不能靠改商品名称清掉自己的行为历史。

先展示维度统计、样本数、独立交易对手数、最近表现和更新时间。没有历史表示信息不足，不能默认等同差服务。调用量、在线时长、技术成功和主观好评不直接混成一个人格总分。

算法按以下次序上线：

1. 收集事实并进行离线复算：先用真实反馈和简单汇总观察偏差。旧 `normalize_score` 可作候选，暂不把旧成功事件固定加分模式带进产品。
2. 控制少数评价者的影响：同一买卖双方重复交易的贡献有上限；已知自源不计独立信誉；少量样本向中性估计收缩，同时显示不确定性。
3. 做推荐顺序的观察版本：记录“算法本来会怎样排序”及原因，和实际复用、买方满意度比较，确认没有明显伤害新 Agent 再启用默认排序。
4. 应用到本地选择：先满足技能、可达性、用户预算等条件，再参考交付表现和信誉；为符合条件、样本较少的 Agent 保留有限探索机会。用户可以自己改排序或屏蔽某方，卖方也可设置接单条件。
5. 持续差表现可以逐步降低排序、自动调用频率或某用户愿意承担的额度；后续好表现允许恢复。单个差评不直接形成全网封禁，正常质量分歧与明确协议造假分开处理。

跨节点反馈必须有数据路径，否则每个人只有自己知道的评价：买卖双方保存签名反馈，发现时按需拉取样品/反馈摘要；允许从买方或声明支持该数据服务的公共节点补充有来源的记录，本地复算。使用分页、有效期和大小上限，不同步全网任务。只有卖方提供的摘要标明来源与覆盖范围；看不到负面记录不能推断从未发生。公共服务可替换，不掌握最终评价权；强制公共发现不要求所有节点缓存完整评价历史。

小号、串谋无法仅靠一条评分公式彻底消除。首期限制影响、提高重复造假成本、暴露样本结构，观察它们是否仍能系统性压过正常交易；不承诺算法一定识别全部恶意用户。

验收加入这些反例：卖方自己调自己 100 次、固定双方互刷、一个人反复差评、买方合理拒收、网络失败被误当作品质量差、旧 Agent 更新版本、卖方只提供好评、新人没有样本。每个案例都要看排序和双方接单机会如何变化。

**R4：接轻量小额付费，允许双方自定风险**

首期支持固定每次价格、一个币种和一个双方可用的实际支付方式。买方调用前看见价格、预算上限和是否处于免费期；卖方看见本次付费条件，可设置并发量及累计未结金额上限。价格在本次调用开始时留一份快照，重试沿用同一任务，避免意外重扣。

沿用“双方直接结清或经所选支付渠道结清”的方向，A2N 不抽成、不保管资金。先有通道可核验的实际到账记录，再显示已收款；买方声称已付、双方记下一笔待结款，都不能直接写成到账。外部通道若有成本，事先显示由谁承担，不能冒称 A2N 交易零抽成就意味着任何渠道都零成本。

买卖双方可以承担明确限额内的未结款和不满意交付，按预先显示的简单规则选择补做、协商退款或留下异议。异议自动关联本次调用，能通知对方并回复，逐步进入信誉统计；普通小额交易不以复杂担保、强仲裁或逐字段手工签合同为前置。

若没有可用支付方式，付费调用明确不可用，不把标价和 `NoSettlement` 包装成已完成付费。提款、跨币种原子交易、自动强制退款都不作为这批开发的验收条件。

**R5：在小网络里验证信誉是否有用**

建议试点起点为 3 位独立供给者、至少 10 位使用者、一个需求清楚的场景；规模是招募目标，不作为禁止更小网络使用的准入条件。可以从现有商品详情页类案例接入真实工作流，先让输入和交付预览都容易理解。确定性演示继续用于测试，不计作真实服务质量证据。

重点观察：搜索后找到可用服务的比例、真实交付率、样品可查看比例、前 10 次完成所需时间、双方反馈覆盖率、使用者再次选择同一 Agent 的比例、新 Agent 获得首次调用的等待时间、差评后的改进和误伤情况。付费启用后补充实际结清比例与未结金额，A2N 收入不作为指标。

这些观察区分免费/付费、测试/真实调用、自源/其他来源、技术失败/质量不满意。先记录基线，再定排序权重与门槛；不用预设高分证明市场已经成功。

**实现分工与复用边界**

| 位置 | 承担职责 |
|---|---|
| `a2n-sdk` | 产品运行时、调用事实、试用与样品本地服务、反馈入口、控制台；保留零 a2n 依赖约束 |
| `a2n-node` | 组装运行时，身份签名，样品与反馈的公共接口和按需交换 |
| `a2n-reputation` 等旧领域包 | 提供可复用的规则思路和纯计算函数；依赖全局数据库的部分不直接接入产品节点 |
| `a2n-server` | 兼容回归；已实现的旧平台业务不能代替产品节点验收 |

如果需要共享归一化等算法，先抽取无数据库依赖的计算接口，通过装配注入；同步分层守卫测试。以现有调用事实为数据源，新增试用状态、公开样品元数据、反馈事件和可重算的信誉摘要。无需先重新拆一批包或建设全局账本。

技术映射继续使用 Agent Card 表达服务声明、Task/Artifact 表达任务与交付，A2N 样品和反馈通过扩展承载；这些对象在 [A2A 1.0 规范](https://a2a-protocol.org/v1.0.0/specification/)中已有定义。与标准的完整兼容程度需单独测试，本路线不凭名称宣称兼容已通过。

**实施前需要定稿的三个细则，均不阻塞 R0**

1. 完成 10 次之后的收费条件：旧毕业接口另有“至少 3 条非自源案例、无未结争议、完整验收模板”等门槛，但建单免费判断在额度用尽时已失效，两者并不一致。建议将第 11 次的新调用是否收费统一由卖方明示报价、支付可用性和买方事前所见决定，把信誉置信度用于选择提示，避免样品少或单笔异议无限阻止交易；这是对旧规则的建议调整，实施前单独明确。
2. 自源样品展示：计入试用完成、排除独立信誉这两条保留。建议允许显示“卖方自测”并区分独立样品，替代把内容完全隐藏；是否采用需单独定稿。
3. 评分冷启动：旧规则是评分者 20 次、供给方 20 位评分者才公开分。建议样品立即可看、原始反馈按公开策略展示，汇总分带样本量和置信度，低样本少影响排序；阈值与评价公开期限在真实反馈到来后再定，不在本轮默改常量。

**下一轮开发的具体起点**

第一批改动只交付 R0：修协议 → 稳定商品身份 → 迁移已确认的旧演示挂载 → 真调用与重启验收。随后交付 R1：本地试用状态 → 样品公开投影 → 描述与样品详情页 → 0 到 10 次真实调用验收。R2 的反馈字段和接口可以在 R1 设计时一起确定，评分排序等有反馈后再上线。
