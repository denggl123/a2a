# Console internationalisation (i18n)

Date: 2026-10-21. This document defines the internationalisation boundary, the message-table structure and the rollout route for the A2N node console.
It applies to `packages/a2n-sdk/src/a2n_sdk/web/` (the console frontend) and to user-facing server error messages.

## Iron rules

1. **Protocol fields and error codes are never translated.** Cross-node interoperability relies on English enums (`state`, `evidence_type`,
   `source`, etc.) and on error codes in the `"CODE: description"` form. Translation happens only before presentation to a person.
2. **A message-table key is protocol semantics, not copy.** Keys look like `state.SETTLED` or `evidence.receipt_unverified`, and
   not one Han character may appear in them; copy goes only into the value. Then adding a language does not touch the keys, and the tests do not need rewriting either.
3. **Server error messages stay `CODE: Chinese description`.** The frontend may split off the prefix and translate the description part;
   code and tests may assert only on the error code, never on the message text (the message text changes with the language).
4. **Present the unknown honestly.** If a lookup misses, fall back to the original value or to an explicit "unknown"; do not guess, invent or leave a blank.

## Structure

```
web/i18n.js            Skeleton: language detection, text()/t() access, {name} interpolation, dual mount (window and globalThis)
web/i18n.js MESSAGES['zh-CN']   Default language table (verbatim identical to historical versions)
web/i18n.js MESSAGES['en']      English table (1325 / 1325; a missing key still falls back to Chinese automatically, no blank screen)
sdk/cli_i18n.py                    Command-line language layer: --lang / A2N_LANG / LC_ALL / LANG, t(), error_text()
sdk/err_en.py                      Command-line error descriptions (**generated file**, do not edit by hand)
scripts/gen_err_en.py              Generates err_en.py from web/i18n.js; --check verifies synchronisation
scripts/i18n_check.py              Message-table audit: missing keys / dead keys / bad values / coverage (called by tests/test_i18n_table.py)
docs/*.en.md                       English documentation (paired as X.en.md in the same directory with the same name, first line carries the sync stamp)
scripts/docs_i18n_check.py         Documentation audit: completeness / sync stamp / dead links / structural alignment (called by tests/test_docs_i18n.py)
```

Access conventions:

| Call | Semantics |
|---|---|
| `I18N.text(key)` | Returns the copy if found; returns `null` if not (the caller decides whether to fall back to the original value or to "unknown") |
| `I18N.t(key, vars)` | Returns the key itself if not found; `vars` performs `{name}` interpolation |
| `I18N.errorText(msg)` | Translates a server "`CODE: description`" by code; **the default language is returned as it is** (see stage 2) |
| `I18N.locale()` | The current language (`localStorage['a2n.lang']` → `navigator.language` → default `zh-CN`) |
| `I18N.locales()` | The list of available languages `[{id, label, keys, ready}]`; `label` is the language's **own name**, `ready` = at least one translation exists |
| `I18N.setLocale(name)` | Switches language (memory + localStorage + `<html lang>`, **no re-render**; a full page reload is the page's `switchLocale()`) |

Load order: `i18n.js` must come before any interface script (the first `<script src>` in `runtime.html`).
At runtime `<html lang>` is set automatically to the current language; it is skipped when the stub environment (Node vm) has no `documentElement`.

The language priority is **explicit choice > browser language**: `setLocale()` changes only memory and `<html lang>`,
and does not run detection again — otherwise a user who clicked "English" would be overwritten back to Chinese by browser detection
(this is a bug that really existed in the skeleton; stage 2 fixed it in passing and added assertions).

## Stage 1 migration pattern (follow this for each file)

0. **The page skeleton goes through `data-i18n` first** (`runtime.html` only): copy for static markup is not written in the tag but
   as `data-i18n="key"` with the tag content left empty; attribute copy uses `data-i18n-placeholder` /
   `data-i18n-title` / `data-i18n-aria-label` / `data-i18n-alt`. The page's inline `localize(root)` fills it all in once at startup:
   **write only when found, leave as is when not found** (do not fling key names at the user). `localize()` handles only the first
   screen; dynamically rendered content still fetches its own words in each `render*`.

1. **Check the verification-chain dependencies first**: `grep` whether the target file's Chinese copy is asserted by `runtime_logic_check.js` /
   `node_console_check.js` / `tests/`. Assertions anchored on **rendered output** need no change (values are kept verbatim);
   assertions anchored on **source-code shape** must be rewritten to a double anchor of "the code references the key + the message-table value verbatim".
2. **Pick one of three access channels** (following the original fallback behaviour):
   - The original code has a fallback (`map[k]||value`) → `I18N.text(key)`, falling back to the original value on `null`;
   - It is certain to exist (a key in a static table) → `I18N.t(key)`;
   - It carries interpolation → `I18N.t(key, {name: value})`, with a `{name}` placeholder in the message value.
3. **Split template strings into concatenation**: `'prefix'+v+'suffix'` becomes placeholders; a ternary else branch must not leave bare quotes
   (`:'+I18N.t(...)+'` is a syntax error; it should be `:I18N.t(...)`).
   **Be careful with nested templates**: nesting `` ${cond?`<br>${I18N.t(k)}`:''} `` inside a template very easily mismatches brackets;
   prefer hoisting to an intermediate variable and concatenating (see `kept`/`review` in `experience.js`).
   **Tags must not go into message values**: structure such as `<br>` and `<b>` stays concatenated in the code,
   and the message value holds text only — the "no HTML in message values" assertion in `runtime_logic_check` catches it (`selection.js` has already tripped over this once).
4. **Leave no display text in this file**: even small tables like `modeLabels` are emptied out, leaving only the list of legal key names.
5. **Add assertions before running verification**: a new domain needs at least "one verbatim value + one unknown fallback"; then run all four layers.
6. **Old-vs-new verbatim comparison (recommended)**: after migrating, take the old file with `git show HEAD:<file>`, run the old and new modules
   in the vm with the same stub data, and compare the rendered `innerHTML`/`textContent`. Only if the output length is the same and it matches verbatim
   has the semantics not changed (this time `task-quality.js` at 3746 characters, `points.js` at 2219 characters and `forms.js` across 14 probe groups all showed zero difference).

### Known boundaries

- **There is no copy left in the skeleton.** The static markup of `runtime.html` has only `data-i18n` keys and empty content,
  and those assertions in `node_console_check.js` that say "the page says such-and-such" are still valid (the rendered result is verbatim identical),
  but **changing copy can only be done in the message table** — editing the HTML directly is caught by the "no Chinese left in the skeleton" assertion.
- **`localize()` runs once on the first screen; switching language does a full page reload.** `switchLocale()` =
  `setLocale()` (persist) + remember the tab + `location.reload()`; after the reload the skeleton is refilled by `localize()`
  and each module is rebuilt in the new language. **The boundary "already-rendered strings are not revisited" therefore no longer exists** —
  after a reload even an already-open dialogue, a `notice`, and tables evaluated at module load (such as `methods` in `settlement.js`) are in the new language.
  The cost is that **a form being filled in is lost**, which is a deliberate trade-off (see stage 4).
- **Category / dimension / feedback-direction values are stable ids.** The values of `SKILL_CATEGORY` are `video`/`doc`/…
  rather than Chinese names (the filter state stores the id, so no state migration is needed when adding a language); the display name goes through
  `catLabel()`/`facetTitle()`/`fbDirLabel()`/`upgradeLabel()`/`viewLabel()`, echoing the original value when not found. Changing these tables means changing the assertions too
  (`video-short → category id is video`).
- `node_console_check.js` uses `addInitScript` to write `localStorage['a2n.lang']='zh-CN'` **before anything has been chosen**, so the assertion rubric
  does not depend on the local browser language (the English table is already 100%, so an English browser would now really pick English automatically —
  without pinning it, the baseline for the Chinese assertions would vary by machine).
- `node_console_check.js` depends on `playwright-core` (point `NODE_PATH` at a `node_modules` containing it when it is not installed locally),
  and accepts **only a brand-new temporary node**; running it directly is refused because of the existing 8771 business records.
  For everyday verification use `bash scripts/node_console_check.sh`, which creates a temporary home itself and cleans up afterwards.
- The `methods` table in `settlement.js` is still evaluated at module load and stores **copy** rather than keys.
  Switching language reloads the whole page, so its result is correct right now; but this table remains a place where
  "adding a third language means changing code". To decouple it completely, change it to "store the key, fetch the words when displaying", the same approach as `catLabel()`.
- `business.js` is not loaded by any logic-check script (it is only included by `runtime.html`); its equivalence is confirmed by a one-off
  old-vs-new probe (34 groups of output, zero difference); `runtime_logic_check` only asserts message-table values and source structure.
  The next change here should add a reusable behavioural assertion first.
- `payment.js` is likewise "loaded only in the page": equivalence relies on a one-off probe (31 groups of output, zero difference, covering
  EARN/DEBT/PAY, upfront/authorization, free and no-common-method, refund verification).
  `planMode()` in `payment.js` uses a `switch` rather than a prefix lookup — an unknown mode must return `undefined`
  (as in the original, the interface shows nothing), and must not echo the key name.

## Stage 2: server error codes (2026-10-22)

User-facing server error messages are unified as `"CODE: Chinese description"`. The code is **part of the protocol** (cross-node interoperability,
log search and frontend translation by code all depend on it), and the description is **the half that may change with the language**.

- **Full coverage**: 433 Chinese `raise`s under `packages/` and `scripts/`, 379 codes (including the 19 from stage 0).
  Code names are prefixed by domain: `BACKUP_*`/`RESTORE_*`, `COORD_*`, `P2P_*`, `RELAY_*`, `CARD_*`,
  `FEEDBACK_*`, `DISPUTE_*`, `MANAGEMENT_*`, `PRODUCT_*`, `PUBLIC_NODE_*`, `API_*` …
  Three scripts are **explicitly excluded** (`EXCLUDE` in `scripts/error_codes.py`): `bootstrap.py` is installer
  progress output (each line starts with `✗`, not a protocol error), `docker_acceptance.py` is acceptance assertions, and
  `error_codes.py` is the script's own help text. The exclusions are written in the code, not left to verbal agreement.
- **Register**: `docs/ERROR-CODES.md`, generated by `python scripts/error_codes.py --write`, listing
  "code / description / number of occurrences" grouped by domain. Hand edits are caught by a test.
- **Invariants enforced by tests**: four in `tests/test_error_codes.py` —
  no Chinese raise may lack a code, a code must be uppercase ASCII snake case, the register must be in sync with the source, and the codes must cover
  `API_/MANAGEMENT_/PRODUCT_/RESTORE_/BACKUP_`, the entries that really face the user.
  The check can also be run on its own: `python scripts/error_codes.py`.
- **The frontend translates by code**: `I18N.errorText(msg)`. The default language (zh-CN) is **returned as it is**,
  not one byte changed — logs, screenshots and existing assertions are unaffected; for other languages it looks up `err.<CODE>`,
  uses the translation if found (**the code still stays in front**, for troubleshooting), and falls back to the server's original text if not.
  The hook is `request()` in `runtime.html`: every panel's `notice(e.message)` benefits automatically.
- **The `en` table being empty at that point was deliberate**: filling in 379 English translations in one go with no proofreader
  would only turn Chinese into another kind of Chinese nobody is sure about. Get the mechanism through first and the assertions standing first
  (in `runtime_logic_check`, one `err.BACKUP_CORRUPT` translation is fabricated to verify the translation path), then fill in translations domain by domain —
  stage 5 finished them, see below.

### Trade-offs of stage 2 (written down so nobody has to guess later)

- **One code may appear in several places** (`MOUNT_NOT_FOUND` 7 places, `PEER_TASK_CONTROL_UNAUTHORIZED` 5):
  the same semantics should be the same code, so the frontend can write one piece of copy. The register notes the occurrence count.
- **A description with parameters is translated only to the code level**: `P2P_CARD_FOREIGN_OWNER: 不能替其他节点通告卡片：'did:…'`
  keeps only the generic description when turned into English, and the parameter detail is lost. Keeping the detail would require the server to send
  the parameters in a structured way, which is a protocol change and out of scope here (already noted in the `errorText()` comment).
- **Protocol envelopes are untouched**: `self._failure(sender, request_id, "RATE_LIMITED", "…")` and the like
  already go through the structured channel of §7 error codes, so no `CODE:` prefix is added, otherwise the code would be printed twice.
- **An error code is not an HTTP status**: the `ERROR_HTTP` table in `COORDINATION-API §7` still owns
  "code → HTTP"; this round only added the message prefix and changed no status-code mapping.
- **The old-node fallback in `coord_network.py`** used to decide the type by `"HTTP 404" in str(exc)`;
  now it recognises the `COORD_HTTP_ERROR:` prefix first and the status code second — so a future translation of the description will not cause a misjudgement.


## Stage 4: language switching (2026-10-22, completed)

First get the "switching the language really changes things" chain through, **without touching the copy** (the `en` table was still empty).

- **Entry**: the `#lang` dropdown inside `#langWrap` in the `runtime.html` header, options from
  `I18N.locales()`, labelled with the language's **own name** (`中文` / `English`) — when the interface is already in a language
  you cannot read, the user has to be able to recognise their own line. The option value is the locale id and is not translated.
- **Only ready languages appear**: `ready` = that table has at least one translation. With only Chinese present the whole thing is
  `hidden` (a selector that changes not one character when clicked is worse than no selector); add the first `en` translation
  and the selector appears automatically, **without changing interface code** (stage 5 added 31, so it is now visible by default).
- **Switching = persist + reload the whole page** (changed 2026-10-22): `switchLocale(name)` →
  `I18N.setLocale()` (memory + localStorage + `<html lang>`) → remember the current tab →
  `location.reload()`. After the reload every module is rebuilt in the new language and the skeleton is refilled by `localize()`.
  What was built at first was "re-render in place, no reload", on the grounds that a reload loses the form being filled in and the current tab;
  but **a dozen modules each do a one-off `innerHTML` at load time in the language of that moment** (panels, forms, lists,
  and the "start using this node" first-screen card), and adding "re-render on language change" to every module is bound to miss one,
  and the missed block then stays in the old language forever — half Chinese, half English on the interface, worse than not switching
  (this is exactly how it was found after the English was filled in: the onboarding card in the screenshot was still Chinese). Between two evils:
  a reload loses the form, but no reload delivers a fake bilingual interface. The tab is remembered in `sessionStorage['a2n.page']` and only the three values
  `find|sell|account` are accepted, so the reload returns to it and the only cost left is "the form being filled in".
- **There is no plural form**: `I18N.t()` only does `{name}` interpolation, no singular/plural. Chinese has no such problem;
  English produces "1 public nodes". The convention is **to put the quantity after a colon** (`Neighbours: {count}`,
  `Public nodes configured: {count}`), so the sentence does not have to inflect with the number; when writing new copy with a count,
  follow that. Really supporting plurals would mean adding rules to the table (`one`/`other`), which is a different job.
- **The boundary "already-rendered strings are not revisited" is gone**: after a reload the whole page is rebuilt, and even dialogues and `notice`s
  disappear, so nothing "keeps the old language". That boundary only existed in the in-place re-render version.
- **Verification**: `runtime_logic_check` (list semantics, own names, an empty table not appearing, appearing after a translation is added,
  "persist + reload" with the tab remembered first, an unknown language neither persisted nor reloaded, the first screen looking up the table in English after a reload);
  `node_console_check` goes through a **real dropdown + real reload**: two options, title/buttons/dynamic panels/
  `<html lang>` all change, the module-built onboarding card changes too, error descriptions are translated by code,
  a refresh still remembers, and switching back to Chinese restores everything.

1325 interface strings + 379 error descriptions, written in one go with no proofreader, is just Chinese turned into another kind of
Chinese nobody is sure about. Mechanism, assertions and entry point first; translations filled in domain by domain, each domain immediately visible on the interface —
that is exactly how stage 5 started.

### `err.*`: server error descriptions (2026-10-22)

All 379 codes now have English. This batch does not follow the same rules as the interface copy, and the reason is worth writing down:

- **There is no `err.*` on the Chinese side.** `errorText()` returns the server message as it is in the default language (not one byte changed),
  so the table does not need a second Chinese copy. Copying it would actually add a second source of truth: the server changes its wording,
  the copy in the table is still the old one, and nobody will look at it.
- **So "other languages must be a subset of the Chinese table" does not apply to `err.*`.** Instead the code names are validated against
  `docs/ERROR-CODES.md` (generated by `scripts/error_codes.py` from the source) — a misspelt code is caught the same way,
  rather than only surfacing when a user really hits that error and it quietly falls back to Chinese.
  `tests/test_i18n_table.py::test_error_translations_match_codes` pins this down, and
  `scripts/i18n_check.py` also reports "interface copy coverage" and "error description coverage" separately.
- **No interpolation.** The server has already interpolated the parameters into the original text (`account does not exist: acct-1`), and `errorText()` looks up
  one generic description by code and stitches `code: description` back together. So the values of `err.*` **do not contain placeholders such as `{account_id}`** —
  they would not be substituted anyway and would just be shown to the user as they are. The cost is the loss of parameter detail (stage 2 already recorded this trade-off).
- Verification: `runtime_logic_check` asserts "the code stays in front, the description becomes English" directly with the real translation from the table;
  `node_console_check` really calls `I18N.errorText('BACKUP_CORRUPT: …')` in the English interface,
  confirming that it changes in the browser too.

### A real bug masked by a "coverage-dependent assertion"

When batch 6 was being filled in, `过半覆盖之后英文浏览器才自动切英文` in `runtime_logic_check` suddenly turned red
(coverage 54.1%, but the auto-selected locale was `zh-CN`). The cause was that the UMD wrapper called `factory()` with
**no argument**, while `detectLocale()` / `setLocale()` inside the factory both used `root.localStorage`
and `root.navigator` — `root` did not exist in the factory scope at all, both threw `ReferenceError`,
and both were silently swallowed by their own `try/catch`. The consequences:

- "Remember the language last chosen" had never worked (the line writing localStorage threw as well);
- "Pick automatically by browser language" had never worked either, and it always stayed on the default language.

Both of these were inside `try`, so nothing showed on the interface: switching the language was right at that moment (the in-memory `current` changed),
it just did not survive a refresh. **The reason the assertion had always been green** was that coverage was then 45.1% < 50%,
so both sides of `(enRatio >= 0.5) === (fullPick === 'en')` were `false` — an assertion that "computes the expectation from coverage" degenerates into a tautology on one side of the threshold.

The fix was to pass `root` into the factory (`factory(root)` / `function (root)`). Three pins were added:

- `切过语言会写进 localStorage`, `刷新后（重新 start）仍是上次选的语言` — a round trip at the logic layer;
- `显式选择优先于浏览器语言` — an English browser with `zh-CN` stored must not be changed back to English;
- `刷新后仍是英文`, `刷新后选择器回显上次选的英文` — a **real reload** at the browser layer.
  The storage is not reachable in the stub environment, so this bug could only be found in a browser.

A latent problem in the test itself was fixed along the way: `addInitScript` in `node_console_check` used to hard-write
`localStorage['a2n.lang']='zh-CN'` on every navigation, which amounted to changing the user's choice back to Chinese on their behalf, so refresh persistence could never
be verified; it now writes only "when nothing has been chosen yet" (each run uses a one-off profile, so the first load is necessarily empty).

- **`en` must be a subset of the Chinese table**: misspell a key and that entry never takes effect, with nobody noticing.
  `tests/test_i18n_table.py` pins this down.
- **Message-table audit tool**: `python scripts/i18n_check.py`
  - Missing keys (referenced in code, absent from the table) → exit 1: the interface would show a key name like `rt.foo` directly;
  - Dead keys (in the table, used by nobody) → a notice by default, `--strict` exits 1;
  - Angle brackets in a value (HTML must stay in the code), Han characters in a key, another language not being a subset of the Chinese table → exit 1;
  - **Missed translations** (a value containing Han characters): judged by "Han share" — a table that hardly uses Han characters but has a few values carrying them
    means Chinese was copied without being changed, or only half a sentence was translated (`Search 搜索`). Using a ratio rather than a hard-coded language name
    makes this rule expire automatically when Japanese is added later (which uses Han characters anyway), instead of misreporting normal translations as missed ones;
  - **Placeholders not matching**: a missing `{count}` means a missing number on the interface, an extra one means it cannot be interpolated and
    `{foo}` is shown as it is;
  - `--coverage` prints only the per-language coverage.
  Places where a key name is passed as **data** (the second column of the dimension table is a key name, and `I18N.t(label)` then fetches the words) also count as references,
  otherwise 68 live keys would be misjudged as dead.
  The last two were extracted into `value_problems()`, and `tests/test_i18n_table.py` feeds it synthetic tables to verify
  **that they really fire** — a check that only alerts when something is broken is always green in the normal state, and nobody knows whether it is still alive.
- **Current state**: `zh-CN` 1325 / 1325 (100%), `en` 1325 / 1325 (100%).
  An untranslated key always falls back to Chinese, so the interface never goes blank and never shows a key name.
- **The fallback acceptance does not pick a specific key**: before switching to English, `node_console_check` **temporarily deletes**
  `rt.acct.connect_btn` from the `en` table inside `page.evaluate`, then the "connect" button must still read Chinese,
  and it is restored immediately after reading; `runtime_logic_check` asserts the same thing. The assertion goes "delete → fall back → restore",
  so no batch can make it red — an early version used "some key not yet translated" as a canary and went red once after batch 2
  and again after batch 3.

## Stage 6: command line (2026-10-23, in progress)

Finishing the console is not finishing the product: `a2n-sdk --help` used to be all Chinese, so an English user hit a wall
at the very first step after installing. The command line has no browser, and the language state can only live in the process, so it is **another layer**:
`a2n_sdk/cli_i18n.py`.

- **Priority is isomorphic to the console** (explicit > environment > default):

      --lang en  >  A2N_LANG  >  LC_ALL  >  LANG  >  zh-CN

  Only `zh*` and `en*` are recognised. `ja_JP.UTF-8` falls back to Chinese rather than being guessed as English — with only two languages,
  guessing wrong is worse than not guessing; `C` / `POSIX` likewise, since they only mean "no localisation environment", not an English user.
  On Windows this is usually Chinese (no `LANG` set), and on Linux/macOS it follows the system —
  consistent with the console's "an English browser goes to English automatically".
- **`--lang` is stripped before argparse.** `product_cli` uses `parse_known_args` to pass unrecognised
  arguments through to the subcommand; if `--lang` were left to argparse it would leak into `extra`, be passed on to the node process, and become
  a startup failure of "the node does not recognise --lang". The cost is that it does not appear in the `options` list, so its usage is written out explicitly
  in the `epilog` of all three entries.
- **The language is decided only once.** `product_cli` calls `a2n_node.__main__.main()` again, and that layer's argv
  is assembled and does not contain the user's `--lang`; parsing again would overwrite the user's choice with the environment variable's value.
- **An unrecognised value must be an error** (`CLI_LANG_UNSUPPORTED`), and must not fall back silently: the user thinks
  `--lang fr` took effect while it is still Chinese, and this kind of "looks successful" is the hardest to diagnose.
- **There is only one copy of the English error descriptions**: `err.*` in `web/i18n.js` is the single source,
  and `scripts/gen_err_en.py` generates `a2n_sdk/err_en.py` (380 codes). Hand-copying into Python
  will drift from the JS sooner or later, and the drift shows up as "English on the interface, Chinese in the terminal", with nobody looking at both.
  `tests/test_cli_i18n.py` watches the synchronisation, so changing the message table and forgetting to rerun the script goes red.
- **The four invariants of the command-line copy table** are the same as the browser table: `en ⊆ zh-CN`, no Han characters in English,
  placeholders one-to-one, and every `cli.*` key used in the source must be in the table (otherwise the terminal prints the key name).
- **Verification**: really start a process and run `--help` (once in each language), `--lang` after the subcommand is also recognised,
  and an unsupported value exits 2 with the available values. These go through the user's real path, not function-level stubs.

### Interface error codes added (2026-10-23, completed)

`{"error": "需要本机管理凭据"}` and similar in `local_api.py` used to be Chinese only, with no code —
without a code there is no translating by code, so both the console and the command line could only show Chinese as it was. This round added 36 codes
(register 380 → 416), and both interfaces can now fetch English by code.

- The scan rubric of `scripts/error_codes.py` was widened accordingly: it used to recognise only `raise`, now **any Chinese literal starting with
  `CODE: `** counts as a registered entry — error copy can appear in `{"error": …}`, in `CallResponse.failure(…)`, and in the `data.error` of a streaming response,
  and recognising them one API at a time would eventually miss some. Only those already carrying a code are collected; `detail` / `reason` without a code
  (such as `对射未达成`) are **not** forced to gain one, because they are state descriptions that belong to "stable id + label table", not errors.
- One code should have only one description: `异议不存在` has the same semantics as the existing `DISPUTE_NOT_FOUND` (no such
  dispute record), so the old code and old copy were reused rather than coining a near-synonym.
- This batch's English is listed as its own section in the message table (`// 服务端错误说明：本机 API 与节点响应`):
  grouping by source is easier to find than stuffing it alphabetically into the four sections above.

### Not done yet

- **About 30 diagnostic descriptions** (`detail` / `reason`: NAT hole-punch results, reasons for a late receipt, conclusions of network path
  probing): these are state descriptions rather than errors, and to put them into English they first have to become "stable id + label table",
  the same approach as `catLabel()` — the work is in changing the data shape, not in translating.
- **About 440 pieces of Chinese-only copy in other modules** (state labels, logs): mostly operational logs, and whether they need English
  depends on "whether an English user would read the logs".
- Known trade-off: the server interpolates parameters (port number, log path) into the Chinese description, so after a language switch only the generic description remains
  and the parameter detail is lost. Keeping it requires the server to send parameters structurally, which is a protocol change — the same trade-off as stage 2.

## Stage 7: English documentation (2026-10-24, completed)

The interface, the error descriptions and the command line all have tables, and a mistake there turns a test red; **the documentation does not**. After a 3000-word Chinese
document is translated into English, the Chinese keeps changing and nobody goes back to read the English — half a year later the English still says
"the current version is 0.2.0b3" while `VERSION` is 0.2.0b7, and the reader has no clue that what they are reading is a fossil.
So this stage sets up the rules and the ruler first, and only then starts writing.

### There is only one pairing rule

```text
X.md  ↔  X.en.md        (same directory, same name, .en.md suffix)
```

The suffix was chosen over a `docs/en/` mirror tree for exactly one reason: **links do not have to be rewritten**. `../VERSION`,
`../scripts/README.md` and `../../docker/README.md` remain valid as they are in the English version. A mirror tree would make every relative link in every
document go up one more level, and one mistake in 51 documents is a dead link, and a dead link is only found when somebody clicks it.

The link rubric can therefore be mechanised: a link in the English version that points at `foo.md` **must**
be written as `foo.en.md` if `foo.en.md` exists, otherwise the English reader clicks once and drops back into Chinese.

`docs/design/` is out of scope: the file names there are Chinese to begin with (`A2N-顶层架构总纲-v2.md`), so an English version would have to be renamed first,
which is a different job, and they are historical design drafts.

### Sync stamp

The first line of the English version is `<!-- source: <first 12 hex of the Chinese sha256> -->`. As soon as the Chinese changes, the stamp no longer matches and
`scripts/docs_i18n_check.py` reports "expired".

This is annoying, but it is the only real value of this stage: **delete it and the English starts to rot silently.**
After a re-read, run `--stamp` to refresh it; `--stamp` does not touch the body, only the first line.

### Audit items

`scripts/docs_i18n_check.py` (called by `tests/test_docs_i18n.py`):

- Han characters in the English version → failure (if Chinese really must be quoted, that spot on the interface should have English too). **The exception is a quotation**:
  Han characters inside backticks do not count as a missed translation — the Chinese column of the terminology table (`结算` → settlement) and the Chinese original quoted
  in an assertion (`过半覆盖之后英文浏览器才自动切英文`) must be copied in Chinese, because translating them away would leave the reader unable to `grep`
  the source with them. Inline code is used rather than a per-file allowlist because the distinction "quotation vs missed translation" holds for any
  document, so no document needs an exception;
- Dead links, or links that should point at the English version but point at the Chinese one → failure;
- The heading count and the code-fence count must match the Chinese version — one heading fewer usually means a whole section was missed,
  and a fence count mismatch means a code block was not closed and everything after it was swallowed into the code;
- A missing or expired sync stamp → reported only by default, a failure under `--strict` (used before a release);
- `--fix-links` mechanically rewrites the links that should point at the English version (examples inside fenced code blocks are left alone) —
  people always copy links from the Chinese version when writing, so rather than hunting them down one by one afterwards, let the script fix them;
- `--list` also prints the untranslated list by size, and the numbers in `--coverage` come from it.

### The error-code register is generated, not translated

`docs/ERROR-CODES.en.md` is generated by `scripts/error_codes.py --write`, and the description text is taken directly from
`a2n_sdk.err_en` (that is, `err.*` in `web/i18n.js`). Hand-copying a 416-row table is bound to disagree with the interface copy,
and error descriptions are exactly what a user is most likely to see in two places at once. `--write` regenerates the English version along with it,
because the English version's sync stamp points at the Chinese version that was just written out.
