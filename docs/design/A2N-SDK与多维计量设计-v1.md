# A2N SDK 职责与多维计量设计 v1.0

> 配套：《A2N-注册与发现设计(A2A)-v1.md》《A2N-架构与模块设计-v1.md》
> 本文回答三个问题：**SDK 到底承担什么、新 agent 上线意味着什么、时长/token/调用这些多维信息怎么管。**

---

## 0. 发现模型：按需拉取，本地列表，无人同步全量

> 修正 v1.0 的表述：SDK 不承担"维护全网目录"，但**完整承担"发起发现"和"维护我的市场列表"**——这是**客户端视角的按需发现**，与"P2P 目录同步"是两回事。后者要维护全量一致视图，前者只是"我要用的时候去查一下"。

### 三种角色

| 谁 | 做什么 | 明确不做 |
|---|---|---|
| **节点 SDK** | 发布 card，让自己**可被搜到** | 不维护全网目录，不广播 |
| **注册表 M1** | 让发现**成为可能**：可搜索索引 + 背书签名 | **不推送、不推荐、不存储"谁的列表里有什么"** |
| **使用方 SDK** | 按需搜索 → 本地验签 → 存入"我的市场" | 不同步全量，不缓存他人数据 |

### 四条关键属性

1. **Pull，不是 Push。** 没人订阅全量目录。注册表只服务查询，不向任何人推流。
2. **本地列表是私人的。** "我最适合谁"是我的判断，平台不存、不知道，也就**无法据此做推荐**。
3. **本地可独立验签。** 注册表返回候选时附带 `card_hash` + 背书签名，使用方本地验证——**不必信任注册表返回的内容本身**。
4. **发现自由，派单受控。** 你可以自由搜、自由选、自由收藏；但真正派单那一刻，调度器仍做一次轻量校验（状态 / 在线 / 黑名单），因为涉及钱。

### 为什么这个模型比"平台下发目录"更好

| 维度 | 好处 |
|---|---|
| **扩展性** | 读压力 ∝ 查询量，而非 节点数 × 使用方数；没有 fan-out 风暴 |
| **中立性** | 平台提供**搜索**，不提供**推荐**；且不掌握"谁在用谁"的关系图 |
| **隐私** | 协作关系留在本地，平台无法构建用户画像、也就无法操纵分配 |
| **容错** | 注册表短暂不可用时，已加入本地列表的 agent 仍可被调用（经调度器校验） |

**一句话：注册表管"可被发现"，使用方管"我发现了谁"，调度器管"这一单能不能派"。三件事，三个主体，互不越界。**

## 1. 有人提供一个 agent ≠ 市场上多一个商品

新 agent 出现后，有三层可见性，**准入条件完全不同**：

| 层 | 是什么 | 准入条件 | 新 agent 立即满足吗 |
|---|---|---|---|
| **注册表条目** | 技术目录，有 card 就有条目 | card 签名有效 + 域名验证 | ✅ 是 |
| **调度候选集** | 能被派单 | `ACTIVE` + 在线 + 过 PROBATION | ❌ 需试单期 |
| **行情板可见** | 公开展示 | 有真实成交统计 | ❌ 需跑出数据 |

**这是刻意的克制。** 凡是涉及真金白银的位置，都不允许"上线即出现"。一个刚注册的 agent 能在注册表被查到，但不能立刻接大单、也不该出现在行情板上——因为它还没有任何可验证的历史。

### 1.1 第四层：我的市场列表（My Roster，仅本地）

平台侧三层之外，使用方本地还有一层——**只有这里，才是真正"我的市场"**。

| 项 | 内容 |
|---|---|
| **存什么** | agent_id、card_hash、发现时间、我的私人标签/评分、**我侧的本地观测**（我自己跑出来的成功率、时延、失败原因）、信任标记 |
| **存在哪** | 使用方本地（SQLite / 加密文件 / 浏览器 IndexedDB） |
| **谁写** | 只有使用方自己 |
| **平台知道吗** | **不知道，也不存** |

两种加入方式：

1. **搜索发现** → 本地验签 → 加入
2. **手动添加**（填写 agent_id 或 card_url）→ 用于私有 / 定向 agent

为什么必须有这一层：

- 调用时不必重复搜索，低延迟
- **保留我自己的观测**：平台给的是全网信誉分，而"最适合我"取决于我自己的场景——平台算不出来，也不该知道
- 平台看不到这张表，就无法对我的选择施加影响

> **这条与铁律一直接相关**：平台一旦掌握"每个人的偏好列表"，就能通过调整返回顺序影响成交与价格。不存，是最干净的隔离——**搜索可以中性，推荐永远不中性。**

调用时可指定范围：`任意（自动调度）` / `仅限我的列表` / `指定这几个`。无论哪种，调度器在派单前仍做一次轻量校验（见注册文档 §5.3）。

## 2. SDK 的六大职责（模块划分）

比原设计多了两个模块：**计量（meter）** 与 **本地校验（verify）**。

| 模块 | 职责 | 说明 |
|---|---|---|
| `a2n_sdk.card` | 生成、签名、托管 Agent Card | `/.well-known/agent.json`，含 `metering_dimensions` |
| `a2n_sdk.registry` | 注册、能力更新、心跳、状态查询 | 30s 心跳，断连自动被摘牌 |
| `a2n_sdk.runtime` | 执行 A2A task（invoke / streaming） | 对齐 A2A 任务生命周期 |
| **`a2n_sdk.meter`** | **多维计量采集 + 上报** | **本文 §3-§5 的核心；签名不在此模块——SDK 保持零依赖，由调用方注入 `attest_fn(task_id, node_id, dims)`，签名格式不进 SDK（唯一口径源是 `a2n_p2p.attest`）** |
| **`a2n_sdk.verify`** | 本地校验：自己的账（Merkle 证明）、任务结果 | 让节点能独立发现平台出错 |
| `a2n_sdk.discovery`（可选） | 本地只读目录缓存 | 副本，标注"可能过期" |

## 3. 多维计量：维度体系

### 3.1 通用维度（所有能力都采集）

| 维度 | 单位 | 谁能观测 |
|---|---|---|
| `wall_time_ms` | 毫秒 | **双方** |
| `call_count` | 次 | **双方** |
| `gpu_seconds` | 秒 · 卡 | 仅节点（内部真相） |
| `cpu_seconds` | 秒 · 核 | 仅节点 |
| `vram_peak_gb` | GB | 仅节点 |
| `input_tokens` / `output_tokens` | token | 仅节点（模型口径） |
| `net_in_bytes` / `net_out_bytes` | 字节 | 双方近似 |
| `retries` / `error_code` | 次 / 码 | **双方** |

### 3.2 业务维度（由 skill 自己在 card 里声明）

```json
"x-a2n": {
  "metering": {
    "dimensions": [
      { "key": "page_count",   "unit": "page",  "verifiable": true  },
      { "key": "gpu_seconds",  "unit": "s*gpu", "verifiable": false },
      { "key": "output_tokens","unit": "token", "verifiable": true  }
    ],
    "basis": "max(page_count, gpu_seconds)"  
  }
}
```

按能力类型举例：

| 能力 | 计量维度 |
|---|---|
| OCR / 文档处理 | `page_count`、`call_count`、`gpu_seconds` |
| LLM 推理 | `input_tokens`、`output_tokens`、`gpu_seconds` |
| 翻译 | `char_count`、`output_tokens` |
| 语音 | `audio_seconds` |
| 渲染 / 视频 | `gpu_seconds`、`frame_count` |
| 数据抓取 | `call_count`、`net_out_bytes` |

### 3.3 维度的三条性质（决定能否作为结算依据）

| 性质 | 含义 | 不满足会怎样 |
|---|---|---|
| **可计量** | SDK 能稳定采到 | 无法上报 |
| **可验证** | 平台侧或第三方能独立核对 | **不能作为结算依据**，只能做统计 |
| **可复算** | 给定输入 + result_hash 能重放得出 | 争议时无法裁决 |

**规则写死：只有同时满足"可计量 + 可验证"的维度，才能进入分账计算。**
只满足可计量的（如 `gpu_seconds`），只能进统计与信誉，不能单独拿来收钱——因为那是节点单方面说了算的数字。

## 4. 双向计量：两个真相源互相牵制（本设计的核心）

```
        ┌─────────────────────┐        ┌─────────────────────┐
        │  节点自报（SDK）      │        │  平台侧计量（A2N）    │
        │  内部真相            │        │  外部真相            │
        │  token / GPU 秒 / 页 │        │  wall clock / 次数 /  │
        │  显存峰值 / 业务维度  │        │  结果 hash 校验       │
        └──────────┬──────────┘        └──────────┬──────────┘
                   └──────────→ 对账 ←────────────┘
                                 │
                    ┌────────────┴────────────┐
               差异在阈值内              差异超阈值
                    ↓                        ↓
              按实结算                抽样复算 → 仲裁
```

**为什么不采信任何单方口径：**
- 只信节点自报、又无凭据 → 节点可以虚报 token 数多收钱
- 只信平台侧 → 平台看不到 GPU 内部，无法计量推理类任务

**所以必须是双向对账：**
1. 节点在交付边界连署一份计量：inline 交付时节点在 `hub.forward` 下传 `task_id` + 与入账同一份 `dims` 就地 `sign_metering`（`a2n_p2p.attest` 是签名唯一源），随回包上行；推送交付由 `Node._handle` 签它即将上报的那份 usage。归因靠卡上公钥，卡未声明 `x-a2n.sovereign.pub` 一律拒收。
2. 平台侧记录自己的观测（wall clock、次数、结果校验），并 `verify_metering` 验签
3. 对账：差异在阈值内（建议 ±5% 或绝对值取大者）→ 按实结算
4. 超阈值 → 抽样复算（找第三方节点用相同输入重跑）→ 仲裁 → 影响信誉
5. 系统性虚报 → 降级 → 黑名单 + 扣除未结算额

**这套机制正是 A2N 中立性的具体形态：谁的单方数字都不采信，只认两个独立来源能对上的部分；而现在节点侧那一份还带真签名——平台 `verify_metering` 验不过就进争议，绝不进已对账。**

> 更正（2026-09-14）：计量签名已真正落库出链。`a2n_p2p/attest.sign/verify_metering` 是签名唯一源；SDK 保持零依赖，仅由调用方注入 `attest_fn(task_id, node_id, dims)`，签名格式不进 SDK（不要写成"SDK 里做了签名"）。控制台"计量签名"徽标 = `已签 N/M` / `未签名`——无签名的如实标为未签名，不伪造成已签。

## 5. 预算冻结与按实结算

### 5.1 时序

```
使用方发任务：声明预算上限 + 接受的价格快照
   → 冻结预算（按上限）
   → 节点执行
   → 节点上报 UsageReport（含交付边界连署的计量 attestation，由 `a2n_p2p.attest` 验签）
   → 平台侧对账
   → 计算实际消耗 amount = Σ(dim_i × unit_price_i)
   → 解冻差额退回使用方
   → 按实际 amount 分账（90/2/3/5）
```

### 5.2 价格从哪来（不能平台定价）

| 概念 | 谁定 | 说明 |
|---|---|---|
| `price_hint` | 节点 | 提示价，写进 card，仅用于预算估计 |
| **合约价** | **使用方 + 节点** | **任务创建时写进 contract，锁定且不可改** |
| 平台报价 | ❌ 不存在 | 铁律一 |

**关键机制：任务创建时锁定 `price_snapshot`**（记录当时 card 里 price_hint 的版本与 card_hash）。这样节点事后涨价无效——你按接单那一刻的价格结算。

### 5.3 公式

```python
amount_point = min(
    sum(dim_i.value * contract.unit_price_i for dim_i in verified_dims),
    frozen_budget_point          # 永不超过冻结预算
)
```

**`verified_dims` 只包含"可计量 + 可验证"的维度。** 且永远有上限兜底，不会出现"跑个任务把余额跑穿"。

## 6. 数据结构

```json
{
  "usage_id": "u_7k2",
  "task_id": "t_9x2f",
  "node_id": "n_8f3a",
  "dims": {
    "call_count": 1,
    "wall_time_ms": 812,
    "gpu_seconds": 0.94,
    "input_tokens": 128,
    "output_tokens": 512,
    "page_count": 3
  },
  "observed_by_platform": { "wall_time_ms": 845, "call_count": 1 },
  "result_hash": "sha256:...",
  "contract_ref": { "card_hash": "a_9x3", "price_version": "2026.09.01" },
  "measured_at": "2026-09-08T10:00:00Z",
  "signature": "..."
}
```

```sql
CREATE TABLE usage_reports (
  usage_id   TEXT PRIMARY KEY,
  task_id    TEXT NOT NULL,
  node_id    TEXT NOT NULL,
  dims       JSONB NOT NULL,          -- 节点自报
  observed   JSONB,                   -- 平台侧观测
  variance   NUMERIC(6,4),            -- 对账差异率
  result_hash TEXT NOT NULL,
  contract_ref JSONB NOT NULL,        -- 锁定的价格版本
  signature  TEXT NOT NULL,
  status     TEXT,                    -- pending | reconciled | disputed
  created_at TIMESTAMPTZ
);
CREATE INDEX idx_usage_task ON usage_reports (task_id);
CREATE INDEX idx_usage_disputed ON usage_reports (node_id) WHERE status = 'disputed';
```

**计量记录必须进凭证链**——它是分账的唯一依据，没有计量就没有付款，这两者必须一一对应、可追溯。

## 7. 争议与复算

| 场景 | 处理 |
|---|---|
| 使用方质疑计量 | 用 `result_hash` + 原始输入找第三方节点**付费复算** |
| 复算一致 | 质疑方承担复算成本，节点信誉加分 |
| 复算不一致 | 节点承担成本 + 退还差额 + 信誉扣分 |
| 系统性偏差 | 自动触发降级；累计三次 → 黑名单 |

**复算本身也是一个任务**，走同一套调度与分账流程——**用你自己的市场来监督你自己的市场**。这个自洽性很关键：不需要额外建一套监督系统。

---

## 8. 一句话

SDK 不只是一个执行器，它是**节点在市场里的全部人格**：它声明你是谁（card）、证明你干了什么（result_hash）、报告你花了多少（UsageReport）、并且能自己校验账有没有被记错（verify）。

而所有它报上来的数字，都要过一遍对账——**因为在一个中立的公证处里，任何单方面的陈述都不构成事实。**
