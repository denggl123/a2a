## 二、P0 — 阻断级（收费调用走不通）　【已修 · 2026-09-14】

> 修法：relay 收口 + 使用端改走 `/v1/invoke`。下文"根因/建议"是**走查当时的分析**，已被取代。

### P0-1 绑了直付渠道，却拿不到调用资格　【已修】

**现象**：`acct:newbie` 已绑定支付宝（ACTIVE、CNY），点收费 agent（accepts = `peer_account, direct_pay:alipay`）的「试调用」，返回：

```
失败 15 ms
{"detail":"没有与该 agent 的 ACTIVE 对等账户配对，无调用资格"}
```

**同一时刻、同一身份、同一 agent，走 A2A 入口却是通的**：

```
POST /a2a/ag_8fa53af7af3b   （X-Principal: acct:newbie）
→ 200 completed · settle_mode=direct_pay:alipay · charge_id=pc__56ee83595c86
```

**根因**：`packages/a2n-server/src/a2n_server/routers/transport.py:188` 的 `call-token` 只放行两种：**已对等配对** 或 **免费 agent**。已绑定直付渠道的用户不在内。而控制台「试调用」(`relayCall`, console.html:859) 与 SDK `call_agent` 都强制先取 call-token → 于是直付用户在 UI 侧被卡死。

**为什么测试没抓到**：冒烟 ④「直付调用通过」走的是 A2A 入口（`send()`），从未覆盖控制台/SDK 的中继路径。

**影响**：用户在控制台上看到的收费 agent 全都调不动；面板自己写着"收费 Agent 需已配对（或已绑定收付款方式）"——**界面承诺与后端行为矛盾**。这是"绑定即自动结算"产品叙事的正面破口。

**建议**：
1. `call-token` 增加第三分支：主体已绑定与 agent `accepts` 交集为直付渠道的，放行（凭据语义交给后续 `_bill_relay_call` 按 direct_pay 记账）；
2. 或让控制台「试调用」对直付型 agent 直接走 `gateway.invoke`（与 A2A 同一编排），与 SDK `call_agent` 对齐；
3. 补一条冒烟：绑定渠道 → **经控制台路径**调用成功。

> **实际怎么修的（2026-09-14）**：三条建议都没采纳。真正做的是**把 relay 从"调用方式"降级为"对等账户的底层原语"**：
> - 程序化入口统一为 `POST /v1/invoke`，走治理链（门禁唯一源 `gate.resolve`，免费/试用/配对/直付/x402 全在此判）；
>   SDK `call_agent` 走同一条链，`relay()` 只是裸中继原语。
> - 控制台不再调 relay，只调 `/v1/invoke`（`tests/test_relay_closure.py` 断言拦住回退）。
> - `call-token` **故意不加第三分支**：403 文案直接指回 `/v1/invoke`（"走错门了"要好过"门开着但不说"）。
> - 直付用户的资格判定落在**服务端门禁**上：门禁通过即放行，不再由 UI 预判 ——
>   "对等账户是默认匹配、不是门槛"，付费方式只当**偏好筛选**。

## 三、P1 — 明显体验缺陷　【P1-2 / P1-3 / P1-4 / P1-5 / P1-6 均已修 · 2026-09-14】

> 修法一句话：绑定走 UPSERT（去重）、错误渲染做人话（含 402/403 分流）、
> 账户页标注「积分余额（网内通用）· 渠道付款不走这个余额」并就地放入口、
> 流水"对方"翻译成名称、价格表单按**主单位**填（元 / USDC）。

### P1-2 同一渠道可重复绑定，产生重复记录

`acct:newbie` 绑定一次支付宝后，账户页显示 **「已绑定 (4)」四条一模一样**的 alipay 记录（`probe-bind.png`）。
根因：`packages/a2n-account/src/a2n_account/paymethods.py:48` 直接 INSERT，无去重/UPSERT，前端也未禁用已绑渠道。

**建议**：同 `principal + channel` 走 UPSERT（保留最新凭据）；前端把已绑渠道的「去绑定」改为「换绑/解绑」。

### P1-3 错误提示是裸 JSON

`console.html:113` 的 `api()` 把 HTTP 响应体原文 `throw new Error(t.slice(0,200))`，于是 UI 里直接显示 `{"detail":"..."}`。所有失败路径（试调用、绑定、上架）都如此。

**建议**：统一错误渲染——提取 `detail`、映射成人话、附一个可点的下一步（如"去绑定支付宝"）。后端 `detail` 也应避免内部术语（"ACTIVE 对等账户配对"）。

### P1-4 余额语义不清 + 充值入口藏太深

账户页「我的余额 ¥0.00」与「近期付款 ¥0.02 2 笔」并列，用户无法理解"我付过钱为什么余额是 0"（余额其实是**积分账户**余额，渠道付款不经过它）。而"模拟充值"按钮在 **高级功能 → 全网总览**（console.html:206），账户页没有任何入金入口。

**建议**：
1. 余额卡明确标注「积分余额」并一句话说明它与渠道付款的关系；
2. 账户页直接放入金/充值入口（demo 环境加"演示"标识）。

### P1-5 流水「对方」显示 agent_id

账户流水对方列显示 `ag_8fa53af7af3b`、`ag_8247a0decb5c`（`06-account.png`）。用户认不出是谁。

**建议**：显示 agent 名称，id 收进悬浮提示或详情。

### P1-6 价格输入要求用户按「最小单位」心算

卖 Agent 表单价格填 `CNY（分）`＝3 表示 ¥0.03/次；USDC 要按 `10⁻⁶` 填。虽有 hint，仍是开发者口径。

**建议**：输入框接受 `3`、`¥0.03`、`0.03` 三种写法并实时回显"= ¥0.03/次"；或默认按元输入。

## 五、DX — 命令行/SDK 用户　【DX-14 / DX-15 均已修 · 2026-09-14】

### DX-14 `a2n_sdk list` 输出不可读且自相矛盾

```
{ "card_json": "{...整个卡...}", "name": "...", "sla": {...},
  "price_hint": null,        ← 但 card_json.x-a2n.price_hint 里是有值的
  "card_hash": "...", "visibility": "public", ... }
```
原始 registry 行直接吐出：`card_json` 字符串与解析后的字段重复，`price_hint` 一处为 null 一处有值。

**建议**：CLI 默认输出精简表（名称/技能/价格/信誉/可达/结算方式）；`--json` 才给原始；修掉 `price_hint` 与 `card_json` 的口径矛盾（价目事实只在 card 里，就别再投影一个空列）。

### DX-15 CLI 没有 discover / call 子命令

`Client` 有 `discover()`、`call_agent()`，但 CLI 只暴露 `shelf / update-card / list / get`。号称"机器可读"，却无法从命令行发现与调用。

**建议**：补 `discover`、`call` 子命令，与文档里的 Quickstart 串起来。

## 六、做得好的地方（别改）

1. **落地页信息架构干净**：三主入口（找/卖/账户）+ 高级功能折叠，正确的事在前；
2. **免费调用一键成功**，且回传端到端耗时（"成功 338 ms"）——实测口径可见，是差异化亮点；
3. **身份切换器**（右上角）让评审/演示极方便；
4. **卡片可复制 JSON 带走**（试调用旁的「卡片」），符合"拿到信息去别处用"的真实诉求；
5. **上架表单默认值合理**（随机名、描述自动生成、技能预填、价格提示），新卖家能一路点完；
6. **对账/凭证/仲裁/共识/AP2 收进高级**，且账户页的"账户状态：正常 · 对账正常，出入金不受限"给了安全感。
