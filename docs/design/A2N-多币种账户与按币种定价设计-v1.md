# A2N 多币种账户、按币种定价与控制台设计 v1

> 范围：账户（稳定币 / 支付宝 / 积分）、按币种分开定价（按次 / 按 token）、控制台的账户操作与流水。
> 目标读者：实现者。本文只做设计决策与数据模型，不含实现细节。
> 配套前提：平台免费不抽成；自持一对一自动结算；资金点对点、平台不归集（二清红线，见 §1.6）。

---

## 1. 六条前置决策（后面所有设计都由它们推导）

### D1 平台不做汇率换算
**汇率就是价格。** 平台一旦提供“按今日汇率把 USDC 折成 CNY”，它就在定价——直接违反铁律一（只发行情不定价）。
因此：agent 为每种币种**自己标价**，使用方选择其中一种支付。平台不换算、不套保、不承诺任何兑换率。
行情板可以**展示**各币种的历史成交价（那是事实），但不提供换算服务。

### D2 计价币种 = 结算币种
一次调用从报价到付款到凭证，全程同一个币种。跨币种结算（用 USDC 付 CNY 标价的单）在一期不支持——它会把汇率风险塞进系统，而系统没有能力也没有牌照承担它。

### D3 A2N 只呈现自己刻章过的事实
- **积分**：价值在 A2N 账本内 → 可以显示真实余额。
- **支付宝 / 稳定币**：钱在外部 → A2N **不知道也不该知道余额**。

所以控制台对外部媒介只显示三类 A2N 自己有据可查的量：**已结算、待结算、流水**；余额位置如实标注“外部账户，A2N 不掌握余额”。**不允许用估算冒充余额**——这跟“不替供给方定价”是同一条纪律。

### D4 金额一律：整数最小单位 + 币种 + 指数
`amount_minor`（整数） + `currency` + 指数（由媒介定义固定，不随行变化）。
禁止浮点、禁止把“分”写进字段名（现有 `amount_fen` 正是这个错误，见 §5.1）。

### D5 积分只做记账与流水，不实现发行
用户明确“先不管积分怎么来”。因此：积分类账户**只实现记账与流水**，发行口子保持封闭（网络侧没有任何增发路径，守住铁律三）。
账本侧的对账不变式仍然成立：积分总量 ≡ 托管读数；在来源确定前，总量恒为 0，任何非零都属异常。

### D6 资金点对点，平台不归集
承接上一轮结论：钱从使用方账户直达提供方账户，平台只发结算指令与凭证。钱一旦在平台账户停留再分发 = 二清，**与是否收费无关**。

## 2. 三种媒介的定义

| 媒介 | 币种 | 最小单位（指数） | 余额可见性 | 自动付款机制 | 适用 |
|---|---|---|---|---|---|
| 稳定币 | USDC / USDT | 链上最小单位（10⁻⁶） | 外部不可知 | 钱包签名转账；x402 凭证即付（已接入） | 海外线 |
| 支付宝 | CNY | 分（10⁻²） | 外部不可知 | **使用方签约免密代扣** → 提供方商家收款 | 国内线 |
| 积分 | POINT | 1 积分（10⁰） | **A2N 可知** | 账本内划转（二期，冻结→验收→分账） | 全网 |

两条必须写在代码注释里的现实约束：

1. **支付宝没有“个人对个人自动转账”的开放 API。** 唯一可规模化的自动付款路径是：使用方签一次免密代扣协议，提供方作为收款商家。所以不是“绑个支付宝就能自动扣”，而是“先签一次授权”——这恰是 AP2 intent（上限 + 时效）在真实渠道的落地，A2N 结构已有。
2. **稳定币在中国大陆境内业务不可用**（虚拟货币相关业务活动属非法金融活动）。架构支持，但产品上只面向海外线，文档与 UI 需明示地域限制。

## 3. 账户模型

### 3.1 语义（沿用现有，不另起炉灶）
一个主体（owner）持有多个结算账户——不同媒介、不同用途各一个。A2N 不存钱、不托管、不校验外部账户真伪，只记录“这个主体声明自己有这么一个账户，并愿意用它结算”。

### 3.2 `party_accounts` 扩展列

| 字段 | 类型 | 说明 |
|---|---|---|
| `medium` | TEXT | `stablecoin` / `alipay` / `points`（**媒介 ≠ 币种**：同一媒介可有多种币种） |
| `currency` | TEXT | `USDC` / `USDT` / `CNY` / `POINT` |
| `network` | TEXT | 链或渠道：`ethereum` / `solana` / `alipay` / `a2n` |
| `address` | TEXT | 收款地址 / 支付宝账号 / 商户号；积分账户为账本科目 id |
| `direction` | TEXT | `payer`（付款）/ `payee`（收款）/ `both` |
| `exponent` | INTEGER | 最小单位指数，由媒介定义固定（USDC=6、CNY=2、POINT=0） |
| `is_default` | INTEGER | 该币种的默认账户 |
| `verified_at` | TEXT | 校验时刻（A2N 只标注是否做过校验，不声明真伪） |

原有 `owner_id` / `label` / `ref` / `status` 保持不变——多账户语义已建成，这次只是给它加上“装的是什么钱”。

### 3.3 三类账户的能力差异（诚实边界）

| 能力 | 稳定币 | 支付宝 | 积分 |
|---|---|---|---|
| 绑定/解绑 | ✅ | ✅ | ✅（系统内科目） |
| 收款地址登记 | ✅ | ✅（需商家资质） | ✅ |
| 自动付款 | ✅（签名/x402） | ✅（需签约授权） | ✅（账本划转） |
| 自动退款 | ❌ 需对方配合 | ✅（有退款接口，需留窗口期） | ✅（账本逆向） |
| 余额显示 | ❌ 外部不可知 | ❌ 外部不可知 | ✅ 真实余额 |

## 4. 价目表：按币种 × 技能 × 计量维度

### 4.1 结构（Card `x-a2n.price_book`，v2，取代 v1 的 `price_hint`）

```json
"price_book": {
  "ocr-pro": {
    "CNY": {
      "dimensions": [
        {"key": "call_count",    "amount": 3, "per": 1},
        {"key": "output_tokens", "amount": 1, "per": 1000}
      ]
    },
    "USDC": {
      "dimensions": [
        {"key": "call_count",    "amount": 5, "per": 1},
        {"key": "output_tokens", "amount": 2, "per": 1000}
      ]
    }
  }
}
```

- `key` 必须是**可计费维度**（现有 `BILLABLE_DIMS`：call_count / page_count / char_count / input_tokens / output_tokens / audio_seconds / frame_count / net_out_bytes）。不可验证的维度不进分账——这条纪律不变。
- `per` 解决 token 类定价：上式 = 每 1000 output_tokens 收 1 分。
- 金额为**最小单位整数**（CNY 用分，USDC 用 10⁻⁶）。
- 多维度**叠加**计费：总金额 = Σ 各维度。
- **不声明币种 = 该币种不支持**；调用方指定不支持的币种 → 门禁拒绝并列出支持的币种（沿用现有 -32001 报错风格，把“你有什么、对方收什么、去补什么”一次说清）。

### 4.2 计价公式与取整（必须一次性定死，否则对账会漂）

```
金额 = round( Σ_dim  (用量_dim / per_dim) × amount_dim )
```

- 先按精确值累加，**最后一次性四舍五入**到最小单位（避免逐项取整的累积误差）。
- 结果不超过成交时冻结的预算上限（现有 `compute_amount` 的封顶逻辑保留）。
- 取整规则写进 PolicyRef，版本化——两年后被问“这笔为什么是这个数”，要能回放当时的规则。

### 4.3 单价快照（成交时冻结）
快照是三元组：**币种 + 计量维度 + 单价**，外加条款版本号。agent 事后改价无效（现有 card_hash + 合约价机制扩到币种维度即可）。

## 5. 数据模型改造

### 5.1 最硬的一处：把“分”从模型里拿掉

现状：`amount_fen` 在 **12 个文件、70 余处**出现（ap2 / custodian / deal / gateway / sdk / store / settlement / wallet…），`pay_charges`、`deals`、`deal_reports`、`statements`、`settlement_orders` 全用它。字段名叫“fen”，等于把人民币分写进了数据结构——多币种下这是硬伤。

迁移三阶段（**不要一次性改完**）：

| 阶段 | 动作 | 风险 |
|---|---|---|
| 1 | 加列 `currency`（默认 `CNY`）、`amount_minor`（= `amount_fen`）；写入双写，读取走旧列 | 零行为变化 |
| 2 | 读取切新列；旧列保留只读；所有新代码只用 `amount_minor + currency` | 需全量回归 |
| 3 | 停止写旧列，标记弃用，后续删除 | 低 |

每一步都要跑 154 单测 + 33 项冒烟。

### 5.2 各表增列

| 表 | 增列 | 说明 |
|---|---|---|
| `party_accounts` | 见 §3.2 | 媒介、币种、网络、地址、方向、指数 |
| `pay_charges` | `currency`、`amount_minor`、`unit_price_minor`、`dims`（计量快照 JSON） | 直付/x402 凭证支持多币种 |
| `deals` / `deal_reports` | `currency`、`amount_minor` | 对等账户按币种记账 |
| `statements` | `currency`、`total_minor` | 账单按币种出 |
| `settlement_orders` | `currency`、`amount_minor` | 分账指令带币种 |
| `tasks` | `currency` | 任务锁定币种（与计价币种一致，D2） |

### 5.3 流水：**先做聚合视图，不要新增表**

这是上一轮 P0 教训的直接应用——当时的问题是“四表各说各话、事实分裂”。流水如果再建一张表，就是第五份事实。

**决策：流水 = 对已有事实的只读聚合视图**（`v_account_ledger`）；结算的唯一事实来源是 `settlements` 表（`task_id` 主键 = 幂等键），两条记账路（积分 `a2n-task.submit` / 对等·直付·x402 `a2n-gateway.call.invoke`）都从 `record()` 进同一张表。头条三数是**笔数**，金额按币种分行（`by_currency`），绝不跨币种相加。等视图字段不够用时，再落实体表并明确它是投影而非新事实。

> 更正（2026-09-14）：结算自 9/12 收口——已结再报返回 `already=True`（不二次计数、不许事后改金额）；失败落 `mark_pending`（已结不许被降级）；`daily_cut` = 对账（积分总量 ≡ 托管余额）+ 当日三数 + 按天覆盖落 `reconciliations` + 报警，`A2N_CLOSING_INTERVAL_SEC` 默认 0 = 关。账本不变式（积分总量 ≡ 托管）仍然成立、不用改。裸中继 relay 成交无 task_id、无幂等键，不进这张表。

流水记录字段：

| 字段 | 说明 |
|---|---|
| `ts` | 发生时刻 |
| `account_id` | 本方账户 |
| `counterparty` | 对手方（主体或 agent） |
| `task_id` | 关联任务（可空：出账类无单笔任务） |
| `kind` | 应付产生 / 付款已发起 / 回执已确认 / 对账出账 / 账单已结 / 退款 |
| `dims` | 计量（如 call_count=1、output_tokens=820） |
| `amount_minor` + `currency` | 金额与币种 |
| `state` | 待结算 / 已结算 / 失败 |
| `ref_id` | 凭证或账单 id（点进去看全文） |

积分账户额外提供**余额**（A2N 持有事实）；外部媒介不提供余额，只显示待结算 / 已结算 / 流水。

## 6. 控制台设计

控制台信息架构已收敛为**三主入口 + 高级功能折叠**：三主入口是「找 Agent / 卖 Agent / 我的账户」；链 / 仲裁 / 共识 / AP2 / **结算与对账** 收进一个默认折叠的「高级功能」区（里面按「运营 / 审计·凭证」分组）。本设计 §6.1~§6.3 的账户相关改动集中在「我的账户」与「结算与对账」。

> 更正（2026-09-14）：原 9 页签（overview/provided/managed/discover/trade/chain/money/arbitration/consensus）已重排为三主入口 + 高级折叠；「结算与对账」成为独立高级页，对应 `settlements`/`reconciliations` 单一结算事实与 `daily_cut` 对账，运维面走 `/v1/ops/settlement*`（需带 `X-Principal`）。付费方式只作偏好筛选、不藏其它 agent；能不能调永远在服务端门禁 `gate.resolve`，绝不在 UI 一刀切。

### 6.1 我的账户 页 → 账户与流水（核心）

**账户区**（按媒介分组：稳定币 / 支付宝 / 积分），每张卡片显示：
- 账户标识（地址尾号 / 账号尾号 / 科目名）、币种、方向（收/付/双向）、默认标记、状态
- **待结算**、**本期已结**（A2N 有据可查的量）、流水条数
- 余额位：积分显示真实余额；稳定币/支付宝显示“外部账户，A2N 不掌握余额”

操作：绑定账户、解绑、设为该币种默认、编辑备注、查看流水。

**流水区**（选中账户后）：
- 表格：时间 / 对手方 / 技能 / 计量 / 金额（币种）/ 状态 / 凭证
- 筛选：时间区间、对手方、技能、币种、状态、方向（收/付）
- 操作：查看凭证全文（AP2 授权链 + 计量 + 快照）、导出 CSV、对有争议的记录发起仲裁（跳转 arbitration）

### 6.2 卖 Agent 页 → 收款设置
- **收款账户绑定**：按媒介/币种绑定（提示支付宝需商家资质、稳定币仅限海外线）
- **价目表编辑器**：技能 × 币种 × 计量维度 × 单价 × per，所见即所得，保存即生成新 card（card_hash 变更 → 重新验签/重新进试单）
- 展示当前单价快照被用在哪几笔成交里（防止改价引发争议）

### 6.3 我的账户 / 结算与对账 页 → 付款设置与对账
- **付款设置**：默认支付账户（按币种）、授权额度（单笔上限 / 周期上限 / 总上限，对应 AP2 intent）、授权有效期、自动付款开关
- **结算与对账**：头条三数为笔数，金额按币种分行（`by_currency`）、绝不跨币种相加；账单列表（按币种分组）、出账、标记已结、导出

### 6.4 一致性要求
所有涉及金额的位置必须显示币种与最小单位；所有“余额”必须区分“A2N 掌握”与“外部不可知”。**宁可显示“不可知”，也不要显示一个猜测值。**

## 7. 与自动结算执行器的衔接

承接上一轮的三执行器设计，本设计给它们补上币种维度：

| 执行器 | 媒介 | 本次新增职责 |
|---|---|---|
| 记账执行器 | 全部（对等账户模式） | 按币种出账（statement 带 currency） |
| 渠道执行器 | 稳定币 / 支付宝 | 按媒介选择执行方式：稳定币走 x402/钱包签名；支付宝走代扣协议号 |
| 托管执行器 | 积分（二期） | 账本内划转，可显示余额 |

渠道执行器的接口形状必须按“两者共性”定死（指令进、回执出、状态可查），真实实现等商户号/链上钱包就绪后接入，业务代码零改动。

## 9. 风险与开放问题

| 项 | 说明 | 处理 |
|---|---|---|
| 跨币种无法成交 | D1/D2 的代价：使用方必须持有 agent 声明的币种之一 | 门禁报错里列清币种与去哪补；后续若要做换算，必须持牌另起模块 |
| 稳定币退款 | 链上转账无强制退款，需对方配合 | 争议期内冻结未结金额；退款走人工/仲裁流程 |
| 支付宝商家资质 | 提供方需个体户或企业资质 | 产品侧引导；个人提供方只能走对等式记账（不出钱） |
| 积分来源未定 | D5 只做记账与流水 | 总量恒 0 校验；发行口子封闭，等持牌方确定再开 |
| 地域合规 | 稳定币境内不可用 | UI 按主体地域明示可用媒介 |
| 取整与多维度叠加 | 规则不定死会导致对账漂移 | §4.2 一次性定死 + PolicyRef 版本化 |

## 10. 一句话总结

**多币种不是加一列币种那么简单，而是把“分”这个写死在 70 处代码里的假设换成“最小单位 + 币种”。** 做完这一步，按币种定价、多账户、流水、以及上一轮的自持一对一自动结算，才真正落在同一个可结算的地基上——而平台自始至终不碰钱、不做汇率、不掌握外部余额。
