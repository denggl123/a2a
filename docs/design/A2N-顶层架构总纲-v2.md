# A2N 顶层架构总纲 v2.0 —— 自顶向下

> 项目代号 A2N（Agent-to-Node Network）
> 一句话定位：一个只做**行情、调度、验收、刻章**的 AI 算力与 Agent 服务网络，钱全程在持牌托管体系内流动，运营方零资金接触。
>
> 本文是**顶层视角**（Top-Down View）。它不重复已由其他文档覆盖的细节，而是回答一个问题：
> **从上往下看，这个系统到底分几层，每层对上一层承诺什么，对下一层要求什么。**

---

## §0 三层模型：一句话说清每层干什么

用户视角的项目是三件事：**A2A 服务、A2A 服务管理、A2A 服务结算**。
落到架构上是三层 + 一根轴：

```
┌──────────────────────────────────────────────────────────────────┐
│  L2 服务层  Service         A2A 服务本身：我能干什么、干得怎么样      │
│            能力声明 · 任务执行 · 多维计量 · 结果产出                 │
├──────────────────────────────────────────────────────────────────┤
│  L1 管理层  Management      让服务可被找到、被信任、被裁定            │
│            注册 · 发现 · 调度 · 验收 · 信誉 · KYA · 管理台           │
├──────────────────────────────────────────────────────────────────┤
│  L0 网络层  Network         让上面两层不需要中心服务器                │
│            身份 · 寻址 · 连通 · 传播 · 共识 · 账本同步               │
└──────────────────────────────────────────────────────────────────┘
        ↑                    ↑                    ↑
        └────────────── 结算轴 Settlement ────────┘
             事实(服务层) + 裁定(管理层) + 证据(网络层) = 一条结算指令
```

| 层 | 用户眼里的名字 | 回答的问题 | 失败时发生什么 |
|---|---|---|---|
| **L2 服务层** | A2A 服务 | 谁会干这个活，干成了什么样 | 任务失败，重试或换节点，钱不动 |
| **L1 管理层** | A2A 服务管理 | 怎么找到它、信不信得过、算不算数 | 搜不到/不派单/不结算，钱仍在冻结 |
| **L0 网络层** | 网络（底层） | 消息怎么到、账本怎么同步、谁做见证 | 降级到 pull 长轮询；账本停批，不丢不重 |

**方向决定性质**：下层不知道上层的存在。
网络层不知道自己在传的是任务还是心跳；管理层不知道自己在管的是 OCR 还是 GPU；
服务层不知道自己的凭证被谁见证。这是解耦能否成立的唯一判据。

## §1 一个必须先钉死的判断：结算不是一层，是一根贯穿的轴

用户把"服务、管理、结算"并列成三件事。前两件是**层**，第三件不是。

**理由：结算的每一次发生，都需要三层各交出一样东西，缺一样就不成立。**

| 层 | 交出 | 具体形态 | 单方持有时会发生什么 |
|---|---|---|---|
| **服务层** | **事实** | 计量 `dims`（调用数、token、时长…）+ 结果 hash | 节点自报自收 → 虚报无解 |
| **管理层** | **裁定** | 验收结论（通过/打回）+ 分账规则版本 `PolicyRef` | 裁判兼出纳 → 可单方决定分账比例 |
| **网络层** | **证据** | 账本 append-only 条目 + 凭证链 hash + 共识签名 | 账本只能记，不能判断"活算不算数" |
| **（层外）持牌方** | **资金动作** | 托管账户内部分账 / 打款到银行卡 | —— |

**所以：A2N 能生成结算指令，但永远不能单独完成结算。** 这就是"只刻章、不碰钱"在工程上的精确定义——不是一句口号，是三层职责切分后的必然结果。

任何试图把结算塞进单一层的重构，都会同时破坏廉洁性和中立性。这条应该写进架构纪律测试。

### 1.1 结算轴的三条不变式

```
INV-S1  没有事实就没有金额      —— 计量未上报 → 不结算（不是按预算结算）
INV-S2  没有裁定就不解冻        —— 验收未通过 → 冻结额退回，不进任何账户
INV-S3  没有证据就不算数        —— 凭证链未刻章 → 该笔在审计上不存在
```

对应到代码：三条都是**前置检查**，不是事后补救。现在的实现里 `compute_amount` 已保证 S1（无 dims 则 amount 兜底为 1 积分，这里有争议，见 §5.6）。

## §2 顶层：服务层（L2 · A2A Service）

### 2.1 服务层的唯一职责

**提供能力、执行任务、产出可计量的事实。**
它不做管理（不决定派给谁），不做结算（不决定分多少钱），不做网络（不管消息怎么到）。

一句话边界：**服务层只回答"我干了什么"，不回答"这值多少钱"。**

### 2.2 Agent Card：服务层对外的唯一契约

服务层与外界之间只有一份文档——**A2A Agent Card**。所有能力声明、计量维度、SLA 都在里面，SDK 不另发明一套（当初自研"能力发现"的设计已废弃，直接吃 A2A v1.0 + 扩展）。

```
card = {
  // ── A2A v1.0 原生字段（能用原生的绝不自造）──
  "name": "bob-ocr-01",
  "description": "高精度 OCR，支持中英混排",
  "url": "https://...",                    // 有公网入口才填；家宽留空 → 自动走 pull
  "version": "1.0.0",
  "capabilities": {"streaming": false, "pushNotifications": false},
  "authentication": {"schemes": ["bearer"]},
  "skills": [{
      "id": "ocr-pro",
      "name": "OCR Pro",
      "description": "...",
      "tags": ["ocr", "vision", "zh"],
      "inputModes": ["application/json"],
      "outputModes": ["application/json"],
      "examples": ["{\"image_url\": \"...\"}"]
  }],

  // ── x-a2n 扩展：只放 A2A 不管的 7 件事 ──
  "x-a2n": {
    "compute":   {"gpu": "4090", "vram": 24, "region": "cn-east-2", "slots": 4},
    "sla":       {"max_latency_ms": 5000, "availability": 0.95},
    "price_hint":{"ocr-pro": {"amount": 1, "unit": "call", "currency": "POINT"}},
    "metering":  {"dimensions": ["call_count", "output_tokens", "wall_time_ms"]},
    "settlement":{"account_ref": "..."},     // 打给谁：只存引用，不存账户
    "compliance":{"kya_grade": "C"},         // 分级会写进每个任务的凭证链
    "reputation_ref": "..."                  // 信誉不在卡片里，只存指针
  }
}
```

**七条扩展的选择标准**：A2A 原生能表达的（`skills`/`capabilities`/`authentication`）一律原生；只有 A2A 明确不管的才进 `x-a2n`。其中 **心跳是必须扩展的**——A2A 协议本身没有心跳语义，而网络层需要它判断节点死活。

### 2.3 三条服务层的红线（必须写进代码注释）

```
R-S1  price_hint 不参与排序
      一旦按提示价排序，注册表事实上就成了"报价排序器" → 铁律一（只发行情、不定价）当场破功。
      提示价只用于使用方做预算校验。真正的成交价 = 任务创建时锁定的合约价（unit_prices + card_hash 双锁）。

R-S2  节点不自我验收
      服务层可以上报"我干完了"，但通不通过由管理层判定。自报 ≠ 裁定。

R-S3  不可验证的维度不能进分账
      维度有三条性质：可计量 / 可验证 / 可复算。
      gpu_seconds 可计量但平台无法独立验证 → 只能做统计与信誉，不能单独收钱。
      BILLABLE_DIMS 白名单就是这个红线的代码形态。
```

### 2.4 任务状态机：对齐 A2A v1.0（**当前缺口**）

现状实现是自建状态机：

```python
STATE_FLOW = ["CREATED", "ASSIGNED", "SUBMITTED", "ACCEPTED", "SETTLED"]
```

问题：这套状态对外不可互操作。任何标准 A2A 客户端看不懂 `ASSIGNED`，也无法把 `completed` 映射回来。**服务层既然站在 A2A 上，状态机就必须说 A2A 的话。**

目标映射（内部状态 → A2A v1.0 状态）：

| A2N 内部 | A2A v1.0 | 含义 | 触发者 |
|---|---|---|---|
| `CREATED` | `submitted` | 已创建，等待派发 | 使用方 |
| `ASSIGNED` | `working` | 已派给节点，节点开始工作 | 管理层 |
| `RUNNING` | `working` | 执行中（可多次心跳上报） | 服务层 |
| `INPUT_REQUIRED` | `input-required` | 需要补充输入（多轮 agent 场景） | 服务层 |
| `SUBMITTED` | `completed`（待裁定） | 节点已交结果，等验收 | 服务层 |
| `ACCEPTED` | `completed` | 验收通过 | 管理层 |
| `REJECTED` | `failed` | 验收不通过 / 仲裁败诉 | 管理层 |
| `CANCELED` | `canceled` | 取消（使用方撤销 / 超时） | 使用方/管理层 |
| `SETTLED` | `completed` + `settlement_ref` | 已分账（A2A 无此语义，放 metadata） | 结算轴 |

**关键设计**：`SUBMITTED` 与 `ACCEPTED` 在 A2A 里都是 `completed`，区别只在 A2N 的内部裁定字段。
对标准 A2A 客户端而言任务已完成；对 A2N 而言钱还没动。**这个分歧是刻意的**——A2A 关心"活交没交"，A2N 关心"交的算不算数"。

### 2.5 多维计量：服务层产出的唯一"事实"

服务层最终只对外交出一样东西：**一条带签名的计量报告**。

```
{
  "usage_id": "us_xxx",
  "task_id":  "tk_xxx",
  "node_id":  "ag_xxx",
  "dims":     {"call_count": 1, "output_tokens": 812, "wall_time_ms": 1430},
  "result_hash": "sha256:...",
  "contract": {"unit_prices": {...}, "card_hash": "...", "budget": 100},
  "signature": "..."        // 节点私钥签，防事后抵赖
}
```

**双向计量对账（核心机制）**：

| 口径 | 谁测 | 性质 |
|---|---|---|
| 节点连署 | SDK `meter` + `a2n_p2p.attest.sign_metering`（交付边界随回包上行） | **可验证的内部真相**（平台用 `verify_metering` 验签；卡未声明 `x-a2n.sovereign.pub` 一律拒收） |
| 平台观测 | 管理层 `acceptance` | **外部真相**（wall clock、次数、结果结构校验） |

- 差异 ≤ 容差 → 按实结算
- 超容差 → 触发**第三方付费复算** → 仲裁 → 信誉扣分
- 系统性虚报 → 黑名单 + 扣未结算额

**谁的单方口径都不采信**——这就是"中立公证处"在工程上的具体形态。
复算本身也是一个任务，走同一套调度与分账流程：**用自己的市场监督自己的市场**，不另建监督系统。

> 已知实现细节：容差不能纯相对。本地瞬时任务自报 120ms、平台观测 ~0ms，纯 ±5% 必然误判为作弊。
> 现实现为 `max(自报 × 10%, 500ms)` 的绝对容差。

### 2.6 服务层的失败语义

| 失败 | 语义 | 后果 |
|---|---|---|
| 执行抛异常 | 任务失败，不是作恶 | 换节点重试，不扣信誉（只扣在线率） |
| 结果结构不合法 | 任务失败 | 不结算，预算解冻 |
| 计量虚报 | **作恶** | 复算 → 仲裁 → 信誉 + 可能黑名单 |
| 心跳断 | 失去派单资格 | 自动摘牌，不人工介入 |

**区分"做不好"和"使坏"**：前者是质量问题，后者是廉洁问题。两者处理方式必须不同，混为一谈会逼走诚实节点。

### 2.7 服务层：已实现 / 缺口

| 项 | 状态 |
|---|---|
| Agent Card（A2A 原生 + `x-a2n`） | ✅ 结构已定，自证验签已实现（`a2n_p2p.attest.verify_selfproof` + `a2n_registry.service.verify_card`，三态 `signed`/`unattested`/`invalid`+`tampered`） |
| 多维计量采集与上报 | ✅ `meter` + `usage_reports` 表 |
| 双向计量对账 | ✅ 容差 + 复算入口 |
| 预算冻结 + 按实结算 | ✅ `compute_amount` 且永不超过冻结额 |
| **A2A v1.0 状态机映射** | ❌ **缺口**：现状是自建 `ASSIGNED/SUBMITTED/...` |
| **Card 自证闸（`verify_card` 三态）** | ✅ 已实现（注册关口 `_guard_selfproof` 拒收验不过的卡；发现路 `assignable()` 跳过被拒收的卡） |
| **多轮任务 `input-required`** | ❌ 缺口：现状是单轮 |
| **流式输出 `streaming`** | ❌ 缺口 |

## §3 中层：管理层（L1 · Service Management）

### 3.1 管理 ≠ 控制

管理层**不拥有服务**，只维护秩序。它做的是四件事：**让服务可被找到、可被信任、可被裁定、可被审计**。

它不存储服务内容，不执行任务，不持有资金。

### 3.2 注册：节点自证，网络背书

```
节点自证（SDK 发 card，自己签名）
      ↓
注册表存：card_hash + 签名验证结果 + 索引 + 网络背书签名
      ↓
注册表 ≠ 权威，节点才是
```

**这个区分很重要**：将来有人质疑"你们是不是篡改了某节点的报价/能力"，掏出 `card_hash` 和签名就能自证清白。注册表存的是**关于卡片的元数据**，不是能力本身。

### 3.3 发现：按需拉取 + 本地列表（My Roster）

**发现模型（用户指定的模型，已实现）**：

| 主体 | 管什么 |
|---|---|
| 注册表 | 让发现**成为可能**（可搜索索引 + 背书签名） |
| 使用方 | **我发现了谁**（本地列表，平台不存） |
| 调度器 | **这一单能不能派**（派单前校验） |

**没有人同步全量目录。** 只有你去搜索时，才会发现别人注册的 agent；发现后它出现在你本地的市场列表里。注册只是"允许被发现"。

这个模型好在四处：

1. **扩展性**——读压力 ∝ 查询量，不是 节点数 × 使用方数，没有 fan-out 风暴
2. **中立性**——平台提供**搜索**，不提供**推荐**。搜索可以中性，推荐永远不中性
3. **隐私**——协作关系留在本地，平台无法构建画像、也就无法操纵分配
4. **容错**——注册表短暂不可用时，已加入列表的 agent 仍可调

> 第 2 条值得单独记住：**平台一旦掌握每个人的偏好列表，就能通过调整返回顺序影响成交与价格。不存，是最干净的隔离。**

**可见性等级**：

| 等级 | 含义 | 出现在搜索结果 |
|---|---|---|
| `public` | 全网可搜 | ✅ |
| `unlisted` | 知道 agent_id 就能调 | ❌ |
| `private` | 仅白名单 | ❌ |

`unlisted`/`private` 是"手动添加到我的列表"能成立的前提——产能有限或合规敏感的 agent 不必暴露给全网。

**四层可见性**（平台三层 + 本地一层）：

```
注册表条目  ← card 形状合规即入册；自称身份却验不过（`invalid`）或入库后被改（`tampered`）的卡在自证闸被拒收，不进「可直接调用」候选（「可直接调用」须同时满足「能付费」+「已自证」）
调度候选集  ← ACTIVE + 在线 + 过试单期（不满足）
行情板可见  ← 有真实成交统计（不满足）
我的列表    ← 使用方本地 SQLite/IndexedDB，平台不知道也不存
```

**刻意的克制**：凡是涉及真金白银的位置，都不允许"上线即出现"。

> 本地这一层很实用：平台给的是全网信誉分，而"最适合我"取决于我的场景——平台算不出来，也不该知道。

### 3.4 调度：发现自由，派单受控

你可以自由搜、自由选、指定 agent。但**派单那一刻**，调度器必查：

```
① 状态是否可派（ACTIVE / PROBATION）
② 是否在线（心跳 90s 内）
③ 是否在黑名单
④ card_hash 是否一致        ← 防能力被偷偷改弱
⑤ KYA 等级是否够            ← 合规分级传递
⑥ 并发上限是否满
⑦ 是否可达（传输层判定）      ← 不可达不派，预算不冻在永不执行的任务上
```

**发现是自由的，派单是受控的**——前者是信息，后者是钱，严格程度天然不同。

### 3.5 验收：双向计量对账

见 §2.5。管理层在这里的角色是**裁定者**，不是执行者。

自动验收（默认）：结构校验 + 计量对账 + 时延达标
人工验收（大单）：使用方 72h 内确认，超时视为通过
打回仲裁：凭凭证三联单（任务单 / 结果 hash / 评分）人工复核

### 3.6 信誉与 KYA

```
归一化信誉分 = f(验收通过率, 任务量, 在线率, 仲裁败诉数)
```

- 全网公开、按能力类别分列
- 冷启动新节点给"新签"标记 + 小额试单保护期
- 降级路径：连续失败 → 降权 → 摘牌
- 恶意行为 → 永久黑名单 + 扣除未结算额

**信誉是唯一可以进排序的第三方事实。** 发现时六维度都可查（D1 能力 / D2 资源 / D3 质量 / D4 合规 / D5 信誉 / D6 计量），但**排序只能用 D5**，因为只有它是第三方验证过的。

**KYA 分级**（对齐 2026-08 中国支付清算协会《智能体支付应用自律公约》）：

| 等级 | 单笔上限 | 说明 |
|---|---|---|
| A | 无限制 | 完成完整 KYC + 历史良好 |
| B | ≤ 1000 积分 | 基础实名 |
| C | ≤ 10 积分 | 新注册默认 |

`kya_grade` 会**写进每个任务的凭证链**，做全链路传递。

### 3.7 管理台：三个视图（用户的直接诉求）

管理台是一套 **Web 控制台**（平台侧 `console.html`）：主入口只有「找 Agent / 卖 Agent / 我的账户」三个，高级功能（结算与对账 / 链 / 仲裁 / 共识 / AP2）收进默认折叠区；Agent 明细抽屉分四段证据（客观表现 / 质量偏差 / 使用评价 / 案例）+ 试用徽标 + 毕业/阻塞按钮 + 单次交付打分，取数失败不翻成空态（用「加载失败…点刷新」）。

| 视图 | 回答 | 关键字段 |
|---|---|---|
| **发现 / 搜索** | 我想要的 agent 在哪 | 多维过滤（能力/资源/质量/合规）、信誉排序、加入我的列表 |
| **我提供的** | 我提供的 agent 怎么样 | 状态、KYA、信誉、能力、**计量（调用/时长/token）**、累计收益、可提现、**连接处境** |
| **我管理的 / 结算** | 我花的钱去哪了 | 我发起的任务（预算/实付/状态）、账本、凭证链、资金流水 |

## §4 底层：网络层（L0 · Network）

### 4.1 网络层要回答的四个问题

```
Q1 我是谁        → 身份与寻址（DID / 公钥 / 地址簿）
Q2 我怎么找到别人 → 对等发现（bootstrap / mDNS / DHT / gossip）
Q3 消息怎么到    → 传输阶梯（direct / holepunch / tunnel / relay / pull）
Q4 我们怎么共识  → 锚定共识 + 账本同步
```

### 4.2 身份与寻址

```
node_id  = "ag_" + 公钥指纹(前 12 字节 hex)
DID      = did:a2n:<node_id>
密钥对    ed25519（v1 原型期可用 HMAC 占位，生产必须换）
私钥      永不出本机；管理台与 SDK 共用同一份本地密钥库
```

**身份即地址**：不需要注册机构分配 ID，公钥自己就是身份。这让"注册"从"申请账号"降级为"广播一张签名的卡片"。

### 4.3 对等发现（a2n-p2p 已实现，见 §4.8；自持模式另见 `docs/SOVEREIGN.md` 的 a2n-node 包）

四种子机制，按网络环境自动选择：

| 机制 | 场景 | 说明 |
|---|---|---|
| **mDNS / 局域网广播** | 同一局域网 | 零配置，插上网线就能互相看见（最适合"办公室/家庭内网算力共享"） |
| **bootstrap 列表** | 冷启动 | 硬编码若干长期节点 + 用户提供；连上一个即可拉取更多 |
| **gossip 对等交换** | 常态 | 每次心跳附带若干已知对等，网络自行稠密化 |
| **DHT（Kademlia）** | 规模期 | 按 `skill_id` 做键路由，查询 O(log N) |

**演进建议**：v1 先做 mDNS + bootstrap + gossip（约 300 行即可跑通），DHT 留到节点数破千再加。过早引入 DHT 是经典的过度设计。

### 4.4 传输阶梯（**已实现**）

五级协商，ICE 思路——先列全候选，再选优：

| 通道 | 状态 | 原理 |
|---|---|---|
| `direct` | ✅ 可用 | 节点有公网 URL + 平台入站探测 |
| `holepunch` | ⚠️ 候选枚举 | STUN 反射候选（RFC 5389 标准库实现）；平台仲裁打洞未实现 |
| `tunnel` | ✅ 可用 | **反向长连接**：节点出站挂住，任务/调用实时推下来 |
| `relay` | ✅ 底层原语 | **对等账户中继**：对外只投影 `/v1/relay/{id}` 门牌号（真实地址仅给 owner）；它是 peer 账户的底层中继原语，使用端调用统一走 `POST /v1/invoke`（治理链），控制台不把它当入口 |
| `pull` | ✅ 兜底 | 长轮询，永远可用 |

```
SDK 用法：
  node.serve(tunnel=True)                     # 任务实时下发
  node.serve(local_agent=(9101, local_api))   # 本机服务可被公网调用，本机零暴露
```

**关于 P2P 穿透的三条不可妥协边界**：

1. **打洞只做候选，永不做依赖**——对称 NAT/CGNAT 成功率低，永不自动选中
2. **数据可以走直连，证据必须走平台**——结果 hash、计量、分账证据仍回平台刻章
3. **中继是唯一 100% 保证连通的通道**——业界约 8~20% 连接最终靠 TURN

> 已实现的工程教训（值得写进团队规范）：`relay` 路由曾是 `async def` 却同步等回包 15s，
> 事件循环被阻塞，全站长轮询一起超时。阻塞等待必须 `run_in_threadpool`。

### 4.5 消息协议（gossip 信封）

```
envelope = {
  "msg_id":   "...",          // 去重：每个节点缓存最近 N 条 msg_id
  "from":     "did:a2n:...",
  "ttl":      5,              // 每跳 -1，归零丢弃（防无限扩散）
  "type":     "CARD",
  "payload":  {...},
  "sig":      "..."           // ed25519 签名，伪造消息在第一跳就被丢
}
```

八类消息：

| 类型 | 用途 | 是否进账本 |
|---|---|---|
| `CARD` | 广播/更新 Agent Card | 是（card_hash） |
| `QUERY` | 按需发现请求（向邻居问"谁会 ocr"） | 否 |
| `OFFER` | 对 QUERY 的应答（我是候选，附背书签名） | 否 |
| `TASK` | 派单（含锁定合约价与 card_hash） | 是 |
| `RESULT` | 结果 + 计量报告（签名） | 是（hash） |
| `RECEIPT` | 凭证 | 是 |
| `EPOCH` | 批次 Merkle root 提议 | 是 |
| `ANCHOR` | 资金锚签名（epoch, balance, root） | 是 |

**去重 + TTL + 签名** 是 gossip 的三件套，缺一不可：没去重会广播风暴，没 TTL 会无限扩散，没签名会女巫污染。

### 4.6 共识：锚定共识（A2N 与公链最本质的区别）

**不需要最长链规则，也不需要烧电**，因为 A2N 有一个公链没有的东西：链外资金事实。

```
每个 epoch（如 10 分钟）：
  1. 收集该 epoch 所有账本条目 → 算 Merkle root
  2. 见证节点（≥2/3）对 (epoch, root) 签名
  3. 资金锚（持牌托管方）签 (epoch, balance, root)
  4. 与锚不一致的分支直接作废 —— 不需要比谁长
```

**铁律三的升级形态**：

> 增发不是"函数不存在"，而是**"没有任何单一方能凑齐增发所需的三把钥匙"**。
> 三把钥匙 = 节点签名 + 见证 2/3 + 资金锚签名。运营方一把都没有。

### 4.7 账本同步：SPV 轻客户端

**节点不需要下载全量账本。**

```
节点只存：自己账户的分支条目 + 每个 epoch 的 root（几十字节）
验证一笔：给出条目 + Merkle 路径 → 与 root 比对 → 5 毫秒
```

这直接回应了"每个人下载一个账本"的担心：账本涨到 100GB 只影响愿意全量存储的人，普通节点始终是轻量的。

配套三件事（按性价比排序）：
1. **Merkle 轻客户端证明**——自己证明自己被正确记账
2. **只读镜像 + 全量导出**——任何人可镜像、可重放、可对账；运营方改数据，镜像站当场打脸
3. **见证节点**——种子节点/合作方/监管方跑只读见证，一旦分叉，公信力立刻破产

> 一句话区别：**用分布式监督中心化，而不是用分布式替代中心化。**

### 4.8 网络层：已实现 / 缺口

| 项 | 状态 |
|---|---|
| 传输阶梯五级 | ✅ 已实现并端到端验证（中继 0.03s） |
| NAT 判定（平台替节点看） | ✅ 比对心跳来源 IP vs 自报本机 IP |
| 内网地址强制降级 pull | ✅ |

## §5 竖切面：结算轴（Settlement）

### 5.1 一次结算的完整证据链

```
服务层 计量报告（签名）         → "我干了这些活"
管理层 验收裁定 + PolicyRef     → "算数，按 v1 规则分"
网络层 账本条目 + 凭证链 + root  → "已刻章，可验证"
────────────────────────────────────────────
持牌方 资金动作                 → "钱动了"（层外）
```

缺任何一条，这条结算指令都不该被生成。

### 5.2 分账规则（可插拔 + 版本化）

```
默认：节点 90% / 样本作者 2% / 网络服务费 3% / 冷启动激励池 5%
```

**90/2/3/5 只是 `SplitRule` 的一个默认实现**，不是硬编码常量。

**规则版本化是必做项**：每笔结算单持久化 `PolicyRef(key, version, params)`。
没有版本化的规则等于没有规则——两年后监管问"这笔单为什么这么分"，答"现在规则是这样"是不合格的。

冷启动池资金来源：**运营方自筹真金白银充值**，不是增发。

### 5.3 提现与销毁

```
SDK 受理 → 冻结积分 + 风控（限额/T+1/异常拦截）
        → 指令发持牌方
        → 持牌方打款至实名绑定账户
        → 回执 → 积分销毁 → 凭证刻章
```

**出口只有提现一条**：不做代币、不上链记账、不设二级市场。
场外交易（闲鱼等）允许存在，但平台不运营、不推荐、零分润，并提供公开余额验证工具与"官方从不收购"声明。

### 5.4 积分记账单位

- **1 积分 = 0.01 元**，固定汇率，v1 不浮动
- 一律**整数存储**，永不出现浮点
- 仅充值 mint、仅提现 burn；网内流转只改归属不改总量
- **账本无余额字段**——余额由 `SUM(delta)` 得出。没有余额字段，就没有"改余额"这个动作

### 5.5 对账熔断（廉洁性的最后一道闸）

```
每日凌晨：全网积分总量 ≡ 托管 API 余额
差一分 → 冻结提现 + 告警
```

> 已验证：这条规则在上线第一天就抓到了一个真 bug——分账时只贷记了收款方、漏了从冻结账户借记，
> 导致使用方被退回全额、积分凭空多出来。**这正是"差一分即停"存在的意义。**

### 5.6 AP2 集成（分工与三个必需扩展）

**AP2 与 A2N 是上下层，不是竞争关系**：

| | AP2 | A2N |
|---|---|---|
| 场景 | 点对点消费（Agent 替人买东西） | 任务结算（调用 + 验收 + 多分账） |
| 关系 | 用户 ↔ 商户，**买卖关系** | 使用方 ↔ 节点 ↔ 样本作者，**协作关系** |
| 金额 | 由购物车**事先确定** | 由计量**事后确定** |
| 完成判据 | 发货即付款 | 验收通过才付款 |
| 收款方 | 单个 | **多个**（节点/作者/网络/池） |

```
AP2 授权 → A2N 判定 → AP2 结算
```

需向 AP2 提交三个扩展：

1. **Acceptance-Conditioned Mandate**——验收不通过就不付（AP2 原生的 Mandate 假设"发货即付款"）
2. **Split Settlement Mandate**——一笔授权 N 个收款方（AP2 原生是单一收款方）
3. **Metering Attestation**——可验证计量凭证（只有"可计量 + 可验证"的维度能进分账）

接 AP2 的附带收益：8 月公约要求的 KYA 与全链路追溯被顺手满足。

## §6 层间接口契约

**下层不知道上层，所以接口必须由上层定义、下层实现（Port 模式）。**

| 边界 | 契约 | 方向 |
|---|---|---|
| L2 → L1 | `RegistryPort.publish(card)` / `DiscoveryPort.query(require, filter, sort)` | 服务层调用管理层 |
| L1 → L2 | `ExecutorPort.execute(task) -> (result, dims)` | 管理层调用服务层 |
| L1 → L0 | `TransportPort.send(peer, envelope)` / `GossipPort.broadcast(type, payload)` | 管理层调用网络层 |
| L0 → L1 | 事件回调：`on_peer_joined` / `on_message(type, payload)` | 网络层通知管理层 |
| 任一 → 轴 | `LedgerPort.post(account, delta, ref_type, ref_id)` | 三层都能记账 |
| 轴 → 层外 | `CustodianPort.payout(account, amount, ref)` | 唯一出钱口 |

**依赖方向铁律**：`L2 → L1 → L0`，反向一律靠事件，不靠调用。

```
纪律（已有 CI 测试强制，tests/test_architecture.py）：
  D1 只能 import 自己 pyproject.toml 声明过的 a2n-* 包，未声明即失败
  D2 依赖图必须无环（函数级 import 也算环，只是躲到了运行时）
  D3 SDK 必须零第三方依赖
  D4 只有 a2n-custodian 允许出现资金系统字样
  D5 a2n-kernel 不许长出业务概念
```

> 迁移时真实抓到两处架构债：registry ↔ transport 环形依赖（改为依赖注入）、
> kernel 反向依赖 store 写 outbox（改为事件总线 `set_sink()` 由装配层接线）。

## §7 一次完整调用：从顶到底再回顶

```
使用方（管理台/SDK）
  │ ① 按需搜索：我要会 ocr 的节点
  ▼
L1 管理层  注册表索引 → 返回候选 + card_hash + 背书签名
  │ ② 本地验签、本地排序（按信誉）、加入我的列表
  ▼
L1 调度器  派单前七项校验（状态/在线/黑名单/card_hash/KYA/并发/可达）
  │ ③ 冻结预算，锁定合约价 + card_hash
  ▼
L0 网络层  传输协商 → tunnel 推送（不可达则降级 pull / relay）
  │ ④ 消息送达
  ▼
L2 服务层  SDK 执行 → 产出结果 + 计量报告（签名）
  │ ⑤ 回传
  ▼
L1 管理层  双向计量对账 → 验收裁定
  │ ⑥ 通过
  ▼
结算轴     服务层事实 + 管理层裁定 + 网络层证据 = 分账指令
  │ ⑦ 账本 append-only + 凭证链刻章
  ▼
层外持牌方 托管内部分账（钱从未离开托管）→ 节点提现时打款 + 积分销毁
```

**钱在整个过程中只在一个地方动过：使用方充值进托管，节点提现出托管。中间全是归属变更。**

**建议从 1 和 2 同时开始**——它们互不依赖，一个补最大的空白（网络层），一个修最实的缺口（服务层对外互操作）。

## 附：三铁律在三层的落点

| 铁律 | 服务层 | 管理层 | 网络层 | 结算轴 |
|---|---|---|---|---|
| **一、只发行情不定价** | price_hint 只是提示 | 排序只用信誉，不用价格 | 只传播不定价 | 成交价 = 锁定的合约价 |
| **二、只刻章不碰钱** | 只报事实 | 只出裁定 | 只出证据 | 只出指令，钱在层外 |
| **三、廉洁刻进代码** | 不可验证维度不进分账 | 规则版本化、平台不自营 | 无单一方能凑齐增发签名 | 无余额字段、append-only、对账差一分即停 |

**铁律四（新增）**：运营方永不自营 agent、永不自营节点、永不与客户争利。
原三铁律保证了廉洁，没保证中立。一旦自营，"既当裁判又当运动员"立刻复发——而中立是唯一能赢大厂商店的理由。
