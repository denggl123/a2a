# A2N 去中心化架构与 AP2 集成 v1

> 触发：你说"p2p 还是要的"、"参考区块链设计模式"、"我不希望有中心服务器"、"ap2 也要集成"。
> 这一版把"去中心"从口号拆成五个可判定的层，说清哪几层能去、哪一层不能、以及不能的那层怎么绕。

---

## 0. 三句话结论

1. **L1~L4（身份、发现、调度、账本）可以完全去掉中心服务器** —— 一层都不用留。
2. **L5（资金锚）去不掉"事实"，但能去掉"服务器"** —— 把持牌方从"平台"降级为"签名机"，它不参与调度、不认识节点、只按 epoch 对余额签名。
3. **AP2 管"授权与问责"，A2N 管"验收与分账"** —— 两者是上下层关系，不是竞争关系；A2N 需要向 AP2 提交三个扩展（验收条件、多方分账、计量凭证）。

---

## 1. "没有中心服务器"到底去掉哪一层

| 层 | 中心化现在做什么 | 能不能去 | 去了之后靠什么 |
|---|---|---|---|
| L1 身份与能力 | 注册表存 card | ✅ 能 | DID + 自签名 Agent Card（A2A 原生支持签名卡）|
| L2 发现与行情 | 中心搜索接口 | ✅ 能 | DHT / gossip 广播查询 + 本地索引与验签 |
| L3 调度与验收 | 中心派单、中心质检 | ✅ 能 | 请求方自选 + 随机抽签复算（复算者也是市场里的节点，质押担保）|
| L4 账本 | 中心库 + hash 链 | ✅ 能 | 区块链设计模式：批次 + Merkle + 见证签名（下一节）|
| L5 资金锚 | 持牌方托管账户 | ⚠️ 去不掉"事实" | 但可把机构降级为**只签名的预言机**，业务参与度 = 0 |

**结论：你可以没有中心服务器，但你不能没有"链外真相的入口"。**
比特币用算力把真相内化（你信最长链），A2N 不能这么干 —— 我们的真相是"托管账户里到底有多少钱"，它在链外。
所以 A2N 的共识不是 PoW/PoS，而是下一节的**锚定共识**。

## 2. 区块链设计模式在 A2N 的逐项映射

| 区块链概念 | A2N 对应物 | 说明 |
|---|---|---|
| 区块 | **Epoch Batch**（如每 1000 条账目或每 10 分钟）| 单条记账太碎，批量才有锚定意义 |
| 链 | 已有 `prev_hash` hash 链（v1 已实现）| 账目级链 + 批次级链，双层 |
| Merkle Tree | 批次内所有 entry 的 root | 节点不必下载全量账本 |
| SPV / 轻节点 | SDK 只拉"自己账户的分支 + root" | 100GB 账本不影响任何节点，只影响存全量的见证方 |
| 共识 | **锚定共识**（A2N 独创处，见下）| 不是算力、不是持币，是"资金锚签名 + 见证多数" |
| 出块者 | 轮值 Producer：信誉 + 质押排序，运营方不垄断 | 出块只提议，不决定 |
| 最终性 | 锚定签名发布后不可逆 | 未锚定的批次可被作废重提 |
| 分叉选择 | **以锚签名为准** | 与锚签名不一致的分支直接丢弃，无需最长链规则 |
| UTXO / 账户 | 账户模型，但**无余额字段**（`SUM(delta)`）| 比 UTXO 更适合多分账；没有余额字段就没有"改余额" |
| 智能合约 | 版本化策略插件（`SplitRule` / `AcceptancePolicy` / `RoutingPolicy`）| 每笔单持久化 `PolicyRef(key, version, params)` |
| 代币 | 积分：1 积分 = 0.01 元，**只在锚定事件上 mint/burn** | 不是可炒作代币：无二级市场、无转账投机、出口只有提现 |
| 预言机 | **资金锚**（持牌方 or 链上合约）| 唯一的链外输入，且只输出 `(epoch, balance, merkle_root)` 三元组签名 |

### 2.1 锚定共识（Anchor Consensus）—— 这是 A2N 与公链最本质的区别

```
每个 epoch：
  1. Producer 提议批次 B（entry 列表 + prev_root + merkle_root）
  2. 见证节点集合 W（N 个，含运营方、种子节点、合作方、监管方、持牌方）各自校验：
       - 链是否连续、hash 是否正确
       - 净额是否为 0（网内流转不增发）
       - mint/burn 是否对应已确认的充值/打款事件
  3. ≥ 2/3 见证签名 → 批次进入 ANCHORING
  4. 资金锚发布签名： Sig_anchor(epoch, escrow_balance, merkle_root)
  5. 校验 Sig_anchor.balance == 账本 SUM(delta)  →  锚定成功，批次最终化
    不一致 → 冻结提现 + 告警（"差一分即停"在共识层的形态）
```

三句话讲清它好在哪：

- **运营方无法单方面增发**：mint 需要"锚定事件 + 2/3 见证 + 锚签名"三把钥匙，任何一把都不在运营方手里。
- **托管方无法篡改业务**：它只输出余额签名，不认识节点、不参与调度、看不到谁在用谁。
- **不需要信任任何单一方，也不需要挖矿**：信任成本 = "N 个见证方里至少有 2/3 不串谋" + "托管余额真实"。

> 铁律三在去中心化后的表述升级为：
> **增发不是"函数不存在"，而是"没有任何单一方能凑齐增发所需的签名"。**
> 前者靠自律，后者靠密码学。

### 2.2 轻客户端证明（解决"每个人都要下载账本吗"）

你之前担心的"人人下载全量账本"在这里有答案：**不需要**。
节点只保存：自己账户相关的 entry + 每个 epoch 的 `merkle_root`（几十字节）。
要证明"我这笔收益确实被记账了"，只要提供：

```
(entry, merkle_path, epoch_root, 见证签名列表, 锚签名)
```

任何人（包括你自己的管理台）5 毫秒内可验证，不需要下载 100GB。
想存全量也可以 —— 那是"见证节点"的自愿选择，不是参与网络的前提。

## 3. P2P 网络层设计

| 要素 | 方案 |
|---|---|
| 节点身份 | DID（`did:key` 起步）+ A2A 签名 Agent Card，无需中心 CA |
| 能力传播 | Card 由节点自己签名发布，gossip 扩散（TTL=3），带 `card_hash` 与时间戳 |
| 发现索引 | DHT：`H(skill_id) → [card_cid...]` + `H(region)` 等次级索引 |
| 查询语义 | 广播 + TTL，结果由请求方本地聚合（排序只用信誉，不用 price_hint）|
| 本地 Roster | 搜索命中后加入本地列表，存 agent_id / card_hash / 私人标签 / **我侧本地观测** |
| NAT 穿透 | 复用 v1.2 传输阶梯：pull 长轮询 → 反向隧道 → 中继转发；holepunch 仅候选 |
| 种子节点 | 运营方跑的是 bootstrap seed，**它挂了网络照常工作**（地址硬编码多份 + DNS 多播）|
| 抗女巫 | 三合一：KYA 分级（B/C 级限流）+ 信誉 + 可选质押；不靠 PoW |

**关键承诺：平台不提供"推荐"，也不存储"谁在用谁"。**
搜索结果由你的本地节点自己算排序 —— 平台一旦掌握偏好图，就能通过排序影响成交与价格。
去中心化在这里不是技术洁癖，是**中立性的物理保证**。

## 4. AP2 集成：分工在哪、扩展在哪

### 4.1 分工（你说对了，这俩不是一回事）

| | AP2 | A2N |
|---|---|---|
| 场景 | 点对点**消费**：agent 替人买东西 | 任务**结算**：调用 + 验收 + 多方分账 |
| 关系假设 | 用户 ↔ 商户，买卖 | 请求方 ↔ 节点 ↔ 样本作者 ↔ 网络 |
| 金额来源 | 购物车（**确定**）| 计量 × 单价（**事后确定**，且必须验收）|
| 核心问题 | 这笔支付**有没有被授权** | 这笔活**算不算数**、钱**怎么分** |
| 付款条件 | 商户履约即付 | 验收分 ≥ 阈值 且 双向计量差 ≤ 容差 |

**所以：AP2 是前置的授权层，A2N 是后置的判定层。**
一笔 agent 经济交易 = `AP2 Mandate（授权）` → `A2N Acceptance（判定）` → `AP2 Settlement（结算执行）`。

### 4.2 概念映射

| AP2 概念 | A2N 映射 | 是否需要扩展 |
|---|---|---|
| Intent Mandate | **Task Mandate**：预算上限、能力要求、验收标准、计量维度 | ✅ 需加 `acceptance_criteria` / `metering_dims` |
| Cart Mandate | **Contract Snapshot**：锁定价 + `card_hash` + 单价表 | ✅ 金额是函数不是常数 |
| Payment Mandate | **Settlement Mandate** | ✅ AP2 单 payee，A2N 要 `splits[]` 多收款方 |
| Verifiable Credentials | KYA 等级证、信誉证、凭证链章 | ❌ 直接复用 W3C VC，不自建 |
| Roles | + **Verifier**（复算方）——AP2 没这个角色 | ✅ 新增 |

### 4.3 A2N 向 AP2 提交的三个扩展

**① Acceptance-Conditioned Mandate（验收条件化授权）**

```json
{
  "type": "a2n:AcceptanceCondition",
  "threshold": 0.95,
  "metering_tolerance": 0.05,
  "verifiers": { "count": 2, "selection": "random_staked" },
  "on_fail": "arbitrate",
  "evidence_ref": "sha256:..."
}
```
语义：**未通过验收，Payment Mandate 不生效。** AP2 原生做不到这点 —— 它假设"发货即付款"。

**② Split Settlement Mandate（多方分账授权）**

```json
{
  "type": "a2n:SplitSettlement",
  "splits": [
    {"role": "node",    "payee": "did:key:z6Mk...", "bps": 9000},
    {"role": "author",  "payee": "did:key:z6Mk...", "bps": 200},
    {"role": "network", "payee": "did:key:z6Mk...", "bps": 300},
    {"role": "pool",    "payee": "did:key:z6Mk...", "bps": 500}
  ],
  "policy_ref": {"key": "default_split", "version": 3}
}
```
语义：**一笔授权，多方结算，规则版本可追溯。**
两年后监管问"这笔单为什么这么分"，掏出 `policy_ref` 即可 —— 规则版本化在这里从"好习惯"变成"合规必需"。

**③ Metering Attestation（计量可验证凭证）**

```json
{
  "type": "a2n:MeteringAttestation",
  "dims": {"call_count": 12, "wall_time_ms": 8120, "output_tokens": 4096},
  "reported_by": "did:key:z6Mk...node",
  "observed_by": "did:key:z6Mk...platform",
  "variance": 0.02,
  "billable_only": ["call_count", "output_tokens"]
}
```
语义：**只有"可计量 + 可验证"的维度能进分账**（`gpu_seconds` 只能统计与信誉，不能单独收钱）。
这条规则从我们 v1 的设计直接搬进 AP2 的凭证体系。

### 4.4 与 KYA / 公约的关系

AP2 的 mandate + VC 体系，正好是《智能体支付应用自律公约》要的"身份识别 + 分级 + 全链路可追溯"。
**接 AP2 = 顺手合规**，不是额外工作量。KYA 等级写进每个 mandate，全链路自动带上。

## 5. 管理台在 P2P 下是什么

它不再是一个"网站"，而是**你本地节点自带的应用**（v1.2 已做成 SDK 内嵌，方向正确）：

| 功能 | 在 P2P 下怎么实现 |
|---|---|
| 搜索想要的 agent | 本地向网络发查询 → 结果本地聚合排序 → **本地验签**（card 签名 / KYA 证 / 信誉证）|
| 管理我提供的 agent | 本地 keystore 持有私钥：发布/更新 card、上下线、调价格提示、看收益、提现 |
| 看到全网行情 | 订阅公开 epoch root 与各见证方发布的统计（只读，无人能改）|
| 我侧观测 | 只存本地，永不上传 —— 平台算不出"谁最适合我"，也不该知道 |

管理中心化的部分只剩两处，且都不在你手里也不在我手里：
**资金锚**（持牌方/链上合约）和**见证集合**（N 个独立机构）。

## 6. 包的演进：新增 4 个包，server 降级

当前 16 包（已交付）基础上：

| 新包 | 职责 | 依赖 |
|---|---|---|
| `a2n-p2p` | DID 身份、card gossip、DHT 索引、查询路由、seed bootstrap | kernel |
| `a2n-consensus` | Epoch 批次、Merkle、见证签名、锚定校验、分叉作废 | kernel, ledger |
| `a2n-ap2` | Mandate 模型（W3C VC）、签发/校验、三个 A2N 扩展 | kernel |
| `a2n-index` | 本地只读索引 + Roster + 我侧观测（SQLite / IndexedDB）| kernel, p2p |

**`a2n-server` 从"中心服务"降级为"一个方便的对等节点"**：提供 bootstrap、行情镜像、HTTP 网关。
它下线，网络照常运行 —— 这是"没有中心服务器"的可验收定义。

依赖方向铁律依旧：`interface → application → domain → kernel`，且由 `tests/test_architecture.py` 机器校验（已实现：未声明的 import 直接判失败）。

## 7. 路线图（每阶段都有可验收的"去掉了什么"）

| 阶段 | 目标 | 验收标准 |
|---|---|---|
| **S1 账本区块链化** | 批次 + Merkle + 见证签名 + 锚定校验 | 三个见证方中任意 1 个作恶不影响最终性；轻客户端证明可验证 |
| **S2 发现 P2P 化** | card 走 gossip + DHT 查询 | 关掉中心 server，两个本地节点仍能互相发现并成交 |
| **S3 验收去中心化** | 复算节点市场：随机抽签 + 质押 | 无人复算时系统退化为自动验收，不阻塞 |
| **S4 结算去信任化** | 锚定升级为链上合约或多机构联盟见证 | 运营方完全退出签名集合，仍能正常运行 |

> 更正（2026-09-14）：S2 设想的"关掉中心 server、两节点互发现成交"已由第 23 包 `a2n-node`（自持模式）落地——无发行方（无托管⇒无积分增发⇒无账本需一致）、无中心账本（两方互签各存一份）、无全局目录，平台侧零改动。详见 `docs/SOVEREIGN.md`。其余 S1/S3/S4 仍按路线图推进。

## 8. 唯一需要你现在拍板的事：资金锚走哪条路

| | 路径 A：人民币持牌托管 | 路径 B：链上资产（稳定币/存款凭证）|
|---|---|---|
| 合规 | ✅ 完全合规，8 月公约明确要求核心环节持牌 | ⚠️ 国内高风险，出海场景可行 |
| 去信任程度 | 中：需信"N 个见证方 2/3 不串谋" | 高：合约即锚，无人可篡改 |
| 用户门槛 | 低：扫码充值、提现到卡 | 高：钱包、助记词、 Gas |
| 落地速度 | 快（v1 已留 MockCustodian 接口）| 慢 |
| 我的建议 | **先走 A，账本层按 B 设计** | 账本不绑定锚，随时可切 |

**推荐：双轨可插拔。** 账本与共识完全不关心锚是银行还是合约，只认 `Sig_anchor(epoch, balance, root)` 这一个接口。
今天合规跑人民币，明天环境变了换签名方即可 —— 这也是 v1 "CustodianPort" 那个抽象存在的真正理由。

## 9. 一句话收尾

比特币解决的问题是"在互不信任的人之间，就'谁有多少钱'达成一致"。
A2N 要解决的问题是"在互不信任的人之间，就'谁干的活算数、钱该怎么分'达成一致"——**而钱的真假由锚说了算，不由共识说了算。**

所以 A2N 不是"一条链"，是**一条以链外真相为最终裁判的链**。
它继承了区块链的全部可验证性，却不需要靠烧电来制造信任。
