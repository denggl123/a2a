# 六条诉求 · 代码对齐

对 A2N 现有代码逐条核实，并给出第 5、6 条新机制的定义与必须定死的问题。
每条都标了 `文件:行号`，便于复核。

---

## 一、网络层是否支持 agent 发现 —— **支持，但有两条互不同源的路**

| 项 | 现状 |
|---|---|
| 按能力发现 | ✅ `a2n_p2p/node.py:188` `query(skill)` 发 QUERY，应答方按 `skills` 匹配（`node.py:159`） |
| 多跳 | ✅ QUERY `ttl=2`（`node.py:195`），`ttl>1` 转发（`node.py:305`） |
| 消息可信 | ✅ 签名 + 去重 + TTL clamp（`envelope.py`） |
| 发现结果落点 | ⚠️ 默认只在内存 `PeerTable`（`peers.py:42`，技能索引 `peers.py:87`）；落表只有一条路：`wiring.py:256` `p2p_discover_to_roster` → `rosters` 表 |
| 平台注册表那条路 | ⚠️ **独立第二条**：`POST /v1/discovery/query`（`routers/registry.py:210`）→ `dispatch/service.py:60` 查 SQLite `skills/agents` |

**要指出的三个缺口**：
1. 两条路（p2p 发现 vs 平台注册表）**互不同源**，唯一交汇是 `rosters` 表，而且只有 p2p 侧往里写 ——
   这与之前定的"每张表只有一个写入方"纪律不冲突，但**"谁能被看见"的答案取决于你走哪条路**，
   这正是"事实分裂"的同类风险。
2. **发现 ≠ 可用**：平台这条路发现完就直接派单，没有"取对方的卡、验卡、核对哈希"这一步；
   自持模式里有（`a2n_node/node.py:196` `find()` 四步），平台路里没有。**平台路缺一道"卡片自证"的闸。**
3. 发现结果不落库（自持侧 `a2n_node/node.py:192` 只返回 offers），所以"我昨天发现过谁"无处可查。

## 二、服务层是否支持 agent 调用 —— **支持，但有一处旁路**

| 入口 | 落点 | 是否过治理链 |
|---|---|---|
| `POST /v1/invoke` | `routers/invoke.py:39` → `gateway/call.py:70` | ✅ |
| A2A JSON-RPC | `routers/a2a.py:81` → `_message_send`（`a2a.py:145`）→ 同一个 `invoke` | ✅ |
| relay（裸中继） | `routers/transport.py:92` | ❌ **旁路**：只验 `call_token`（`transport.py:115`），只对 `peer_account` 记账（`transport.py:142`），**不过门禁、不支持直付/x402** |

- 治理链共用：`gate.resolve`（`gate.py:85`）+ `tasks.create/submit` + `settle.dispatch`（`call.py:89-136`）
- 同步：`hub.forward` 阻塞等回包，超时 15s（`hub.py:122`）
- **无重试**；失败有回执（relay 超时 504 `transport.py:128`；通道失败 `tasks.fail` `call.py:107`；验收不过 REJECTED `task/service.py:271`）

**缺口**：relay 这条旁路是"服务层支持调用"的一个洞 —— 它绕开治理链，我之前的记忆里把这条
定义为"仅对等账户的裸中继原语"，**但它目前对使用端是可达的**，需要一刀切干净（要么收进治理链，要么对它不可见）。

## 三、结算是否支持自动结算 —— **不是"自动"，是"提交那一次顺手结"**

| 项 | 现状 |
|---|---|
| 触发方式 | ⚠️ `tasks.submit` 内**同步**调 `settlement.settle`，且仅 `settle=True`（积分）时（`task/service.py:277`） |
| 事件驱动 | ❌ **没有**。wiring 只订阅 `acceptance.failed` / `arbitration.resolved` / `node.suspended` / `epoch.anchored`（`wiring.py:84,112,124,159`）——**没有订阅 `acceptance.passed`** |
| 非积分路径 | 由 dispatch 在调用链尾记账（`call.py:135`），与积分路径**不是同一个触发点** |
| 同事务 | ✅ `settle(commit=False)` 与转 SETTLED 同一 `tx()`（`service.py:246`）——钱与终态同生共死，这是优点 |
| 分账 | ✅ 默认 node 90 / author 2 / fee 3 / pool 5，余数补 node（`a2n_kernel/policy.py:10,27`），规则带版本可重放 |
| 对账 | ⚠️ `settlement/reconcile.py:23` 比对积分总量与托管余额，但**只能手动调** `GET /v1/ops/reconcile`（`public.py:81`）；**全仓无定时任务**（无 scheduler/cron） |

**结论**：说"支持自动结算"目前站不住。准确说法是——
**验收通过 → 同一个事务里就结了**（这条是真的，而且做得比大多数系统严），
但**触发面不完整、没有事件驱动的自动结算、没有定时对账、没有任何后台 daemon**。
"自动"目前依赖"有人发起那次调用"。

## 四、硬指标评估系统是否完善 —— **测量有了，评估系统没有**

**已有的质量事实（四类，来源不同）**：

| 来源 | 是什么 | 落点 |
|---|---|---|
| 平台探测 | 入站可达性 / `rtt_ms` | `registry/reachability.py:101` |
| 服务端自报 | `wall_time_ms` / `ttft`（**仅 owner 可见，业务面被剔除**） | `sdk/runner.py:130` → `registry.py:231`，剔除 `registry.py:97` |
| 调用方实测 | 端到端往返（"端到端只有调用方测得到"） | `POST /registry/agents/{id}/observations`（`registry.py:197`） |
| 验收策略 | 双向计量对账（±10%/500ms 容差）、SLA 时延、`score` 只作内部分级（1.0/0.4） | `acceptance/service.py:16-52` |

**已有的"谁可进钱"的硬闸门（这是全项目最接近硬指标系统的地方）**：
`a2n_settlement/dims.py` —— 维度注册表，**可计量 + 可验证才允许计费**，
`gpu_seconds` / `cpu_seconds` / `vram_peak_gb` / `wall_time_ms` 只能进统计与信誉，永远不能变成钱。

**没有的（四条）**：
1. ❌ **没有"使用方给供应方打分"这个动作**：无评分 API、无评分表 —— scheme 25 张表全查过，无 `rating`/`review`；全仓 `rating|review|stars` 零命中。
2. ❌ **没有多维聚合总分**：`a2n_reputation` 只有"事件 → 权重增减"的标量（`reputation/service.py:17-42`，[0,1] 区间），不区分能力、不区分维度。
3. ❌ **没有反向信誉**（供方给需方打分），信誉只挂 `agents.agent_id`。
4. ❌ **没有"限时免费 / 试用额度"的任何痕迹**：`trial|quota|free_calls` 零命中；`free` 只表示"卡上没标价 = 免费"（`price.py:103`），不是促销额度。

**一个必须点出的硬伤**：`usage_reports.signature` 恒为 `"mock-signature"`（`task/service.py:260`）——
计量上报是**没有签名的**。所以现在"可验证"的真实含义是"平台自己观测 vs 节点自报的比对"，
**不是"带签名的可复算证据"**。硬指标要对外当质量事实，这一处必须先补。

## 五、新 agent 前 10 次免费（重连后前 5 次）+ 详情含这 10 次案例与评分

### 我的理解

这是一笔**双向交易**：对新摊主，平台用"免费"换"证据"。
新 agent 没有历史，所以详情页**不给分数，给案例** —— 前 10 次调用的原始材料
（谁调的、输入输出摘要、耗时、对方签收没有、以及打分）公开挂在详情页，
让使用端"看案例而不是看分数"来真实评估质量。

"重连后前 5 次免费"我理解为**额度重置**：网络中断/节点重启后，该 agent 的免费额度
重置为一个更小的数（5 次），目的是**重连后还能被人试**，不至于"一回来就收费，没人愿意再试"。

### 数据基础（不需要新造事实）

案例所需材料**现有事实里全都有**：`tasks`（状态/耗时/金额）+ `usage_reports`（计量与对账）
+ `receipts`（凭证链）+ `notary.for_task`（流程时间线），并且已有只读端点
`GET /v1/console/calls/{id}` 返回 `timeline`。**案例是既有事实的投影，不是第二份真相。**

### 必须先定死的四件事（否则一上线就被滥用）

1. **"10 次"按谁计 —— 我强烈建议按"10 个不同的使用者各一次"，而不是"任意 10 次"。**
   理由有两个，都很硬：① 按"任意 10 次"计，一个大客户能把额度全吃掉，**10 个案例来自同一个人，
   等于没有案例**；② 按"10 个不同使用者"计，**天然堵死同源自刷**（自己开小号刷不满 10 个人）。
2. **重启即重置 = 无限免费。** 必须给重置上约束：按**同一 agent 身份**（同一把钥匙）限次数、
   限时间窗（例如 24 小时内不重复重置），并设**生命周期累计上限**。
3. **免费换公开，必须在调用前告知使用者原话。**
   "这次免费，代价是这次交互会作为公开案例展示（内容可脱敏，你可以选择不上传）"——
   不能一边发补贴一边悄悄披露用户数据。**这是底线，不是选项。**
4. **免费单必须打标，否则会污染全局统计。**
   免费调用天然落在 `ACCEPTED`（非积分完成）而不是 `SETTLED`，于是 `a2n_market` 的
   `success_rate = done/total`（`market/service.py:45,151`）会被免费单**抬高**，
   而 GMV 只计积分（`market/service.py:31`）不受影响 —— 结果是"成功率虚高、GMV 不动"。
   **必须给免费单打 `trial=true`，并从"付费成功率"里剔除，或分开呈现。**

## 六、使用端评分归一化

### 先把公式对出来（用你给的三个数字反推）

你的例子：平均 80 分 → 拉到 50；下次 80 → 50；90 → 75；40 → 25。

这三个点**只有一种两段折线能同时满足**：锚点把 `μ`（该评分者自己的平均分）映到 50，
同时保留 `0 → 0`、`100 → 100` 两个不动点：

```
f(x) = x · 50/μ                    (x ≤ μ)
f(x) = 50 + (x − μ) · 50/(100 − μ)  (x > μ)
```

代入 μ=80：f(80)=50 ✓　f(90)=50+10×2.5=75 ✓　f(40)=40×0.625=25 ✓ —— **三个数字全对上**，
所以我认为这就是你要的那条曲线。

### 它的用意（我认同的部分）

**消除"手松 / 手紧"的评分者偏差**：归一化后 `50 分 = 这个评分者眼里的中性`，
于是不同人打的分数才第一次可比。这是对的，也是通行做法。

### 但有四处必须改（否则会反噬）

1. **锚点必须是他"给所有人的平均"，不能是"他给这一家的平均"。**
   若是后者，这家供应商**永远被拉回 50**，做得多好都涨不上去 —— 等于判无期徒刑。
   这一点不澄清，第 6 条会把整个评估系统变成"谁也涨不了分"。
2. **它消掉了"刻度位置"偏差，却放大了"刻度宽度"偏差。**
   μ=80 时上方斜率 2.5、下方 0.625：同样是"超出预期 10 分"，**手松的人给 75，手紧的人只给 58**
   —— 越手松越能把人推高，与直觉相反。μ=90 时上方斜率是 5，"手松者的略高分"几乎成了加分武器。
   建议二选一：**给两端斜率设上下限**（改动小）；或**先减均值、再除以他自己的标准差**
   （z-score 型，同时消掉位置与宽度两种偏差，更正确）。
3. **μ 早期极不稳定，而且会退化。** 第一次评分时 μ 就等于那一次的分（输出恒为 50，零信息）；
   只评过一家时 μ 就是那一家的分。建议加**收缩**：`μ_用 = (n·μ + k·50)/(n+k)`，
   样本不足时把 μ 往 50 拉。另外 `μ=0` 会爆炸、`μ=100` 会除零，**必须有边界**。
4. **归一化只能校正"人打的软分"，校正不了"事实的质量"。** 所以第 4 和第 6 条要合起来定一条总纪律：

   > **硬指标（谁测的、什么口径）直接对外，不做任何归一化；软评分归一化后对外；
   > 两者分开呈现，绝不合成一个总分。**

   合成一个总分等于把"平台探测的 200ms"和"某人心情好给的 90 分"搅在一起，
   出来的数字不可解释，也就不可验证 —— 这违反产品最核心的承诺。

### "前 20 次不传给供应商"这半句，需要你确认是哪个 20

它可能指两个完全不同的数，含义差很远：

- **评分者的 20 次**：他需要 ≥20 次评分才能建立稳定的 μ（供归一化用）；
- **供应商收到的 20 次**：它需要 ≥20 个**去重评分者**才对外公布分数，在那之前只公布案例。

我的建议是**两个都要，并且分工明确**：评分者满 20 次之前，他的评分只进本地校准池、
不对外发布；供应商满 20 个去重评分者之前，详情页只给案例、不给分数
（这与第 5 条"新 agent 用案例代替分数"正好接上：**案例先行，分数后到**）。

### 还有一个必须防的洞

归一化后的分数必须**带上样本数与去重后的评分者数**。否则"3 个人评的 88 分"和
"300 个人评的 88 分"长得一样，而这两件事的可信度完全不是一回事。
