# 服务积分支付模块

2026-10-08。实现：供应方服务发行、主动加分、欠账与还账、接受表、最多三跳兑换、三方循环、整体提交与恢复、双方约定的原积分退款。实际部署与验证记录见 [交付记录](../artifacts/POINTS-DELIVERY-2026-10-08.md)。

## 1. 分层

```text
业务：TradeService / CallService / TrialBook / ContractBook / TradeFactsBook
  免费样品 → 直接调用、公开脱敏样品；没有结算订单
  普通服务 → 明确结算意图、固定条件、实际执行与交付凭据
    ↓
支付协调：PaymentCoordinator / PaymentBook / PointsCoordinator
  共同能力、方法选择、固定计划、预留、决定、核对与恢复
    ↓ 通过端口调用独立方法
原生币 EvmNativeDriver | x402 驱动 | PointsBook / PointsNode
```

`PointsBook` 为零依赖 SDK 模块；身份签名与网络由节点注入。它不读取样品或试用计数，不判断免费资格，不调用 Agent，不访问原生币或 x402 的余额。`PointsNode` 只翻译积分协议与签名请求；`PointsPayment` 编排协议；`TradeService` 决定接单和执行。

原 `/v1/payment-coordination/quote`、`free-execute`、`prepare`、`plans/...` 保留为兼容入口，交给同一业务服务，不形成第二套规则。控制台使用 `/v1/trades/...`。样品报价由业务服务签发，保存到 `business_free_offers`，不进入支付协调的报价、订单、预留与结算状态机。

## 2. 账户与分录

账户键为 `(issuer_did, holder_did)`。每个发行方只维护自己发行的积分账本；持有其他发行方积分时向对应发行方取得签名余额，不把它们相加成一个全局余额。

| 模式 | 真实交付后的分录 | 使用方付出 |
|---|---|---|
| 前十次样品 | 无任何结算分录 | 无；强制公开脱敏样品 |
| EARN | 供应方持有的供应方积分增加约定数量 | 无支付、无欠账 |
| DEBT | 供应方持有的供应方积分增加；使用方对供应方欠账增加 | 双方明确接受的欠账，受供应方额度限制 |
| PAY | 按接受的路径转移已有积分，不额外发行供应方积分 | 选定发行方的原积分，整数成本上限 |
| 主动加分 ISSUE | 新发行供应方积分到指定使用方 | 双方线下约定；平台不收款 |
| 主动加分 TRANSFER | 供应方存量减少，使用方持有的供应方积分增加 | 明确的存量转移 |
| 还账 | 使用方持有的供应方积分转给供应方，等量减少原欠账 | 不能重复还账或超额抵消 |

已有积分支付选择“仅转移”以避免重复计入服务价值；主动加分明确区分新发行和存量转移。这是本次实现采用的具体规则，不把尚未确定的分录隐含在一个按钮里。

供应方可按 Agent 设置启用状态、单次积分数量、允许模式和每位使用方欠账上限，也可停止新发行。停止发行不会清空已有积分或原交易；已取得各方确认的交易继续按原条件恢复。

## 3. 接受表与寻路

接受表默认空。节点自行决定接受哪些发行方、比例、单笔上限、每天接收上限和最多持有量。比例 `numerator / denominator` 表示每单位对方积分认可为多少自家积分价值。中间节点用自己持有的自家积分交换收到的、自己认可的其他发行方积分。

寻路最多三条转移边，最多查询 64 个明确连接的积分节点。先选择一个付款发行方，在该发行方的单位内比较总成本；不将不同发行方的原始数量直接比较成“统一价格”。从目标服务价倒算，逐跳向上取整；同成本优先少跳，再按节点 ID 排序。没有路径、余额不足或对方不接受时说明原因，不执行服务，不扣积分。

每条计划固定发行方、持有方、金额、原业务任务、输入摘要、服务版本、各方签名和路由。新价格与接受表用于新交易；已经准备的原计划不被新设置改写。接受条件变化不自动改变已有积分数量。

## 4. 整体提交与恢复

1. 发起节点持久化自己的签名计划。参与方包括业务双方、各积分发行方和被借记或贷记的持有方。
2. 各方先确认条件。任何第三方的余额借记，必须有该持有方签名；自动兑换只能在其接受表和足额换入条件内发生。
3. 各发行方核对完整确认集合，预留原余额或欠账额度，持久化并签名准备凭据。预留不改变余额。
4. 服务交易由业务模块执行一次并取得供应方签名的真实交付凭据。EARN / DEBT 发行必须绑定这份原交付。兑换或还账交易没有 Agent 执行步骤。
5. 发起节点先持久化唯一的整体 COMMIT / ABORT 决定，再发送给所有参与方。COMMIT 包含完整准备凭据集合及服务交付凭据。
6. 各方按同一个计划 ID 幂等应用分录并回签收据。收据齐全后显示 CONFIRMED / FAILED；未齐全时保留 COMMITTING / ABORTING。

断线不会自动释放未知预留，不允许把已完成的跳永久保留而作废其他跳。每个节点重启后保留原计划、准备、决定与分录。后台每 30 秒进行有界恢复：参与方查询原发起节点的决定，发起节点补送原决定。控制台可立即核对原结算。

交付结果丢失时，业务恢复接口读取原私有交付并核验原签名、结果摘要和接单合同，不再次提交 Agent。确实未接单的原请求，供应方先在同一存储事务下保存禁止迟到执行的标记，再给出取消凭据，随后整体中止。结果仍未知时继续等待。

网络分区可能暂时阻塞完成；协议要求各方遵守签名账本和唯一决定。积分价值仍由对方对供应方履约的认可决定，系统没有全网积分共识或全局汇率。

## 5. 退款

已有积分支付的退款使用双方签名接受的现有异议方案，退还供应方原来实际收到的发行方积分。不能把“服务标价积分”当成多跳后实际收到的另一种积分，不能超过原收到数量，也不能重复执行同一方案。

退款通过新的、整体提交的逆向转移完成，不倒改原交付或质量评价。EARN 没有使用方付款；DEBT 的补偿可通过供应方明确加分与使用方还账处理，不伪造一笔已发生的付款退款。

## 6. 本机 API

以下入口沿用管理令牌、Host 与 Origin 保护。金额支持十进制整数字符串；账本使用最小单位整数，展示提供字符串金额，避免浏览器精度丢失。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/v1/points` | 本发行方余额、预留、欠账、服务策略、接受表、已知节点及结算记录 |
| POST | `/v1/points/configure` | 停发与本机实验传输设置 |
| POST | `/v1/points/services` | 指定 Agent 的模式、数量、欠账上限；要求策略版本 |
| POST | `/v1/points/peers` | 核对签名发行方身份并连接明确地址 |
| POST | `/v1/points/acceptance` | 发行方接受条件；要求策略版本 |
| POST | `/v1/points/grants` | ISSUE / TRANSFER 主动加分；要求命令 ID |
| POST | `/v1/points/holdings` | 向各发行方核对当前使用方自己的签名余额 |
| POST | `/v1/points/swap` | 两方或三方签名积分互换；要求命令 ID |
| POST | `/v1/points/repay` | 用原发行方积分还原欠账；要求命令 ID |
| POST | `/v1/points/orders/{id}/reconcile` | 补齐原决定和收据 |
| POST | `/v1/points/orders/{id}/cancel` | 未执行、未整体提交时明确中止 |
| POST | `/v1/points/recover-participants` | 参与方核对原发起节点的决定 |
| POST | `/v1/points/refund`、`refund-reconcile` | 执行或核对双方已接受的原积分退款 |
| POST | `/v1/trades/quote` | 业务资格与服务条件；样品优先绕过结算 |
| POST | `/v1/trades/free-execute` | 免费业务调用 |
| POST | `/v1/trades/prepare` | 明确选择 EARN / DEBT / PAY 或其他支付方法 |
| POST | `/v1/trades/plans/{id}/execute`、`reconcile` | 调用或恢复原业务，不重跑已执行的 Agent |

积分协议为 POST `/public/v1/points/{catalog,balance,consent,prepare,apply,status,decision}`。目录只返回本节点签名能力与接受条件；余额只向持有方自己的签名请求返回。所有交易操作绑定作者、目标、操作、请求摘要和有效期。公共反代只开放上述明确端点，不开放本机管理 API。

默认支付私有传输要求 HTTPS。本机 Docker 实验可由节点所有者明确开启 HTTP；该选择不改变账本、签名或业务规则。

积分现在也可经[私有结算协调通道](SETTLEMENT-TRANSPORT.md)发送。已验签的发现邻居可以自动核对并导入发行方目录；接受表和兑换比例仍需各节点自己设置。计划保存原参与方路由，租约更新不新建积分计划。入站 HTTP 与出站邮箱共用接单及记账守卫。

## 7. 产品与验证

完整 Windows SDK 和 Docker 镜像均包含积分模块与控制台。账户页可以设置模式、主动加分、接受表、还账和两方/三方互换；发现页在统一业务条件中选择支付方式并给出所用发行方与总成本上限。

自动化覆盖账本分录、签名与双方授权、预留防重复消费、额度、原样品绕过、真实 HTTP Agent、原交付恢复、整体提交恢复和原积分退款。四个实际安装节点使用真实代码 Agent 验证三种服务模式与三跳兑换。跨设备互联网可达性、真实人群对积分价值的长期认可仍需后续实际使用验证。
